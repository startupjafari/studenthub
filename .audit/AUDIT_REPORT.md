# Итоговый отчёт аудита

## 1. Резюме

Аудит прошёл по 148 бизнес-процессам шести групп: учётки и доступ, структура вуза, учебный
процесс, услуги и карьера, соцчасть, коммуникации и инфраструктура. Каждый процесс сверен с
кодом API и веба. Ссылки на строки — в `.audit/findings/<группа>.md`.

**Общее состояние.** Платформа функционально полная: почти все процессы доходят до конца.
Но у большинства есть пробелы на краях: права на чужие данные, гонки статусов, тихая обрезка
списков, удаление каскадом. Целиком работают без замечаний 27 процессов, с проблемами — 116,
сломаны 4–5. Unit-тесты модулей зелёные: ~950 тестов прогнаны агентами по группам. Но у ряда
процессов тестов нет вовсе: посещаемость, портфолио, учебный план, часть карьеры.

**Главное (P0, 6 шт.):**

- Включённые плановые техработы роняют весь API для всех ролей (B-F01).
- Преподавателя нельзя назначить на курс ни из одного клиента, поэтому преподавательские
  сценарии на новых курсах мертвы (C-F01).
- Удаление пары или версии расписания каскадом стирает посещаемость (C-F11).
- PRIVATE- и UNIVERSITY-записи портфолио уходят в публичное резюме и работодателю
  (E-F01 = D-F14).
- Забаненный участник группы читает её новые сообщения через поиск (F-F01).
- Мобильные пуши по умолчанию выключены, а iOS включить их не может (F-F09).

**Темы P1 (64 шт.):**

- **Права и утечки:**
  - токен мини-аппа принимается WebSocket'ом;
  - удалённый сотрудник сохраняет доступ через Telegram;
  - деканат видит черновики заявок;
  - статьи и опросы закрытого профиля отдаются по прямому запросу;
  - репост показывает снятый оригинал;
  - истёкший допуск компании к вузу не проверяется;
  - правка одобренной вакансии обходит модерацию.
- **Доступность:**
  - лимиты входа и регистрации считаются по IP, и кампус за NAT упирается в 429;
  - статус вуза BLOCKED ничего не блокирует.
- **Целостность:**
  - удаление группы стирает курсы, экзамены и материалы;
  - удаление задания стирает оценённые работы;
  - повторное одобрение демо-заявки создаёт вуз-дубликат;
  - решение по жалобе применяется дважды;
  - пустое сообщение остаётся при сбое вложения;
  - официальные чаты дублируются.
- **Тихая обрезка списков:** `take` без порядка по актуальности. Студент не видит новые
  задания, у декана видны 200 самых старых экзаменов, очередь записей в деканат вытесняется.
- **Производительность:**
  - список чатов читает все сообщения чатов страницы;
  - лента запрашивает каждую картинку отдельно и упирается в троттлер;
  - уведомление и письмо уходят на каждое сообщение;
  - ночная чистка держит в памяти весь листинг бакета.
- **Масштабирование:** socket.io без Redis-адаптера, «онлайн» хранится в памяти процесса,
  поэтому второй инстанс API работать не будет.

**P2 (108 шт.)** — UX-пробелы, мёртвый код (эндпоинты без клиентов, отложенные сообщения без
UI), мелкая производительность и недостающие тесты.

**Подход к исправлению.** Сначала P0, затем P1 по группам, затем P2 пакетами по модулям.
Изменения API должны оставаться обратно совместимыми: веб, iOS, Android и мини-апп ходят в
один API. Ломающие изменения формы ответа и применение миграций — через `.audit/QUESTIONS.md`.

## 3. Проблемы

### P0 — критично (6)

#### B-F01 Плановые техработы роняют весь API: `maintenanceFrom` из Redis-кэша не превращается обратно в Date

- Процесс: B-10 (и B-11 — `GET /platform/state`)
- Файлы: apps/api/src/modules/platform/platform.service.ts, apps/api/src/modules/platform/platform.service.spec.ts, apps/api/src/common/guards/maintenance.guard.ts
- Описание: `PATCH /platform/maintenance` со `startsInMinutes > 0` пишет `maintenanceFrom` в БД. Первое чтение после записи идёт из БД (Date) и кладёт строку в Redis как JSON. Следующее чтение (через ≤5 с, когда истекает память процесса, или сразу на другом инстансе) берёт строку из кэша, и `maintenanceFrom` остаётся строкой. `MaintenanceGuard` → `maintenanceActive` падает с `TypeError: this.memo.from.getTime is not a function`. Каждый запрос к API, кроме маршрутов с `@MaintenanceExempt` (вход, мини-апп, platform, health), получает 500 у всех ролей, включая платформенные. `GET /platform/state` пока окно не истекло падает с `TypeError: row.maintenanceFrom?.toISOString is not a function`. Падение не заканчивается вместе с окном: `maintenanceFrom` остаётся в строке БД, а `from.getTime()` вычисляется раньше проверки срока. API лежит, пока кто-то явно не снимет режим: `minutes: null` записывает `from = null`. Подтверждено временным jest-тестом в scratchpad: Redis отдаёт `JSON.stringify` строки с `maintenanceFrom`, получены обе TypeError. В platform.service.spec.ts путь через кэш при плановых работах не покрыт: там `setup(..., cached = null)`.
- Решение: в `reviveDates` восстанавливать и `maintenanceFrom`, лучше — все DateTime-поля модели списком. Добавить в спецификацию кейс «плановые работы, состояние из кэша» для `maintenanceActive` и `publicState`. В `MaintenanceGuard` ловить исключение `maintenanceActive` и пропускать запрос — как уже сделано для сбоя чтения БД в `read()`.
- Стоп-точки: нет

#### C-F01 Преподавателя нельзя назначить на дисциплину ни из одного клиента — преподавательские сценарии на новых курсах мертвы

- Процесс: C-01 (каскадно C-04, C-11, C-13, C-15, C-16, C-17)
- Файлы: apps/web/src/views/course-admin/ui/create-course-modal.tsx, apps/web/src/views/course-admin/ui/course-admin-view.tsx, новый apps/web/src/views/course-admin/ui/edit-course-modal.tsx, словари i18n CourseAdmin

#### A-F02 Лимиты публичных auth-маршрутов считаются по IP: кампус за NAT упирается в 429 на входе, регистрации и refresh

## 4. Рекомендуемый порядок исправлений

Сначала все P0 (данные и доступ), затем P1 по группам, затем P2 пакетами по модулям. Задачи со стоп-точками («миграция», «контракт», «новая зависимость») выполняются с созданием миграции/изменения, но применение миграций к БД и изменение публичного контракта — через `.audit/QUESTIONS.md`. Детальная очередь — `.audit/TASKS.md`.

1. P0 B-F01 — Плановые техработы роняют весь API: `maintenanceFrom` из Redis-кэша не превращается обратно в Date
2. P0 C-F01 — Преподавателя нельзя назначить на дисциплину ни из одного клиента — преподавательские сценарии на новых курсах мертвы
3. P0 C-F11 — Удаление пары (и версии расписания) каскадом стирает всю историю посещаемости по ней
4. P0 E-F01 — PRIVATE- и UNIVERSITY-записи портфолио уходят в публичное резюме и в карточку работодателя
5. P0 F-F01 — Забаненный участник группы продолжает читать её переписку через глобальный поиск по сообщениям
