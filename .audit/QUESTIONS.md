## Q1. Применить миграцию `20261017120000_attendance_pair_restrict` (FIX-C-F11, P0)

Удаление пары больше не стирает посещаемость: сервис отказывает с 409, а на уровне БД FK
посещаемость → пара меняется с CASCADE на RESTRICT. Данные не меняются, только ограничение:

```sql
ALTER TABLE "attendance" DROP CONSTRAINT "attendance_pair_id_fkey";
ALTER TABLE "attendance" ADD CONSTRAINT "attendance_pair_id_fkey" FOREIGN KEY ("pair_id") REFERENCES "pairs"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
```

Применить: `set -a && . apps/api/.env && set +a && pnpm exec prisma migrate deploy` (локально), на проде — через обычный деплой миграций.
Продуктовый вопрос: пару с отметками сейчас можно только перенести (день/время). Нужен ли «архив пары» (мягкое удаление с переносом предмета/группы в Attendance)?

## Q9. Порядок ленты (FIX-E-F06) — решение продукта + миграция

Сейчас лента сортируется строго: `pinnedAt → priority → createdAt`. Из-за этого объявление вуза годичной
давности стоит выше сегодняшнего поста группы, а отложенный пост встаёт по времени создания, а не по
времени выхода. Чтобы исправить, нужно:

1. сортировать по моменту выхода (`publishedAt`); старые строки заполнить миграцией данных
   `UPDATE posts SET published_at = created_at WHERE published_at IS NULL AND status = 'PUBLISHED'`;
2. пересобрать индекс ленты (рукописный SQL, как в 20261010131500_feed_order_index);
3. решить, как учитывать приоритет аудитории.

Варианты для пункта 3:

- (а) приоритет только внутри дня: `pinnedAt, date_trunc('day', publishedAt) desc, priority desc, publishedAt desc, id`;
- (б) приоритет только у закреплённых, остальное — по времени;
- (в) оставить как есть.

Задача помечена [blocked] до ответа. Миграцию подготовлю под выбранный вариант, но применять её не буду.

## Q10. Email в разном регистре — данные и индекс (FIX-A-F01)

В коде сделано: email приводится к нижнему регистру на входе. Вход, сброс пароля и проверки дублей
ищут сначала точное совпадение, затем `LOWER(email)` (для старых строк в смешанном регистре). Если
совпадений несколько — отказ и warn в логе. Чтобы убрать запасной поиск и закрыть дубли на уровне
БД, нужна разовая работа с данными. Это изменение данных на проде — только с вашего подтверждения:

(a) Проверка коллизий:
SELECT lower(email), count(_) FROM users GROUP BY 1 HAVING count(_) > 1;
SELECT lower(email), count(_) FROM invites WHERE email IS NOT NULL AND status = 'PENDING' GROUP BY 1 HAVING count(_) > 1;
(b) Если коллизий нет или они разобраны вручную:
UPDATE users SET email = lower(email) WHERE email <> lower(email);
UPDATE invites SET email = lower(email) WHERE email <> lower(email);
(c) Индексы (рукописная миграция — Prisma не описывает индексы по выражению, и следующий
`migrate diff` может предложить их удалить):
CREATE UNIQUE INDEX CONCURRENTLY users_email_lower_key ON users (lower(email));
CREATE INDEX CONCURRENTLY invites_email_lower_idx ON invites (lower(email));

После (b) запасной поиск без учёта регистра в коде можно удалить.
