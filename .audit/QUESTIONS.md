## Q1. Применить миграцию `20261017120000_attendance_pair_restrict` (FIX-C-F11, P0)

Удаление пары больше не стирает посещаемость: сервис отказывает с 409, а на уровне БД FK
посещаемость → пара меняется с CASCADE на RESTRICT. Данные не меняются, только ограничение:

```sql
ALTER TABLE "attendance" DROP CONSTRAINT "attendance_pair_id_fkey";
ALTER TABLE "attendance" ADD CONSTRAINT "attendance_pair_id_fkey" FOREIGN KEY ("pair_id") REFERENCES "pairs"("id") ON DELETE RESTRICT ON UPDATE CASCADE;
```

Применить: `set -a && . apps/api/.env && set +a && pnpm exec prisma migrate deploy` (локально), на проде — через обычный деплой миграций.
Продуктовый вопрос: пару с отметками сейчас можно только перенести (день/время). Нужен ли «архив пары» (мягкое удаление с переносом предмета/группы в Attendance)?

## Q2. Пуши: включение при привязке устройства (FIX-F-F09, P0)

Сделано: новая привязка токена устройства (или перехват токена от другого аккаунта) включает
`pushEnabled`; повторная регистрация того же токена при запуске настройки не трогает. iOS теперь
шлёт `pushEnabled/emailEnabled`. Компромисс: выход и вход на том же телефоне снова включает пуши —
отличить «выключил сам» от «не трогал» без нового поля нельзя. Нужно ли поле `pushOptOutAt`
(миграция), чтобы явный отказ переживал перевход? Отдельно: Android регистрирует токен и без
разрешения ОС — сервер включит флаг, но система ничего не покажет.

## Q3. Разовая чистка привязок Telegram у ранее удалённых аккаунтов (FIX-A-F04)

Теперь удаление аккаунта удаляет и привязку Telegram, а бот/мини-апп/уведомления удалённых не пускают.
Старые строки удалённых до исправления остались (использовать их уже нельзя). Удалить разово?

```sql
DELETE FROM telegram_accounts WHERE user_id IN (SELECT id FROM users WHERE deleted_at IS NOT NULL);
```
