# Аудит производительности iOS-клиента StudentHub

Цель: скорость и ощущение мгновенности на уровне Telegram. Аудит — только чтение кода
(`apps/ios/Sources`, ноябрь 2026). Профилирования в Instruments не было: «влияние» — оценка
по коду, а не замер. Все пути ниже — от `apps/ios/Sources/`.

> **Ограничение среды.** Репозиторий ведётся из Linux: приложение здесь не собирается и
> Instruments не запускается. Сборка, тесты и замеры после каждой итерации — на Mac
> (Xcode / `xcodebuild test`), см. раздел «Как мерить».

## Этап 0. Что за проект

|                 |                                                                                                                                                                               |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Стек            | Нативный Swift: SwiftUI + UIKit там, где нужен контроль (лента переписки — `UICollectionView` с SwiftUI-ячейками через `UIHostingConfiguration`)                              |
| Минимальная iOS | 17.0; Swift 5 mode, `SWIFT_STRICT_CONCURRENCY: targeted`                                                                                                                      |
| Зависимости     | SPM через XcodeGen (`apps/ios/project.yml`): GRDB 7, socket.io-client-swift 16, Sentry 8. Вторая сборка — xtool из Linux (`apps/ios/Package.swift`, без Sentry)               |
| Архитектура     | MVVM на `@Observable`-моделях; общие сервисы — статический контейнер `AppServices` (`App/AppServices.swift`); данные и сеть — `Core/<Область>`, экраны — `Features/<Область>` |
| Сеть            | Актор `APIClient` с одним `URLSession` (`Core/Network/APIClient.swift:43`), общие `JSONCoding`, `PagedLoader` для курсорных списков; refresh токена одним запросом            |
| Хранилище       | GRDB `DatabasePool` (`Core/Storage/AppDatabase.swift`): chat, message, attachment, draft, folder, pair/pairChange. Остальное — только сеть                                    |
| Картинки        | `ImageMemoryCache` (NSCache 80 МБ, декод вне main, `CGImageSource`-даунсемплинг) + `RemoteImage`/`AvatarView`/`LQIP` — `Features/Feed/FeedComponents.swift`                   |
| Реальное время  | socket.io → `RealtimeCoordinator` пишет события в GRDB, экраны наблюдают базу (`ValueObservation`)                                                                            |
| Навигация       | `AppRouter` (`Core/Navigation/AppRouter.swift`): свой `NavigationStack` на вкладку, диплинки                                                                                  |
| Точка входа     | `App/StudentHubApp.swift` → `AppDelegate` → `RootView` (восстановление сессии, экран загрузки) → `AppShellView` (вкладки)                                                     |

**Ключевые экраны:** главная роли (`Features/StudentStudy/StudentHomeView.swift`,
`Features/Workspace/RoleHomeView.swift`, `Features/Teaching/TeachingDashboardView.swift`),
расписание (`Features/Study/ScheduleView.swift`), чаты — список и переписка
(`Features/Chats/ChatListView.swift`, `Features/Chats/Thread/*`), лента
(`Features/Feed/FeedView.swift`), уведомления (`Features/Feed/FeedScreens.swift`),
профиль (`Features/Profile/ProfileView.swift`), заявки, библиотека, сообщество.

**Что уже хорошо:** чаты, папки, черновики и расписание открываются из GRDB без сети;
чтение базы в наблюдениях — вне main; декодирование картинок — вне main с даунсемплингом;
один `URLSession`; общие JSON-кодеры и ISO-форматтеры; главная студента и лента грузят блоки
параллельно (`async let`); реакции, закладки, удаление поста, заявки в друзья в ленте —
оптимистично; везде `@Observable`, `ObservableObject`/`@Published` нет; длинные списки —
`List`/`LazyVStack`/`UICollectionView`; токены `Motion` с учётом «уменьшения движения».

## Этап 1. Проблемы

Отсортировано по соотношению «эффект для пользователя / трудозатраты»: сверху — то, что
даёт больше всего за меньшую работу. Влияние: В — высокое, С — среднее, Н — низкое.
Сложность: Н — низкая, С — средняя, В — высокая.

### Переписка и список чатов — главный источник «тупит»

Корень: на каждое изменение в базе — работа O(N) по всем загруженным сообщениям, в основном
на главном потоке, и N растёт с каждой страницей истории.

## Этап 2. План итераций

Каждая итерация самостоятельна: её можно влить и откатить отдельно, бизнес-логика и вид не
меняются (кроме исчезновения спиннеров и мгновенного отклика). Порядок — по выигрышу на
единицу работы; внутри итерации — отдельные коммиты по пунктам.

**Урок прошлой попытки.** Своя раскладка ленты с кэшем высот (#479/#480) на устройстве дала
пустоты между сообщениями и откатана (#481). Поэтому здесь — никаких переписываний раскладки
вслепую: только снятие лишней работы поверх проверенного системного списка, с замером до и
после.

1. **Переписка без лишней работы** — п. 1, 2, 3, 4, 5, 6, 7, 10, 11, 15. Самый ощутимый
   выигрыш: убирает пересчёт всей ленты и всего списка чатов на каждое событие и разбор
   текста на прокрутке. Плюс signpost'ы ленты (см. ниже).
2. **Мгновенный запуск** — п. 16, 17, 18, 19. Приложение открывается сразу по известному
   токену, база прогревается в фоне, счётчик непрочитанного — один.
3. **Оптимистичный UI** — п. 20 (без кэша), 21, 22, 23, 24, 50. Действия отвечают сразу,
   откат при ошибке.
4. **Лента и картинки без дисковых изменений** — п. 33, 34, 36, 37, 38, 39, 40, 42, 43.
5. **Кеш экранов (stale-while-revalidate)** — п. 20 (кэш), 25, 26, 27, 28, 29, 31, 32.
   Общий механизм «последний ответ на диске → показать сразу → обновить фоном» для
   `RemoteContent`/`PagedList` и главной.
6. **Дисковый кэш картинок** — п. 35. Свой, в Caches/, без зависимостей. Если понадобится
   Nuke — отдельное согласование.
7. **Переписка: глубже** — п. 8, 9, 12, 13, 14. Точечная перенастройка при прочтении,
   наблюдение окном и сборка ленты вне main, кэш в `ChatBubbleStack`. Самая рискованная
   часть — только с замером на устройстве после каждого шага.
8. **Прочее** — п. 30, 41, 44, 45, 46, 47, 48, 49.

### Требует бэкенда

- Окно повторного использования refresh-токена шире предела ожидания продления на
  клиенте. Механизм уже есть (`REFRESH_REUSE_GRACE_MS`, `apps/api/src/modules/auth/auth.service.ts`:
  повтор только что ротированного токена в окне отдаёт уже выданного преемника), но
  окно по умолчанию — 10 с, а клиент ждёт ответа на продление до 60 с
  (`AuthAPI.refreshTimeout`). Ответ, потерянный после ротации, и повтор позже 10 с
  сервер сочтёт кражей и погасит всю цепочку сессий. Нужно: `REFRESH_REUSE_GRACE_MS=60000`
  в окружении API (код менять не нужно) и строка в `docs/PROJECT.md` §7.2.
- Агрегатный `/me/home` (и аналог для преподавателя) вместо ~9 запросов главной.
- Дельта-синхронизация `?since=`/`updatedAfter`: список чатов (сейчас до 500 строк при
  открытии и `catchUp` на каждый возврат), лента, уведомления, заявки, расписание (сейчас
  всегда целиком). У сообщений чата дельта уже есть (`Core/Chats/ChatMessagesAPI.swift:66-70`).
- `ETag`/`Cache-Control` на редко меняющиеся GET: `schedule`, `users/me`, `grades`,
  `attendance`, `platformState`, `library/settings`, настройки.
- Счётчик непрочитанных уведомлений — в ответе страницы уведомлений и событием сокета.
- `courseId` в ответе `/schedule` (карточка пары без трёх запросов).
- События сокета для состояния камер и аудиторий вместо опроса раз в 30/60 с
  (`Features/Security/SecurityCamerasView.swift:127-130`,
  `Features/Security/SecurityRoomsView.swift:203-206`).
- Проверить сжатие ответов (gzip/br) на прокси.
- Blurhash/LQIP уже приходят в медиа (`placeholder`) — достаточно; новых полей не нужно.

### Итерация 3 — оптимистичные действия

- **Сценарий:** в ленте трижды быстро нажать лайк; переключить «Показывать почту» туда-сюда
  пять раз; в уведомлениях «Прочитать все»; то же в авиарежиме.
- **Смотреть:** `Actions/OptimisticSend` — один интервал на серию нажатий (слитые —
  `OptimisticMerged`); `OptimisticRollback` — только в авиарежиме или при отказе.
  Network-инструмент: один запрос на серию. Время «нажал → экран изменился» — кадр
  (Animation Hitches без провала на нажатии), не зависит от сети.

  плитки × масштаб (не 1260 px на аватар); `Images/FeedPrefetch` опережает появление
  постов. Animation Hitches на прокрутке ленты — сравнить с базой. Core Animation (на
  устройстве) / Debug → Color Offscreen-Rendered (симулятор): у фото ленты не должно быть
  внеэкранных проходов размытия. Allocations — пик памяти на прокрутке ленты.

### Итерация 5 — кеш экранов

- **Сценарий:** открыть главную, ленту, уведомления, оценки, профиль; убить приложение;
  включить авиарежим; открыть снова и пройти те же экраны; выключить авиарежим.
- **Смотреть:** `ScreenCache/ScreenCacheRead` — `hit` на каждом экране; содержимое на
  экране — в пределах кадра-двух от появления экрана (а не после сети); полоса «не свежее»
  в авиарежиме. При возврате на экран — без спиннера, обновление фоном;
  `notifications/unread-count` на холодном старте — один раз (раньше до трёх).

### Итерация 6 — дисковый кеш картинок

- **Сценарий:** пролистать ленту и чат с фото; убить приложение; открыть и пролистать снова
  (с сетью и в авиарежиме).
- **Смотреть:** `Images/ImageDiskHit` вместо `ImageFetch` для уже виденных картинок;
  Network — повторных загрузок картинок после перезапуска почти нет; `ImageJoined` —
  ячейки не качают одну картинку дважды. Размер кеша — Настройки → Основные → Хранилище
  iPhone → StudentHub («Документы и данные»), не больше ~200 МБ картинок + 20 МБ экранов.

## Замеры на устройстве: базовая линия плана по Telegram-iOS

План переделки по разбору Telegram-iOS (этапы 0–6) принимает шаги только по цифрам с
устройства. Эта таблица — точка «до»; после каждого этапа сюда добавляется строка «после»
на тех же устройствах и тех же сценариях.

- **Тестовый чат.** Отладочная сборка → Настройки → «Разработка» → «Засеять чат для
  замеров (5000)». Чат `PerfFixture` одинаков на любом устройстве, история только из базы,
  сети не нужно. Фото в нём без файлов: плитки встают нужного размера и показывают
  «не загрузилось» — для замера раскладки этого хватает, для замера картинок — нет.
- **Новые метки** (`Chats`): `ChatOpen` — от появления экрана переписки до первого
  показанного кадра ленты; `CellRemeasure` — ячейка пересчитала высоту после показа (их
  число на прокрутку — главный счётчик для кеша высот).
- **Устройства:** самый слабый iPhone на iOS 17 (XR/XS) и текущий Pro на iOS 26.
- **Сценарии на тестовом чате:**
  1. Открыть чат из списка (`ChatOpen`).
  2. Пролистать вверх 20 экранов и вернуться вниз (Animation Hitches, `CellRemeasure`).
  3. Отправить 10 сообщений подряд (hitches, `SnapshotApply`).
  4. Поставить 20 реакций на разные сообщения (hitches, `CellRemeasure`).
  5. 10 раз смахнуть клавиатуру жестом вниз (запись экрана 120 Гц на Pro).
- **Ещё:** прокрутка списка чатов и ленты постов на живом аккаунте (hitches).
