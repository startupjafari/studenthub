# Стенд «IP-камеры вуза»

Эмулятор видеорегистратора с камерами для разработки модуля камер без железа. Ведёт себя
как регистратор Hikvision в закрытой сети вуза: RTSP с digest-авторизацией, основной и
второй поток, смешанные кодеки, ONVIF, недоступность снаружи, плохая сеть и обрывы.

Стенд отдельный от dev-стека `docker/dev/compose.yml` и по умолчанию не запущен.
Нагрузка: регистратор кодирует три канала и занимает около одного ядра процессора.

## Запуск

```bash
cd docker/camera-sim
docker compose up -d                      # регистратор, вход веб-камеры, плохая сеть
docker compose --profile onvif up -d      # + ONVIF-устройство (необязательно)
docker compose down                       # остановить
```

Каналы 2 и 3 регистратор генерирует сам, они работают сразу. Канал 1 — ваша веб-камера,
он появляется, когда запущен `webcam.ps1` (ниже).

## Что внутри

```
          хост (WSL / Windows)
               │ 127.0.0.1:18554 — только публикация веб-камеры
               │ 127.0.0.1:8474  — пульт помех
     ┌─────────┴──────────────── сеть edge ────────────┐
     │  ingest                  bad-network            │
     └────┬─────────────────────────┬──────────────────┘
          │                         │
   ┌──────┴── сеть campus (internal: без выхода наружу) ─────────┐
   │  ingest ──► nvr 10.77.0.10:554 ◄── bad-network 10.77.0.30:554 │
   │                    ▲                                         │
   │                    └── onvif 10.77.0.40:8080 (ONVIF), :554    │
   │  здесь же будет наш агент; пока вместо него — probe          │
   └──────────────────────────────────────────────────────────────┘
```

Регистратор (`nvr`) живёт только в сети `campus`. Контейнер вне её его не видит ни по IP, ни по
имени, а из `campus` нет выхода в интернет. Наш агент подключается к `campus` и сам ходит
наружу, к платформе. Так он будет устроен и в вузе.

С самого WSL-хоста адрес 10.77.0.10 всё же отвечает: хост Docker всегда видит свои сети.
Изоляцию проверяйте из контейнера, а не с хоста.

## Учётные данные и адреса

Только для разработки. Значения по умолчанию меняются переменными окружения перед `up`.

| Что                           | Логин    | Пароль        | Переменная                |
| ----------------------------- | -------- | ------------- | ------------------------- |
| Просмотр камер (RTSP, digest) | `admin`  | `Camera12345` | `CAM_PASSWORD`            |
| Публикация веб-камеры         | `webcam` | `webcam-dev`  | `WEBCAM_PUBLISH_PASSWORD` |

| Канал | Основной поток                                                     | Второй поток        | Источник         |
| ----- | ------------------------------------------------------------------ | ------------------- | ---------------- |
| 1     | `/Streaming/Channels/101` — H.264 720p (`-MainCodec h265` — H.265) | `/102` — H.264 360p | веб-камера       |
| 2     | `/Streaming/Channels/201` — H.265 720p                             | `/202` — H.264 360p | тестовая таблица |
| 3     | `/Streaming/Channels/301` — H.264 720p                             | `/302` — H.264 360p | цветные полосы   |

Адреса — изнутри сети `campus`:

- напрямую: `rtsp://admin:Camera12345@nvr:554/Streaming/Channels/201`
- через плохую сеть: `rtsp://admin:Camera12345@bad-network:554/Streaming/Channels/201`
- ONVIF: `http://onvif:8080/onvif/device_service`, `.../media_service`

## Веб-камера (канал 1)

На Windows нужен ffmpeg: `winget install Gyan.FFmpeg`, потом новое окно PowerShell.
WSL2 сам не видит веб-камеру, поэтому её захватывает Windows и публикует во вход стенда.

```powershell
cd <репозиторий>\docker\camera-sim
powershell -ExecutionPolicy Bypass -File .\webcam.ps1
powershell -ExecutionPolicy Bypass -File .\webcam.ps1 -MainCodec h265
powershell -ExecutionPolicy Bypass -File .\webcam.ps1 -Camera "HD Webcam" -Size 640x480
```

Ctrl+C останавливает публикацию, и канал 1 уходит в «офлайн», как отключённая камера.
Если камера не умеет отдавать 1280x720, ffmpeg пишет «Could not set video options»:
укажите `-Size 640x480`.

Если `127.0.0.1:18554` с Windows не отвечает, значит выключен проброс портов WSL. Включите
`localhostForwarding` в `.wslconfig` или передайте адрес WSL (`wsl hostname -I`) параметром
`-Address`. Во втором случае порт входа придётся публиковать не только на 127.0.0.1
(`ports` сервиса `ingest`).

## Проверить, что камеры отвечают

Пока агента нет, его роль играет `probe`: тот же ffmpeg внутри сети `campus`.

```bash
# кодек и разрешение
docker compose run --rm probe sh -c 'ffprobe -v error -rtsp_transport tcp \
  -show_entries stream=codec_name,width,height -of csv=p=0 \
  rtsp://admin:$CAM_PASSWORD@nvr:554/Streaming/Channels/201'

# снимок кадра → docker/camera-sim/snapshots/ch2.jpg
docker compose run --rm probe sh -c 'ffmpeg -v error -rtsp_transport tcp \
  -i rtsp://admin:$CAM_PASSWORD@nvr:554/Streaming/Channels/201 -frames:v 1 -y /snapshots/ch2.jpg'
```

Что отвечает регистратор:

| Ситуация                                 | Ответ                                           |
| ---------------------------------------- | ----------------------------------------------- |
| Без пароля                               | `401`, `WWW-Authenticate: Digest realm="ipcam"` |
| Неверный пароль                          | `401 Unauthorized`                              |
| Канал без сигнала (веб-камера выключена) | `400 Bad Request`                               |

## Плохая сеть и сбои

Помехи действуют только на подключения через `bad-network:554`. Пульт —
API Toxiproxy на `127.0.0.1:8474`.

```bash
T=http://127.0.0.1:8474/proxies/nvr-rtsp

# задержка 800 ± 200 мс на поток от камеры
curl -s -XPOST $T/toxics -d '{"name":"lag","type":"latency","stream":"downstream","attributes":{"latency":800,"jitter":200}}'
# слабый канал: 50 КБ/с — основной поток канала 2 весит ~120 КБ/с, видео начинает отставать
curl -s -XPOST $T/toxics -d '{"name":"slow","type":"bandwidth","stream":"downstream","attributes":{"rate":50}}'
# убрать помеху
curl -s -XDELETE $T/toxics/lag

# связь пропала и вернулась
curl -s -XPOST $T -d '{"enabled":false}'
curl -s -XPOST $T -d '{"enabled":true}'
```

Перезагрузка камеры — `docker compose restart nvr`: все потоки рвутся, через пару секунд
регистратор отвечает снова. Агент обязан переподключиться сам.

Toxiproxy передаёт только TCP, поэтому агент через `bad-network` ходит с RTSP поверх TCP.

## ONVIF

Профиль `onvif` поднимает ONVIF-устройство поверх канала 2. Оно отвечает на
`GetDeviceInformation`, `GetProfiles` (`main_stream`, `sub_stream`) и `GetStreamUri`.
Адреса потоков выдаёт на себя (`rtsp://10.77.0.40:554/...`) и проксирует их в регистратор.

Особенности эмулятора (сторонний `daniela-hase/onvif-server`):

- Ему нужна сеть `edge`: WSDL при старте качает XSD-схемы с www.onvif.org. Без них каждый
  запрос отвечает `500`. Настоящей камере интернет не нужен.
- Кодек в профилях он всегда называет H264, даже когда поток в H.265. Агенту это полезно:
  кодек надо брать из описания самого RTSP-потока, а не из ONVIF. У дешёвых камер
  такое расхождение тоже встречается.
- Образ закреплён по digest: тегов с версией у проекта нет, только `latest`.

## Агент

Профиль `agent` запускает настоящего агента StudentHub (`apps/camera-agent`) внутри сети
кампуса — так же, как его поставят в вузе. Он видит регистратор и ходит к API на хосте
разработчика (`host.docker.internal:3001`).

1. Запустить API (`pnpm dev`), войти админом вуза, в «Камерах» включить модуль и добавить
   агента — скопировать токен.
2. Поднять агента:

   ```bash
   # токен целиком из окна «Токен агента»: shca_ и 43 символа
   STUDENTHUB_AGENT_TOKEN='<токен агента>' docker compose --profile agent up -d --build agent
   docker compose logs -f agent
   ```

3. Через пару секунд агент «На связи». Добавить камеры с адресами изнутри кампуса:
   `rtsp://nvr:554/Streaming/Channels/202`, логин `admin`, пароль `Camera12345`. С неверным
   паролем камера получит «Неверный пароль», с несуществующим адресом — «Нет связи».

Камеры проверяются раз в 15 секунд (`STUDENTHUB_PROBE_INTERVAL_S`). Ключ агента лежит в томе
`agent_state`: `docker compose --profile agent down -v` его удаляет, и следующему запуску
понадобится перевыпущенный токен.

## Чего стенд не покажет

Перед пилотом всё равно нужна настоящая камера или регистратор вуза с учёткой только на
просмотр:

- особенности прошивок конкретных вендоров (метки времени, RTCP, нестандартные ответы);
- поток через настоящий регистратор с десятками каналов;
- ISAPI Hikvision (снимок по HTTP, список каналов) — эмулятор отдаёт только RTSP и ONVIF;
- ONVIF WS-Security (авторизация ONVIF-запросов) и обнаружение по WS-Discovery
  через границы сетей;
- UDP-транспорт под реальными потерями: помехи Toxiproxy работают только с TCP.
