# StudentHub — Каталог модулей

> Обзор продукта по модулям: для каждого — **что это, для кого и как работает**.
> Под каждым модулем — сноска «Технически» с реализующим backend-модулем и экраном фронтенда.
> Первоисточник по продукту и контрактам — [`docs/PROJECT.md`](./PROJECT.md); при расхождении верить коду и PROJECT.md.

---

## 1. Что такое StudentHub

Закрытая многоролевая образовательная платформа для университетов. Объединяет **академическую жизнь** (расписание, оценки, задания, посещаемость, экзамены, заявки в деканат, документы) и **социальную активность** (лента, чаты, события, профили) в одном приложении.

**Ключевой принцип — платформа полностью закрыта.** Публичной регистрации нет: попасть внутрь можно только по персональной ссылке-приглашению (инвайту) от вышестоящей роли. Это защита на уровне архитектуры, а не отдельных проверок.

### Восемь ролей и четыре зоны

```
PLATFORM_ADMIN            управляет всей платформой         ┐
└── PLATFORM_MODERATOR    модерация контента платформы      ┘ Платформенная зона

UNIVERSITY_ADMIN          управляет своим вузом             ┐
└── UNIVERSITY_MODERATOR  модерация контента одного вуза    ┘ Университетская зона

DEAN                      управляет факультетом             ┐
TEACHER                   работает со своими группами       │ Учебная зона
STAROSTA                  координирует свою группу          ┘

STUDENT                   базовый пользователь              ┐ Социальная зона — все роли
                                                            ┘ (посты, чаты, события, профили)
```

- **Инвайт выдаётся только на роль строго ниже своей и в пределах своего scope.** `PLATFORM_ADMIN` создаётся единственным способом — seed-скриптом.
- **Scope** — область данных пользователя (`universityId` / `facultyId` / `groupId`), зашитая в JWT. Любой `:id` в маршруте проверяется на принадлежность scope (защита от IDOR).
- **Староста** — студент с надстройкой координации своей группы: у него все студенческие экраны плюс раздел управления группой, но **без** доступа к персональным данным одногруппников (оценки, документы, личные заявки).

Матрица «роль × функция» — источник истины и для бэкенда (guard'ы), и для фронтенда (что рендерится). Полная версия — [`docs/PROJECT.md` §2.2](./PROJECT.md).

## 2. Как читать этот документ

Каждый **модуль** — это законченная продуктовая функция, которую видит пользователь. Модуль обычно складывается из одного или нескольких backend-модулей NestJS (`apps/api/src/modules/*`) и одного или нескольких экранов фронтенда (`apps/web/src/views/*`), связанных общим контрактом из `packages/shared-schemas`.

Структура описания:

- **Что это** — назначение одним абзацем.
- **Для кого** — какие роли пользуются и в каком объёме.
- **Как работает** — ключевая механика.
- **Технически** — реализующие backend-модуль(и) и экран(ы).

## 3. Социальные модули

### 3.1 Посты и лента

**Что это.** Главная лента платформы — поток объявлений и публикаций. Пост может быть текстом с медиа, файлами, реакциями, комментариями (в виде веток), репостом; его можно закрепить или пожаловаться на него.

**Для кого.** Создавать посты могут все роли, кроме модераторов. Тип поста определяется ролью автора (пост платформы / университета / факультета / преподавателя / группы / личный), а **аудитория** (`ALL / UNIVERSITY / FACULTY / GROUP / SUBJECT / TEACHERS / PERSONAL`) задаётся при публикации и ограничена ролью автора. Закрепить чужой пост может только роль выше автора; модерация — модераторы своего scope.

**Как работает.** Лента собирается по видимости смотрящего: сервер строит выборку по его university/faculty/group scope, отдаёт cursor-пагинацией. Контент ранжируется по приоритету (сверху вниз): срочные уведомления → изменения расписания → ответы по заявкам → объявления вуза → факультета → группы → события → посты преподавателей → посты студентов. Поддержаны черновики и отложенная публикация (`SCHEDULED` — публикуется фоновой задачей каждую минуту). Медиа лежит в приватном бакете MinIO и отдаётся через presigned-URL.

> **Технически:** backend `posts` (лента = метод `feed`, отдельного модуля `feed` нет); экраны `views/home` (лента-дашборд студента), `views/feed` (лента для остальных ролей), виджет `widgets/feed-list`, фича `features/create-post`.

### 3.2 Чаты

**Что это.** Встроенный мессенджер в стиле Telegram: личные и групповые чаты с сообщениями, вложениями, реакциями, ответами-ветками, пересылкой, закреплением сообщений, блокировками и управлением участниками группы.

**Для кого.** Все роли. Типы чатов: `PRIVATE` (личный), `GROUP` (произвольная группа), `GROUP_OFFICIAL` (чат учебной группы), `SUBJECT` (по дисциплине), `FACULTY`, `DEAN` (чат с деканатом), `SUPPORT`, `EVENT`. Администраторы и модераторы не получают доступ к личным чатам без жалобы, и каждый такой доступ пишется в аудит.

**Как работает.** REST отвечает за список и создание чатов, историю сообщений, участников, вложения и настройки; сам обмен сообщениями (отправка, редактирование, удаление, отметки о прочтении, «печатает…») идёт в реальном времени через WebSocket (socket.io). Каждое WS-сообщение валидируется Zod-схемой; войти в комнату чата можно только после серверной проверки членства в БД, рассылка адресная — только участникам этого чата. Ссылки в сообщениях разворачиваются в превью фоновой очередью. На фронте — оптимистичная отправка (сообщение появляется мгновенно по временному id).

> **Технически:** backend `chats` (REST + `ChatGateway` для realtime); экран `views/chats`, крупный виджет `widgets/chat-window`. WS-события: `message:send/edit/delete/read`, `typing:start/stop` → `message:new/updated/deleted`, `typing:started/stopped`.

### 3.3 Профиль

**Что это.** Единый профиль пользователя в стиле ВКонтакте с ролевыми секциями и вкладками контента: **Профиль / Фото / Видео / Статьи / Опросы**. Включает свой профиль (редактирование, загрузка контента) и публичный просмотр чужого.

**Для кого.** Все роли. Набор полей зависит от роли: у студента — курс, год поступления, специальность, статус, интересы, навыки; у сотрудников — должность, учёная степень, кафедра, приёмные часы и т. д.

**Как работает.** Видимость профиля управляется полем `profileVisibility` (`PUBLIC / UNIVERSITY / FACULTY / GROUP / PRIVATE`). При просмотре чужого профиля API возвращает либо полную карточку (`full` — если смотрящий в нужной аудитории/scope или это друг), либо «визитку» (`limited` — только имя, аватар, роль, вуз/факультет). Надзорные роли своего scope видят `full` даже при `PRIVATE`, но такой доступ пишется в аудит. Персональные поля (email, телефон, номера, GPA) прячутся по настройкам приватности и не отдаются чужим. Аватар с кропом и обложка грузятся в MinIO; статус «в сети» берётся из активных WebSocket-соединений (`presence`). Контент вкладок: **Фото/Видео** (multipart или presigned-загрузка крупных видео), **Статьи** (markdown, обложка, теги, комментарии, закладки, расчёт времени чтения на бэке), **Опросы** (голосование с настраиваемой видимостью результатов), плюс **Портфолио** достижений.

> **Технически:** backend `users` (карточка + приватность), `profile-content` (фото/видео/альбомы/статьи), `polls` (опросы), `portfolio` (достижения), `friends` (дружба); экраны `views/portfolio`, `views/settings`, крупнейший виджет `widgets/user-profile` (`user-profile.tsx` свой, `public-user-profile.tsx` чужой).

### 3.4 События

**Что это.** Мероприятия и события с регистрацией участников: университетские, факультетские, групповые, учебные, социальные, онлайн.

**Для кого.** Просмотр — все роли (по видимости своего scope); создание/управление — управляющие роли (платформа, админ вуза, декан) и в ограниченном виде другие. Организатор видит список зарегистрировавшихся.

**Как работает.** Список фильтруется по видимости (предстоящие/прошедшие/мои). Пользователь регистрируется и отменяет участие; за ~час до события приходит напоминание (фоновая задача каждые 15 минут с защитой от повторной отправки).

> **Технически:** backend `events`; экран `views/events`, фича `features/create-event`. Также события сводятся в `views/calendar` и `views/today`.

### 3.5 Друзья

**Что это.** Социальный граф: заявки в друзья, список друзей, статус дружбы (для кнопки в чужом профиле).

**Для кого.** Все авторизованные роли.

**Как работает.** Заявки делятся на входящие и исходящие; отправка встречной заявки автоматически принимает существующую. Принятая дружба (или ожидающая от владельца) открывает доступ к полной карточке профиля.

> **Технически:** backend `friends`; UI встроен в `widgets/user-profile`.

## 4. Академические модули

### 4.1 Расписание

**Что это.** Учебное расписание: просмотр пар, аудиторий, замен и переносов, а также управление расписанием групп.

**Для кого.** Просмотр — все по scope роли (студент видит свою группу, преподаватель — свои занятия, декан — факультет). Управление контейнерами расписания — декан/админ вуза; отдельными парами — в т. ч. преподаватель (свои).

**Как работает.** Расписание состоит из контейнеров (расписание группы) и пар внутри них. При добавлении/изменении пары проверяются конфликты аудитории, преподавателя и группы. Разовое изменение (перенос/замена аудитории/отмена) сразу шлёт WebSocket-событие `schedule:changed` в комнату группы и ставит уведомление участникам.

> **Технически:** backend `schedules` (+ `pairs`, `schedule`), справочник аудиторий `rooms`; экраны `views/schedule`, виджет `widgets/schedule-grid`, фича `features/manage-schedule`.

### 4.2 Дисциплины и учебный план

**Что это.** Справочник дисциплин студента и его учебный план: список предметов, рабочее пространство одной дисциплины, статусы (сдано / учится / предстоит / не сдано) с прогрессом.

**Для кого.** Студент — просмотр своих дисциплин; декан/админ вуза — управление (назначение дисциплин группам, справочник предметов, семестры).

**Как работает.** В основе три сущности: справочник дисциплин вуза (subjects), семестры (terms) и назначение дисциплины группе (course). Учебный план студента совмещает его курсы с опубликованными оценками, показывая прогресс по каждому предмету.

> **Технически:** backend `courses` (subjects/terms/courses); экраны `views/courses`, `views/study-plan`, админ-экран `views/course-admin`.

### 4.3 Журнал и оценки

**Что это.** Электронный журнал: контрольные точки (колонки оценок), выставление баллов, публикация. Студент видит свои оценки и общий балл.

**Для кого.** Преподавательские роли ведут журнал; студент видит только **опубликованные** оценки своих дисциплин.

**Как работает.** Преподаватель создаёт колонки (контрольные точки), массово выставляет баллы и управляет публикацией (пока колонка не опубликована — это черновик, студенту она не видна). У студента экран оценок считает взвешенный балл по кредитам дисциплин.

> **Технически:** backend `gradebook`; экраны `views/gradebook` (преподаватель, матрица), `views/student-grades` и `views/academic` (студент).

### 4.4 Задания

**Что это.** Учебные задания по дисциплинам и полный цикл их сдачи: выдача преподавателем, сдача студентом, проверка и оценивание.

**Для кого.** Преподаватель создаёт, публикует, проверяет; студент видит опубликованные задания своей группы, сдаёт черновик или отправляет на проверку и видит только свою работу.

**Как работает.** Задание проходит жизненный цикл draft → PUBLISHED → CLOSED. Студент сохраняет черновик и отправляет работу; преподаватель в рабочем пространстве проверки ставит балл или возвращает на исправление. Каждое действие сопровождается уведомлением студенту.

> **Технически:** backend `assignments` (+ `submissions`); экраны `views/assignments` (`student-assignments-view`, `teacher-assignments-view`, `grading-workspace`).

### 4.5 Посещаемость

**Что это.** Учёт посещаемости занятий: отметки преподавателем или самоотметка студента по QR-коду.

**Для кого.** Преподаватель отмечает группу; студент видит свою сводку и может отметиться сам по QR.

**Как работает.** Преподаватель получает ростер занятия и массово проставляет отметки, либо показывает короткоживущий QR-код (живёт 90 секунд, подписан, содержит id пары и дату). Студент сканирует QR и делает check-in — операция идемпотентна (существующая отметка не перетирается), проверяются срок и подпись.

> **Технически:** backend `attendance`; экраны `views/attendance` (`student-attendance-view`, `teacher-attendance-view`, `attendance-roster`, `checkin-view`).

### 4.6 Экзамены

**Что это.** Экзаменационная сессия: назначение экзаменов, ведомости, допуски и результаты.

**Для кого.** Декан/преподаватель назначают экзамены и ведут ведомость; студент видит свою сессию с допуском и только собственным результатом.

**Как работает.** Управляющие роли создают экзамены и массово проставляют допуски и результаты; студенту показывается timeline его экзаменов.

> **Технически:** backend `exams`; экраны `views/exams` (`student-exams-view`, `exam-management-view`, `exam-results-roster`).

### 4.7 Учебные материалы

**Что это.** Хранилище учебных материалов группам с прикреплёнными файлами.

**Для кого.** Авторские роли (преподаватель, декан, админ вуза) создают материалы и прикрепляют файлы; студент видит и скачивает материалы своей группы.

**Как работает.** Материал создаётся для группы, файлы грузятся в приватный бакет MinIO и отдаются через presigned-URL с проверкой scope.

> **Технически:** backend `materials`; экран `views/materials`.

## 5. Сервисы деканата и документооборот

### 5.1 Документы

**Что это.** Защищённое личное хранилище документов студента плюс механизм запросов вуза на документы. Отдельный раздел с под-навигацией: обзор, мои документы, запросы университета, документы от университета, управление доступом, архив.

**Для кого.** Студент/староста — владеют своими документами и отвечают на запросы. Деканат и студ.офис (декан, модератор вуза) и преподаватель (учебные типы) — создают и проверяют запросы. Админ вуза управляет каталогом типов и сроками хранения. Платформенный админ обычного доступа к содержимому не имеет — только спец-режим с обязательной причиной, который пишется в аудит.

**Как работает.** Документ принадлежит владельцу; полный номер наружу не отдаётся (только маска вида `******4821`), файлы лежат в приватном бакете и доступны лишь через presigned-URL после проверки владения или выданного гранта. Владелец выдаёт и отзывает доступ (вузу / подразделению / конкретному пользователю), архивирует документы. Запросы вуза работают по схеме: сотрудник создаёт запрос с чек-листом позиций → студент собирает комплект, привязывая свои документы → сотрудник проверяет по позициям и финализирует. Фоновая задача ежедневно переводит документы в статусы EXPIRING/EXPIRED по срокам и уведомляет владельцев. Каждое действие пишется в журнал документа (`DocumentEvent`).

> **Технически:** backend `documents` (+ подмодули запросов и типов); экраны `views/documents`, `views/document-types` (админ), `views/platform-documents` (спец-доступ платформы).

### 5.2 Заявки на услуги университета

**Что это.** Цифровой сервис получения университетских услуг (справки и т. п.): каталог услуг → заполнение формы → прикрепление документов → обработка деканатом → выдача результата. Принцип: «студент приходит в деканат только за готовым результатом».

**Для кого.** Студент создаёт и отслеживает заявки; сотрудники деканата обрабатывают их в едином рабочем пространстве; староста видит групповые обращения только для чтения.

**Как работает.** Каталог настраиваемый (не enum): категория → услуга (с локализованными названием/описанием, SLA-сроком, способами выдачи) → требования (чек-лист документов) и поля формы. Студент создаёт черновик, прикрепляет документы (в т. ч. из личного хранилища «Документы») и отправляет — заявке присваивается номер `SH-YYYY-NNNNNN` и SLA-срок. Дальше — не generic-смена статуса, а бизнес-действия: сотрудник берёт в работу, назначает исполнителя, запрашивает исправления, готовит результат, выдаёт электронно или оригинал. Статусная модель: `DRAFT → SUBMITTED → IN_REVIEW → (NEEDS_CORRECTION) → IN_PREPARATION → READY/READY_FOR_PICKUP → DELIVERED/ISSUED` (терминальные REJECTED, CANCELLED). Каждый переход пишется в единый журнал (`ApplicationEvent`) — он же timeline для студента и audit для сотрудника. Права централизованы в `ApplicationPolicy`.

> **Технически:** backend `application-services`; экраны `views/appointments`-соседи, виджет `widgets/applications` (student/dean/staff/starosta вью). Отзыв — статус `CANCELLED`, не удаление.

### 5.3 Запись в деканат

**Что это.** Запись студентов на приём в деканат с очередью и подтверждением сотрудниками.

**Для кого.** Студент создаёт запись и отменяет свою; деканат (админ/модератор вуза, декан) ведёт очередь факультета.

**Как работает.** Студент выбирает тип приёма, время и тему; сотрудник подтверждает с назначением времени, переносит, завершает или отменяет.

> **Технически:** backend `appointments` (`DeaneryAppointment`); экран `views/appointments`.

### 5.4 Консультации преподавателей

**Что это.** Приёмные слоты преподавателей, на которые записываются студенты.

**Для кого.** Преподаватель/декан открывают и удаляют слоты; студент видит преподавателей с открытыми слотами и записывается.

**Как работает.** Отмена универсальна: для студента снимает его запись, для преподавателя — весь слот. Общий экран показывает преподавателю его слоты, а студенту — его записи.

> **Технически:** backend `consultations`; экран `views/consultations`.

### 5.5 Цифровой студенческий билет

**Что это.** Электронный студенческий с QR-кодом и его проверка сотрудниками.

**Для кого.** Студент/староста получает свою карту; сотрудники вуза и платформенные роли верифицируют билет по QR.

**Как работает.** Карта содержит QR-токен; сотрудник сканирует его и получает подтверждение подлинности.

> **Технически:** backend `student-id`; экраны `views/student-id` (`student-id-card`, `verify-id-view`).

## 6. Управление и модерация

### 6.1 Управление вузом (структура)

**Что это.** Администрирование организационной структуры: университеты, факультеты, специальности, группы, аудитории.

**Для кого.** Платформенный админ — университеты глобально; админ вуза — факультеты, специальности, группы, аудитории своего вуза; декан — назначение старост.

**Как работает.** Иерархия «университет → факультет → специальность → группа» задаёт границы scope для всех прав. Мутации ограничены ролью и своим вузом; удаление возможно только «снизу вверх» (нельзя удалить непустой вуз/факультет/группу). Назначение старосты меняет роль участника группы.

> **Технически:** backend `universities`, `faculties`, `specialties`, `groups`, `rooms`; экраны `views/university-admin`, `views/platform-admin`, виджеты `widgets/groups-list`, `widgets/group-members`, `widgets/users-table`.

### 6.2 Приглашения (инвайты)

**Что это.** Единственный способ регистрации в закрытой платформе — персональная ссылка-приглашение с заранее зашитой ролью и scope.

**Для кого.** Выдавать могут `PLATFORM_ADMIN`, `UNIVERSITY_ADMIN`, `DEAN`, `STAROSTA` — каждый только на роль строго ниже своей и в своём scope.

**Как работает.** Токен одноразовый, живёт 48 часов; при наличии email отправляется письмо со ссылкой. Публичный предпросмотр по токену показывает будущую роль/вуз/факультет/группу (read-only). Claim инвайта атомарен внутри транзакции регистрации — защита от двойного клика.

> **Технически:** backend `invites`; фича `features/create-invite`, форма регистрации `features/auth-invite`.

### 6.3 Модерация и жалобы

**Что это.** Жалобы на контент (посты, комментарии, сообщения, пользователей) и их разбор, плюс журнал аудита.

**Для кого.** Подавать жалобы могут студенты, старосты, преподаватели (лимит 10/час). Разбирают — модераторы и админы в пределах своего scope.

**Как работает.** По жалобе на сообщение модератору доступен контекст чата (с записью в аудит). Решение: удалить контент / заблокировать / отклонить. Все значимые действия платформы фиксируются в журнале аудита (`AuditLog`).

> **Технически:** backend `complaints` (+ `AuditModule`); экраны `views/moderation` (`complaints-queue-view`, `audit-view`).

### 6.4 Аналитика факультета

**Что это.** Сводные показатели факультета: посещаемость по группам, «требует внимания», drill-down по студентам.

**Для кого.** Платформенный/вузовский админ, модератор вуза, декан.

**Как работает.** Обзор агрегирует группы, студентов, посещаемость (доля не-пропусков, порог риска 60%), ожидающие сдачи и предстоящие экзамены. Есть детализация посещаемости по студентам конкретной группы.

> **Технически:** backend `analytics`; экраны `views/dean-analytics`, дашборд `widgets/stats-dashboard`.

## 7. Сквозные модули (пронизывают весь продукт)

### 7.1 Уведомления

**Что это.** Единый центр уведомлений: лента, счётчик непрочитанных (колокольчик), настройки каналов. Каналы: in-app, email, push.

**Как работает.** Счётчик непрочитанных кэшируется в Redis. Доставка идёт через фоновую очередь: для каждого получателя идемпотентно (по `dedupeKey`) создаётся запись; онлайн-пользователю сразу летит WebSocket-событие `notification:new`, офлайн — зеркалится в email и/или web-push по включённым тумблерам (системные уведомления доставляются всегда). Отдельной страницы «/notifications» нет — только поповер колокольчика.

> **Технически:** backend `notifications` + `push` (web-push/VAPID) + `email` (nodemailer); виджет `widgets/notifications-bell`.

### 7.2 Поиск и командная палитра

**Что это.** Глобальный кросс-модульный поиск (люди, дисциплины, задания, материалы) и командная палитра быстрых действий по Ctrl/Cmd+K.

**Как работает.** Каждый источник поиска запрашивается независимо и устойчиво; результаты ограничены scope смотрящего. Быстрые действия палитры зависят от роли пользователя.

> **Технически:** backend `search`; виджет `widgets/command-palette`.

### 7.3 Экраны «Сегодня» / «Задачи» / «Календарь»

**Что это.** Агрегирующие экраны, которые не имеют собственного бэкенда, а собирают операционную картину дня из других модулей.

**Как работает.** «Сегодня» показывает следующий/текущий блок дня по роли (студент, преподаватель, декан). «Задачи» сводят в один список всё, что требует действия (заявки, задания, события, пары). «Календарь» совмещает пары, события и дедлайны (месяц на десктопе, повестка на мобильном).

> **Технически:** экраны `views/today`, `views/tasks`, `views/calendar`; тянут `entities/schedule`, `entities/event`, `entities/assignment`, `entities/application-service`, `entities/notification`.

## 8. Техническая опора (кратко)

### Монорепо и контракт

Turborepo + pnpm. Пакеты в `packages/`:

- **`@studenthub/shared-schemas`** — **SSOT контрактов API**: Zod-схемы валидируют и запрос на бэкенде (`ZodValidationPipe`), и форму на фронте (`zodResolver`); из них же выводятся TS-типы. Контракт описан один раз — рассинхрон фронт↔бэк исключён.
- **`@studenthub/shared-types`** — роли (`Role`, `ROLE_HIERARCHY`), коды ошибок, формат ответа API.
- **`@studenthub/shared-config`** — константы, лимиты, каталоги (пагинация, TTL, rate-limit, локали `ru/kk/en`, конфиг документов).
- **`@studenthub/shared-utils`** — общие утилиты (date-хелперы, uuid).

### Аутентификация и доступ

| | Access-токен | Refresh-токен |
|---|---|---|
| Срок | 15 минут | 30 дней |
| Хранение | память клиента (Redux) — **не** localStorage | httpOnly + Secure + SameSite cookie |
| Payload | `{ sub, role, universityId, facultyId, groupId }` | UUID; в БД только bcrypt-хэш |

Три уровня guard последовательно: `JwtAuthGuard` (глобальный, снимается `@Public`) → `RolesGuard` (`@Roles`) → `ScopeGuard` (scope из JWT). Guard не заменяет проверку в сервисе — сервис дополнительно сверяет фактическую принадлежность ресурса. Роль и scope берутся **только** из токена, никогда из тела запроса. `passwordHash` и токены никогда не попадают в ответы API и логи.

### Realtime, очереди, cron

- **WebSocket (socket.io):** аутентификация JWT в handshake, рассылка только адресно по комнатам (`user:{id}`, `group:{id}`, `university:{id}`, `chat:{id}`). Обслуживает чаты, уведомления, presence, изменения расписания.
- **Очереди (BullMQ + Redis):** `email`, `notifications`, `file-processing`, `cleanup`; job'ы идемпотентны, payload — только идентификаторы.
- **Cron (`CleanupService`):** истечение инвайтов и документов, напоминания о событиях, публикация отложенных постов, чистка старых уведомлений/аудита/файлов-сирот; всё батчами по 500.

### Файлы и аудит

- **MinIO:** публичные бакеты (`avatars`, `profile-media`, `profile-covers`) — прямой URL; приватные (`posts-media`, `stories-media`, `applications`, `materials`, `chat-media`, `documents`) — только presigned-URL после проверки прав.
- **AuditLog:** фиксирует login/logout, операции с инвайтами, смену роли/статуса вуза, блокировки, решения модератора, доступ к личным чатам и приватным профилям/документам.

### Frontend (FSD)

Слои `app → views → widgets → features → entities → shared` (импорты только вниз). `app/**/page.tsx` — тонкие обёртки над `views/*`. Серверное состояние — TanStack Query (в `entities/*/api`), клиентское (auth/UI) — Redux Toolkit. Стилизация — Tailwind v4 + shadcn/ui; i18n через `next-intl` (`ru/kk/en`); realtime — единый socket.io-провайдер в `shared/realtime`.

### Технологический стек

- **Backend:** NestJS · Fastify · Prisma · Zod + nestjs-zod · Passport (JWT + local) · bcrypt · Helmet · Throttler · BullMQ + Redis · socket.io · Swagger · Terminus · MinIO · pino · nodemailer.
- **Frontend:** Next.js (App Router) · TypeScript · Tailwind v4 + shadcn/ui · Redux Toolkit · TanStack Query · react-hook-form + zod · axios · socket.io-client · chart.js · lucide-react · next-intl · next-pwa.
- **Инфраструктура:** PostgreSQL 16 · Redis 7 · MinIO · nginx (reverse proxy, TLS, WS-upgrade).
