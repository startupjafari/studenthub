# StudentHub — замер отклика на объёме вуза

Первый прогон: 2 октября 2026. Закрывает пункт «Нагрузку на реальном объёме не мерили»
из аудита готовности к запуску.

Повторять этот замер нужно перед каждым релизом, который трогает ленту, чаты или журнал, и
обязательно — после переезда инфраструктуры в РК: числа ниже сняты на машине разработчика,
и смысл имеют не сами по себе, а в сравнении между собой и с будущими прогонами.

**Троттлинг выключен намеренно.** Иначе замер упирался бы в лимитер, а не в код, и
показывал бы скорость защиты от перебора, а не скорость ленты. На проде он включён — это
значит, что цифры параллельной части ниже описывают поведение кода, а не то, сколько
запросов платформа реально пропустит.

**N+1 не найден нигде.** На запрос уходит 2–6 обращений к базе, и число не растёт с
размером страницы. Риск, названный в приложении к плану как ожидаемый, не подтвердился.

**Глубокая пагинация не деградирует**: `offset` 0, 100, 500, 1000, 2000 дают одинаковые
28–30 мс. Но это не хорошая новость, а следствие проблемы ниже: лента и так читает таблицу
целиком, поэтому глубина смещения ничего не меняет.

## Находка: лента читает таблицу постов целиком

План запроса ленты (`EXPLAIN ANALYZE`, стенд на 90 тыс. постов):

```
Limit (actual time=15.138..17.169 rows=20)
  -> Gather Merge (Workers Launched: 2)
     -> Sort (Sort Key: pinned_at DESC NULLS LAST, priority DESC, created_at DESC, id DESC)
        Sort Method: top-N heapsort
        -> Hash Left Join  (rows=13181 loops=3)
           -> Parallel Seq Scan on posts   ← вся таблица, 29 986 строк × 3 воркера
```

Чтобы отдать 20 постов, Postgres прочитывает все посты, отбирает подходящие по scope и
сортирует. Стоимость линейна по размеру таблицы: 90 тыс. постов — 17 мс в базе, миллион
будет примерно в десять раз дороже. Параллельные воркеры делают это терпимым для одного
запроса и невыносимым для двадцати: на четырёх ядрах они кончаются.

**Почему не помогает существующий индекс.** `posts_pinned_at_priority_created_at_idx`
построен по `(pinned_at, priority, created_at)` в порядке по возрастанию, а запрос сортирует
`pinned_at DESC NULLS LAST, priority DESC, created_at DESC, id DESC`. Обратный проход по
btree даёт `DESC NULLS FIRST` — порядок не совпадает, и планировщик индекс не берёт.
Вторая причина — условие видимости: большой `OR` по `audience`/`university_id`/`faculty_id`/
`group_id`/`author_id` индексами не покрывается.

**Чего это НЕ объясняет.** Счётчик комментариев Prisma собирает подзапросом
`LEFT JOIN (SELECT post_id, COUNT(*) FROM comments GROUP BY post_id)` — то есть по всей
таблице комментариев. На стенде их 309, и в плане этот узел стоит 0,1 мс; на живом вузе,
где комментариев будут сотни тысяч, он станет второй половиной проблемы. Сейчас это не
находка, а то, за чем стоит последить.

## Что с этим делать

Правки в этот прогон не входили — он отвечает на вопрос «где медленно», а не чинит. Три
направления, в порядке дешевизны:

1. **Индекс под фактический порядок сортировки** — `(pinned_at DESC NULLS LAST, priority DESC,
   created_at DESC, id DESC)`. Самое дешёвое: миграция на один `CREATE INDEX`. Снимет
   сортировку, но не seq scan — `OR` по видимости останется.
2. **Keyset-пагинация вместо `offset`** (курсор по тому же ключу). Делает стоимость
   страницы независимой от глубины и позволяет остановить чтение на первых подходящих
   строках. Ломает контракт `offset` — согласовывать с клиентами.
3. **Сузить выборку до сортировки**: вместо одного `OR` на семь веток — объединение
   нескольких узких выборок по scope (`UNION ALL` с собственными индексами), каждая из
   которых берёт свои 20 строк. Больше всего работы, больше всего эффекта.

**Порог, при котором это становится срочным.** На стенде один вуз набрал 90 тыс. постов. При
двадцати одновременных читателях лента уже отвечает за треть секунды. Если к запуску
ожидается больше десяти одновременных читателей ленты на вуз — чинить до запуска; если
меньше — после, но до второго вуза на том же инстансе.

## Находка: страница истории чата дорожала с глубиной

Базовый прогон мерил список чатов, но не саму переписку — `GET /chats/:id/messages` в
таблице выше нет. Замер 10 октября 2026 на чате из 150 тыс. сообщений (всего 300 тыс. в
таблице) показал, что страница истории стоила тем дороже, чем она глубже.

| Страница | Было | Стало |
|---|---|---|
| ~20-я | 0,19 мс · 71 буфер | 0,03 мс · 5 буферов |
| ~1200-я | 7,0 мс · 3104 буфера | 0,025 мс · 4 буфера |
| ~2900-я | 16,8 мс · 7655 буферов | 0,024 мс · 5 буферов |

**Причина — не отсутствие индекса.** Индекс `[chatId, createdAt]` на месте и берётся. Но
курсор Prisma при сортировке по времени раскладывается в
`(created_at = X AND id <= Y) OR (created_at < X)`, а такой OR планировщик границей
индекса взять не умеет и применяет **фильтром**: проход идёт от новейшего сообщения и
выбрасывает всё, что новее курсора. В плане это видно как `Rows Removed by Filter: 148500`.

**Что сделано.** История ходит по `Message.seq` — монотонному номеру внутри чата, у
которого есть уникальный индекс `[chatId, seq]`. Курсор снаружи остался id сообщения;
сервис превращает его в `seq` одним запросом по первичному ключу, и дальше `seq < X` —
обычная граница диапазона. Порядок выдачи не изменился: `seq` бекфилился как
`row_number() OVER (PARTITION BY chat_id ORDER BY created_at, id)`.

Тем же путём пошло и окно вокруг сообщения (`around`, переход по дате): `seq` уникален
внутри чата, поэтому пара «время + id» там больше не нужна.

**Заодно выяснилось, чего делать нельзя.** Сортировка `orderBy: { seq: 'desc' }` вместе с
`cursor: { id }` выглядит очевидной заменой, но Prisma в этом случае **не отправляет
`LIMIT` вовсе**: тянет все подходящие строки (149 тыс. на том же чате) и режет страницу в
памяти процесса. Это заметно хуже исходного варианта, а по коду незаметно.

## Чего этот прогон не измерял

- **Запись.** Создание постов, отправка сообщений, выставление оценок — только чтение.
- **Вебсокеты.** Чаты измерены как список диалогов по HTTP, не как живая переписка.
- **Файлы.** Загрузка и раздача вложений, в том числе прямые ссылки мимо API.
- **Сеть.** Всё на localhost: ни задержек, ни мобильного канала, ни TLS.
- **Прод-железо.** Четыре ядра на машине разработчика — не Railway. Абсолютные числа
  отсюда переносить нельзя, соотношения между экранами — можно.
