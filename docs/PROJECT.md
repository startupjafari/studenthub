## 1. Что это за продукт

Многоролевая образовательная платформа для университетов. Объединяет академическую жизнь (расписание, заявки в деканат, документы) и социальную активность (лента, чаты, события) в одном приложении.

**Ключевое архитектурное решение:** платформа полностью закрыта. Публичной регистрации не существует — попасть внутрь можно только по персональной ссылке-приглашению от вышестоящей роли. Это защита на уровне архитектуры, а не на уровне проверок.

### Четыре зоны

| Зона | Роли | Ответственность |
|---|---|---|
| Платформенная | Администратор платформы, Модератор платформы | Все университеты, пользователи, глобальная модерация |
| Университетская | Администратор университета, Модератор университета | Факультеты, группы, преподаватели, структура вуза |
| Учебная | Декан, Преподаватель, Староста | Расписание, заявки, материалы, объявления |
| Социальная | Все роли | Посты, сторисы, чаты, события, профили |

### Терминология

| Термин | Значение |
|---|---|
| **Университет** | Организация (entity), **не** роль. Управляется пользователем с ролью `UNIVERSITY_ADMIN` |
| **Scope** | Область данных пользователя: `universityId` / `facultyId` / `groupId` из JWT |
| **Инвайт** | Одноразовая ссылка регистрации с зашитой ролью и scope |
| **Аудитория (audience)** | Кому адресован контент: `ALL / UNIVERSITY / FACULTY / GROUP / SUBJECT / TEACHERS / PERSONAL` |
| **Пара** | Учебное занятие в расписании (`Pair`) |
| **Староста** | Координатор группы. Расширенные права по организации, но **не** доступ к персональным данным одногруппников |

## 2. Роли и иерархия

```
PLATFORM_ADMIN            управляет всей платформой
└── PLATFORM_MODERATOR    модерация контента всей платформы

UNIVERSITY_ADMIN          управляет своим вузом
├── UNIVERSITY_MODERATOR  модерация контента одного вуза
├── SECURITY_GUARD        охрана одного вуза: сканер QR, проверка студенческого, помещения
└── LIBRARIAN             библиотекарь одного вуза: каталог, выдача и возврат книг (Фаза 20)

DEAN                      управляет факультетом
TEACHER                   работает со своими группами
STAROSTA                  координирует свою группу
STUDENT                   базовый пользователь
```

### 2.1 Иерархия выдачи инвайтов

Выдать инвайт можно только на роль **строго ниже** своей и только в пределах своего scope.

| Роль нового пользователя | Кто выдаёт | Scope инвайта |
|---|---|---|
| `PLATFORM_ADMIN` | Seed-скрипт (единственный способ) | Глобальный |
| `PLATFORM_MODERATOR` | `PLATFORM_ADMIN` | Глобальный |
| `UNIVERSITY_ADMIN` | `PLATFORM_ADMIN` | `universityId` |
| `UNIVERSITY_MODERATOR` | `UNIVERSITY_ADMIN` | `universityId` |
| `DEAN` | `UNIVERSITY_ADMIN` | `facultyId` |
| `TEACHER` | `UNIVERSITY_ADMIN` / `DEAN` | `universityId` |
| `STAROSTA` | `DEAN` | `groupId` |
| `STUDENT` | `DEAN` / `STAROSTA` | `groupId` |
| `SECURITY_GUARD` | `UNIVERSITY_ADMIN` | `universityId` |
| `LIBRARIAN` | `UNIVERSITY_ADMIN` | `universityId` |

**Исключение: `EMPLOYER` инвайтом не выдаётся.** Работодатель регистрируется сам —
`POST /companies/signup` — потому что компания приходит извне платформы и приглашать её
некому. Это единственное отступление от правила «регистрация только по инвайтам», его
границы зафиксированы в `BACKEND_RULES §19` п. 9: компания создаётся в статусе
`PENDING_EMAIL` и до подтверждения почты вузам не видна, scope пользователя пустой,
профиль приватный, а к студентам компания получает доступ только после одобрения вузом.

**Охрана и библиотекарь — роли с запретом по умолчанию** (`RESTRICTED_ROLES` в
`@studenthub/shared-types`). Им открыт только явный список маршрутов, где роль названа в
`@RestrictedAllowed(...)`. Всё остальное `RestrictedRoleGuard` закрывает `403 FORBIDDEN` —
в том числе эндпоинты без `@Roles`, которые по общему правилу открыты любому вошедшему, а
в сервисах отдают незнакомой роли данные уровня «весь вуз» (группы, расписание, материалы,
поиск). Так закрыты и маршруты, которых ещё нет: новый эндпоинт для такой роли надо
разрешить явно. Маршрут одной ограниченной роли закрыт другой. Почему список, а не правка
сервисов: так же, как у `@MiniAllowed()` — то, что доступно, видно одним грепом.

Обеим ролям открыт аккаунт (`@RestrictedAllowed(...RESTRICTED_ROLES)`): вход и 2FA
(включая подтверждение входа на компьютере по QR), свой профиль (`/users/me`: данные,
согласие, логин, пароль, аватар, удаление аккаунта), выгрузка своих данных, уведомления,
пуши, «что нового». Охране сверх того — проверка студенческого, чтение помещений и камеры
(`@RestrictedAllowed(Role.SECURITY_GUARD)`). Библиотекарю — маршруты библиотеки, которые
добавляет Фаза 20 (`docs/IMPLEMENTATION_PLAN.md`).

Обе роли в иерархии ниже студента: это нужно только правилу «инвайт строго ниже своей
роли», выдаёт их админ вуза. 2FA обязательна, профиль по умолчанию закрыт (`PRIVATE`).
Постов, сторис, событий, чатов (включая «Сохранённые»), друзей, жалоб, заявок, карьеры и
поиска у них нет. В вебе — свой раздел (`/security`: пост и справочник помещений;
`/library`: главная библиотеки) и общие экраны по списку: охране `/scan`, `/verify-id`,
`/r/<код>`, библиотекарю `/scan`, обеим `/settings`, `/setup-2fa`, `/qr`. На остальные
адреса middleware (`isRestrictedRolePath`) возвращает на главную роли. iOS и Android эти
роли пока не поддерживают: показывают экран неподдерживаемой роли.

## 3. Модули продукта

### 3.1 Расписание
Просмотр и управление парами, аудиториями, заменами. Ролевая выборка: студент видит группу, преподаватель — свои занятия, декан — факультет. Изменения (перенос, замена аудитории, отмена) генерируют уведомление и WS-событие. Фильтры: группа, преподаватель, аудитория, предмет, дата. Особые события: экзамены, консультации, дедлайны.
Сущности: `Schedule`, `Pair`, `Room`, `ScheduleChange`.

### 3.2 Заявки в деканат (услуги университета)
Цифровой сервис получения университетских услуг (переработка модуля, идёт в ветке `feat/applications-redesign`). Студент выбирает **услугу** из каталога (категория → услуга), видит требования/срок/способ выдачи, заполняет форму, прикладывает документы (в т.ч. из личного хранилища «Документы»), отправляет; деканат обрабатывает и выдаёт результат (электронно или оригинал). Принцип: «студент приходит в деканат только за готовым результатом».

**Каталог (настраиваемый, не enum; управление — экран «Услуги» у админа вуза, см. §8.3):** `ApplicationCategory` (ACADEMIC · CERTIFICATES · FINANCIAL · MILITARY · DORMITORY · PERSONAL_DATA · TECHNICAL · OTHER) → `ApplicationService` (локализованные название/описание/инструкции, `slaHours`, `deliveryModes[ELECTRONIC|PAPER]`, `requiresPickup`, `processingMode`, `universityId` для кастома вуза) → `ServiceRequirement` (чек-лист документов, `documentType` → каталог «Документов») и `ServiceFormField` (динамическая форма). Глобальные шаблоны (`universityId=null`) видны всем вузам.

**Статусная модель** (строки; SSOT — `@studenthub/shared-schemas` `APPLICATION_TRANSITIONS`):
```
DRAFT → SUBMITTED → IN_REVIEW → NEEDS_CORRECTION → RESUBMITTED → IN_REVIEW
                            ↓
                      IN_PREPARATION → READY | READY_FOR_PICKUP → DELIVERED | ISSUED
терминальные: REJECTED, CANCELLED
```
`Application`: `number` (SH-YYYY-NNNNNN), `serviceId`, `deliveryType`, `formData(Json)`, `assignedToId`, SLA-тайминги (`submittedAt/startedAt/dueAt/readyAt/issuedAt`), pickup-поля. Каждый переход/событие пишется в `ApplicationEvent` (единый journal → человеческий timeline студенту + audit сотруднику). Права — `ApplicationPolicy` (единый источник для guard/сервиса/scope, §2.2). Отзыв — статус `CANCELLED` (не DELETE). Документы-требования и результат строятся поверх домена «Документы» (`Document`/`issuedByUniversity`).

> Старая тикет-модель (`ApplicationRequest`, статусы NEW…CLOSED, `PATCH /status`) снята с регистрации и удаляется в финальном cleanup переработки.

### 3.3 Посты и лента
Главная лента платформы. Тип поста определяется ролью автора (пост платформы / университета / факультета / преподавателя / группы / личный). Аудитория задаётся при публикации и ограничена ролью автора. Функции: текст, медиа, файлы, реакции, комментарии (thread), репост, закрепление (только роль выше автора), жалоба. Пагинация — cursor.

**Приоритет контента в ленте (сверху вниз):**
1. Срочные уведомления
2. Изменения в расписании
3. Ответы по заявкам
4. Объявления университета
5. Объявления факультета
6. Объявления группы
7. События
8. Посты преподавателей
9. Посты студентов

### 3.4 Сторисы (Ф14.1)
Короткий формат на 24 часа: фото/видео, текст на цветном фоне, ссылка, опрос и реакции.
Видимость — по аудитории (`StoryAudience`: ALL · UNIVERSITY · FACULTY · GROUP · TEACHERS);
личной и предметной аудитории у сторис нет: формат публичный, адресное сообщение одному
человеку — это чат. Кто какую аудиторию выбирает — по матрице §2.2 («Сторисы — создание»),
scope подставляет сервер из профиля автора, а не из тела запроса.

Срок жизни хранится полем `expiresAt` (24 ч, `STORY_TTL_HOURS` в shared-schemas).
Истёкшая сторис не видна никому, включая автора; строки и медиа убирает cron
`deleteExpiredStories` (каждые 30 минут), TTL-политика бакета `stories-media` страхует
объекты. Мягкого удаления у модели нет намеренно.

Просмотры хранятся по парам «сторис + зритель»: по ним рисуется кольцо «смотрел / не
смотрел» и строится список зрителей — его видит ТОЛЬКО автор (§14.7 BACKEND_RULES).
Опрос — один на сторис, 2–4 варианта, выбор одиночный, переголосовать можно пока сторис
жива. Жалоба на сторис разбирается как на пост; решение «удалить контент» сносит её
физически вместе с медиа.

В вебе раздел закрыт флагом раскатки `NEXT_PUBLIC_FEATURE_STORIES` (см. §13, открытый
вопрос 3): без него кольца над лентой и форма публикации не показываются.

### 3.5 События
Типы: университетское, факультетское, групповое, учебное, социальное, онлайн. Регистрация участников, напоминание за час, комментарии.

**Онлайн-встреча (Ф14.5).** У события есть ссылка на встречу (`meetingUrl`), код доступа
(`meetingPasscode`, Zoom выдаёт его отдельно) и провайдер (`meetingProvider`: ZOOM ·
GOOGLE_MEET · TEAMS · OTHER). Провайдер определяет СЕРВЕР по хосту ссылки — клиент его не
присылает, иначе «Zoom» в карточке означал бы лишь то, что так написал организатор.

Ссылка отделена от `location` намеренно: место проведения видит вся аудитория события, а
ссылку — только зарегистрированные участники и организатор, и отдаётся она отдельной ручкой
(`GET /events/:id/meeting`), а не полем карточки. В списках и карточке остаётся только
провайдер. Окно подключения считает сервер: открывается за 15 минут до начала и держится
30 минут после конца (у события без `endsAt` — два часа от начала).

Создания встречи через API Zoom/Google пока нет: для него нужны OAuth-приложение вуза и
хранение токенов организатора. Ссылку организатор вставляет сам.

### 3.6 Чаты
Типы: `PRIVATE`, `GROUP`, `GROUP_OFFICIAL` (чат учебной группы), `SUBJECT`, `FACULTY`, `DEAN` (чат с деканатом), `SUPPORT`, `EVENT`. Функции: текст, медиа, файлы, thread-ответы, реакции, закрепление, push, жалоба, модерация. Транспорт — socket.io, REST используется для истории и управления участниками.

**Как начинается личный чат (§50).** Вход — та же единая строка поиска над списком чатов
(Telegram-стиль): вместе с чатами и сообщениями она отдаёт секцию «Люди» из `GET /users/directory`,
клик по строке заводит переписку. Отдельного пункта «написать человеку» нет. Порядок выдачи
справочника: друзья → одногруппники → остальной вуз; в строке поиска показываются первые 8. Личный чат заводится
только внутри своего вуза; исключение — уже сложившаяся дружба (`Friendship` вуза не знает).
Роли вне вуза (платформенные) под ограничение не попадают, `EMPLOYER` справочника не получает.

Переписка с **другом** начинается сразу. Со всеми остальными — **запросом на переписку**,
и роль адресата на это не влияет: декан, староста, модератор и админ вуза получают такой же
запрос, как студент. Модель — Telegram-стиль: чат создаётся сразу, но `Chat.requestPendingForId`
хранит id адресата, который ещё не согласился. Пока он не null:
- у адресата чат виден **только** во вкладке «Запросы» — ни в «Все», ни в «Личные», ни в
  пользовательских папках, ни целью пересылки;
- уведомлений о сообщениях адресат не получает: при первом сообщении инициатора ему уходит
  одно `SYSTEM`-уведомление `chat-request` (`dedupeKey=chat-request:<chatId>`), и всё;
- инициатор может отправить не больше **5 сообщений** до принятия (`FORBIDDEN` дальше):
  без потолка непринятый запрос был бы каналом без согласия;
- пустая оболочка чата (открыли карточку, ничего не написали) адресату не показывается вовсе.

Снимается пометка тремя способами: `POST /chats/:id/request/accept`, ответное сообщение
адресата (ответ = согласие) и появление дружбы между этими двумя. `POST /chats/:id/request/decline`
удаляет чат целиком; инициатору, как и при отклонении заявки в друзья, ничего не сообщается.

### 3.7 Профили
Единый профиль с ролевыми секциями (стиль ВК). Настройки приватности (`showEmail`, `showPhone`)
определяют, какие поля видны другим; email/телефон/номера/адрес чужим не отдаются.

**Закрытый профиль (`profileVisibility`).** Поле `User.profileVisibility` (строка
`PUBLIC | UNIVERSITY | FACULTY | GROUP | PRIVATE`, дефолт по роли: сотрудники/руководство —
`PUBLIC`, студенты/старосты/модераторы — `UNIVERSITY`) задаёт, кто видит полную анкету.
`GET /users/:id` возвращает поле `access`: `full` — карточка целиком (по правам), `limited` —
только «визитка» (id, имя, аватар, роль, вуз/факультет, headline, `profileVisibility`), детали
скрыты. Надзорные роли своего scope (платформа — глобально, админ/модератор вуза — свой вуз,
декан — свой факультет) видят `full` даже при `PRIVATE`; такой доступ пишется в `AuditLog`
(`action=PROFILE_VIEW_PRIVATE`). Преподаватель (свой вуз) и староста (своя группа, только
студенты/старосты) видят `full` в пределах scope, но `PRIVATE` не пробивают. Оценки (`gpa`)
видны только владельцу и надзорным ролям — не одногруппникам/старосте.
Поля `User`: общие (middleName, phone, bio, birthDate, gender, languages, telegram, website,
headline, timezone, locale), студент/староста (course, enrollmentYear, graduationYear, educationLevel,
studyForm, fundingType, specialty, studentCardNumber, academicStatus, gpa, interests, skills,
dormitory, address, starostaSince, duties), сотрудники (position, jobTitle, academicDegree,
academicTitle, department, subjects, officeRoom, officeHours, employeeNumber, researchInterests,
publicationsUrl, appointmentDate, workPhone, responsibilities, moderationAreas). Редактирование —
`PATCH /users/me` (роль/scope не меняются); форма показывает поля релевантные роли.

**Язык пользователя** (`User.locale` = `ru|kk|en`, по умолчанию `ru`; SSOT —
`SUPPORTED_LOCALES` в `@studenthub/shared-config`). Хранится в профиле, а не только в
cookie `NEXT_LOCALE`: письма и push уходят с сервера в момент, когда открытой вкладки нет,
и cookie браузера им недоступна. Cookie при этом остаётся — её читает next-intl при
серверном рендере; при входе она приводится к профилю (профиль принадлежит человеку,
cookie — браузеру). Наружу `locale` уходит только в собственном профиле (`/users/me`,
`/auth/me`): чужая настройка языка другим пользователям ничего не говорит и в публичной
карточке была бы лишним персональным полем.

**Доступность полей профиля по роли.** Набор «самоописываемых» полей зависит от роли —
единый источник `PROFILE_FIELD_ROLES` в `@studenthub/shared-schemas` (одна карта на форму
и на валидацию). Общие поля (ФИО, headline, bio, phone, telegram, languages, timezone, locale,
showEmail/showPhone, profileVisibility) — у всех ролей; личное и соцсети (birthDate, gender,
country, website, instagram) — студенты и преподаватели; академические (academicDegree,
academicTitle, department, subjects, officeHours, researchInterests, publicationsUrl) —
только TEACHER и DEAN; вузовские служебные (employeeNumber, appointmentDate, officeRoom,
jobTitle) — сотрудники вуза; position и workPhone — все не-студенты; responsibilities —
администраторы и модераторы вуза и платформы; moderationAreas — только модераторы;
duties — только STAROSTA. Платформенные роли вне вуза, поэтому кафедры, предметов
и табельного номера у них нет.

`PATCH /users/me` с полем, недоступным роли, отвечает `400 BAD_REQUEST`; `details[]`
перечисляет отклонённые поля (`field` + сообщение). Запрос отклоняется целиком, разрешённая
часть тоже не сохраняется. Роль читается из JWT, не из тела.

**Учебные данные ведёт вуз.** Поля `course`, `enrollmentYear`, `graduationYear`,
`educationLevel`, `studyForm`, `fundingType`, `specialty`, `studentCardNumber`, `academicStatus`,
`gpa` студент видит в своём профиле, но не меняет: `PATCH /users/me` с ними — тот же `400`
(список — `STAFF_MANAGED_STUDENT_FIELDS`, проверка — `profileFieldSelfEditable`). Из них
печатаются справка об обучении и цифровой студенческий, и самозаполнение давало подписанную
справку с «грантом» и «обучающимся», которых вуз не подтверждал. Правит их
`PATCH /users/:id/academic` (DEAN — студенты своего факультета, UNIVERSITY_ADMIN — своего вуза;
цель — только STUDENT/STAROSTA, иначе `400`; вне области — `403 WRONG_SCOPE`; тело —
`UpdateAcademicRecordSchema`, строгое). Каждая правка пишется в аудит `user_academic_updated`
со списком полей. В вебе — кнопка «Учебные данные» в таблице студентов; уходят только
изменённые поля, потому что `studentCardNumber` в чужую карточку не приходит.
`specialty` принимается только из справочника специальностей вуза, если он заведён, иначе
`422 VALIDATION_ERROR` (`field=specialty`); `PATCH /specialties/:id` переименовывает `specialty`
и у студентов вуза. Общежитие тоже ведёт вуз: `PATCH /users/:id/academic` принимает `dormitory`,
а в `PATCH /users/me` от студента или старосты `dormitory` молча игнорируется.

**Чужая карточка: что видно.** `birthDate`, `fundingType`, `academicStatus` и `dormitory`
в `GET /users/:id` приходят только тем, кто ведёт учёт студента (владелец, сотрудники вуза
по области, платформенные роли); остальным — `null`. Проверка студенческого
(`student-id/verify`) старосте, преподавателю и охране отдаёт карточку без даты рождения,
формы оплаты и общежития: им для проверки достаточно личности и статуса. Ответ проверки
содержит `selfDeclared: string[]` — поля, указанные самим студентом, а не вузом (сейчас
`birthDate`, если показана).

**Контент профиля (вкладки).** Профиль разбит на вкладки: Профиль / Фото / Видео / Статьи /
Опросы. Просмотр — любой аутентифицированный с учётом `visibility` (ALL/UNIVERSITY/FACULTY/GROUP);
черновики (`status=DRAFT`) видит только автор; загрузка/редактирование — только владелец.
Модели: `ProfileArticle` (title, description, content markdown, coverUrl/coverGradient, category,
tags[], visibility, allowComments, status, readingMinutes — считается на бэке), `Poll` + `PollOption`
+ `PollVote` (question, options, multiple, anonymous, allowRevote, resultsVisibility, visibility,
closesAt, status). Фото/видео — `File` в публичном бакете `profile-media`; обложки статей — `profile-covers`.

Эндпоинты (`ProfileContentController`, база `/profile`):
- `POST /profile/media` (multipart, ≤ порога) и `POST /profile/media/presign` → `POST /profile/media/confirm`
  (крупные видео, прямой presigned-PUT в MinIO); `GET /profile/:userId/media`; `DELETE /profile/media/:fileId`.
  Квота на пользователя — `PROFILE_MEDIA_QUOTA` (300 файлов, 2 ГБ): превышение на `POST /profile/media`,
  `/media/presign` и `/media/confirm` → `409 CONFLICT`, `details[0].field = profileMediaQuota`,
  `message` = `files|bytes`. Новая обложка видео заменяет прежнюю только после записи.
- `POST|GET(:userId)|PATCH|DELETE /profile/articles[...]`; `POST /profile/articles/cover` (обложка → URL).
  `GET /profile/:userId/articles?view=card` — карточки без `content`; `GET /profile/articles/:id` —
  статья целиком; `POST /profile/articles/:id/view` — один просмотр на зрителя в сутки.
- `GET /profile/:userId/counts` → `{ photos, videos, articles, polls }`.

Статьи и опросы подчиняются видимости профиля автора, как медиа и альбомы: при закрытом профиле
списки пустые, по id — `404`; `GET /profile/bookmarks` отдаёт только видимое сейчас.

Опросы (`PollsController`, база `/polls`): `POST /polls`, `GET /polls/by-user/:userId?limit&cursor`, `GET /polls/:id`
(с результатами по правам смотрящего), `POST|DELETE /polls/:id/vote` (голос/отмена), `PATCH /polls/:id`
(до появления голосов), `DELETE /polls/:id`. Результаты гейтятся `resultsVisibility` (AFTER_VOTE /
AFTER_END / HIDDEN); один голос на пользователя (`@@unique([optionId,userId])`), несколько — при `multiple`.
Голос и его отмена берут разделяемый лок опроса, `PATCH` — исключительный.

Мутации проверяют владение (`actor.sub`), просмотр — по `visibility`/scope. Медиа фильтруются по MIME
(image/video); presigned-confirm валидирует объект через `statObject` и лимит 100 МБ.

**Модерация контента профиля.** `DELETE /profile/media/:fileId`, `/profile/articles/:id`,
`/profile/articles/:id/comments/:commentId`, `/polls/:id`, `/polls/:id/comments/:commentId`: чужое
удаляет модератор по правилам постов — платформа везде, админ и модератор вуза — у авторов своего
вуза, декан — своего факультета, и только при роли строго выше автора. Для комментария scope —
автор комментария или владелец статьи/опроса. В аудит пишется `profile_media_deleted` /
`profile_article_deleted` / `poll_deleted` / `content_comment_deleted`.
(Прежняя модель `ProfileQa` удалена миграцией `articles_polls` — заменена опросами.)

**Присутствие.** `GET /users/:id/presence` → `{ online }` (снапшот по активным WS-соединениям,
`RealtimeGateway`). Настоящий статус видят свой вуз, друзья и платформенные роли; остальным
всегда `{ online: false }` — иначе любой аккаунт мог бы по id следить, когда человек в сети.
Живые изменения — WS-событие `presence:changed { userId, online }`; получают его не все в вузе, а
собеседники личных чатов (в `user:{id}`) и участники общих чатов (в `chat:{id}`). Снимок —
`GET /chats/:id/presence` и `GET /users/:id/presence`.
Аватар профиля показывает статус в сети/не в сети (свой профиль — всегда в сети).

### 3.8 Документы (Ф15)

Защищённое личное хранилище документов + запросы вуза. Отдельный раздел `/documents`
(под-навигация: Обзор, Мои документы, Запросы университета, Документы от университета,
Управление доступом, Архив).

**Приватность номера.** Полный `Document.number` наружу НЕ отдаётся (как `passwordHash`) —
API возвращает только маску `******4821` (`numberMasked`) из `numberLast4`. Файлы — в приватном
бакете MinIO `documents`, доступны только через presigned-URL после проверки владения/гранта.

**Модели.** `Document` (owner, category, type, title, number/numberLast4, issuedAt/expiresAt,
status `DRAFT|UPLOADED|IN_REVIEW|VERIFIED|ACCEPTED|REJECTED|NEEDS_REPLACEMENT|EXPIRING|EXPIRED|ARCHIVED`),
`DocumentAccess` (грант: `UNIVERSITY|DEPARTMENT|USER`, причина, срок, отзыв), `DocumentEvent`
(журнал: UPLOAD/VIEW/DOWNLOAD/EDIT/GRANT/REVOKE/EXPIRE/ARCHIVE/…). Запросы вуза: `DocumentRequest`
(+`Item`/`Target` — адресат `UNIVERSITY|FACULTY|GROUP|USER`), `DocumentSubmission` (+`Item` —
привязка документа студента к позиции, вердикт `PENDING|ACCEPTED|REJECTED`). Типы: гибридный каталог —
статические 25 типов в `@studenthub/shared-config` + правки вуза в `DocumentType`
(вкл/выкл, `retentionDays`, custom-типы).

**Ролевая матрица (§15.2).** Создают/проверяют запросы деканат/студ.офис (`DEAN`,
`UNIVERSITY_MODERATOR`) и преподаватель (только учебные типы); админ вуза управляет типами/сроками
(не участвует в запросах); студент/староста — отвечают. Сотрудник видит только СВОИ запросы.
Адресаты — в области автора, иначе `403 WRONG_SCOPE`: весь вуз (`UNIVERSITY`) — только
`UNIVERSITY_MODERATOR`; декан — свой факультет, его группы и студентов; преподаватель — группы
своих дисциплин (`Course.teacherId`) и их студентов, факультет и вуз ему недоступны.
Гранты на документ `DEPARTMENT` и `UNIVERSITY` — доступ администрации: `DEPARTMENT` действует
для декана этого факультета, `UNIVERSITY` — для админа, модератора вуза и декана. Студентов и
преподавателей вуза такой грант не пускает: им документ открывают персональным грантом `USER`.
Платформенный админ обычного доступа к содержимому не имеет — только спец-режим с обязательной
причиной (пишется в `AuditLog` + `DocumentEvent`).

Область сотрудника в запросах: модератор вуза — весь вуз; декан — свой факультет, кроме
запросов преподавателей; преподаватель — свои запросы. Студенческие ручки запросов (комплект,
отправка) — только `STUDENT`/`STAROSTA`.

**Правила документа.** Документ `ISSUED_BY_UNIVERSITY` появляется только через вуз (выдача по
заявке): `POST /documents` с этой категорией → `403`. Владелец выданного документа меняет лишь
`comment`. Правка содержимого снимает `VERIFIED`. `unarchive` восстанавливает статус, бывший до
архивации (`previousStatus`). Удалённый документ не открывается ни по заявке, ни по запросу; его
сканы физически удаляются через 30 дней (`cleanDetachedFiles`).

**Комплект по запросу.** Студент сохраняет и отправляет комплект только в `DRAFT`/`REJECTED`/
`PARTIAL`; `SUBMITTED`/`ACCEPTED`, закрытый запрос или истёкший `dueAt` → `409`. `dueAt` без
времени действует до конца дня. Правка возвращённого комплекта переводит его в `DRAFT`, вердикты
нетронутых позиций сохраняются. `review`/`finalize` — только из `SUBMITTED`/`PARTIAL`.
`GET /document-requests(/:id)` отдают `acceptsSubmissions`. Принятая позиция `CERTIFICATE` своего
типа переводит документ студента в `VERIFIED`. `GET manage/:id` отдаёт первые 200 комплектов и
`submissionCount`, остальные — `GET manage/:id/submissions?cursor&limit≤50`; `POST manage/:id/close`
идемпотентен.

**Автоматизация.** Cron `sweepDocumentExpiry` (ежедневно): `expiresAt` → `EXPIRING`/`EXPIRED`,
затем архив по сроку хранения — по типам с `retentionDays`, пачками до исчерпания. Cron
`closeOverdueDocumentRequests` (03:35) закрывает запросы с прошедшим сроком. Уведомления BullMQ
(`SYSTEM`): новый запрос → адресатам (пачками по 1000), результат проверки → студенту, истечение →
владельцу, отправленный комплект → автору запроса (`document-submitted`), грант → получателю
(`document-shared`, §10.1).

**Эндпоинты** (база `/documents`, `/document-requests`, `/document-types`): CRUD документов,
`/upload`+`/files`(+`/order`), `GET :id/files/:fileId/url` (presigned), `access` (grant/revoke),
`overview`, `events`; `GET /documents/shared-with-me?cursor&limit≤50` — активные гранты на меня
(`USER`), мой факультет (`DEPARTMENT`, декану), мой вуз (`UNIVERSITY`, администрации), без своих
документов; запросы — создание/список/`manage`, submission (save/submit), review
(`submission-items/:id/review`, `submissions/:id/finalize`); типы — `GET /document-types/effective`
(каталог типов своего вуза для выбора, все роли; вуз из токена, у ролей без вуза — статический
каталог; ответ как у `GET /document-types`, выключенные типы приходят с `enabled=false`, у
собственных — `label`), управление `GET|POST /document-types`, `PATCH|DELETE /document-types/:typeId`
— только `UNIVERSITY_ADMIN`; спец-режим — `POST :id/platform` (`{ reason }` 5–500 символов;
`GET :id/platform` устарел), `POST :id/platform-access` (платформенный админ;
тело `{ fileIds: string[] (1..50), reason }` → `{ urls: Record<fileId, url> }` — файлы берутся
пачкой, одно обращение = одна запись `DOCUMENT_PLATFORM_DOWNLOAD` с `metadata.fileIds`).

### 3.9 Помещения и QR над дверью (Ф16)

Над каждым помещением вуза висит печатная наклейка с QR. Студент наводит камеру телефона
(без установки приложения) и попадает на страницу `/r/<код>`, где видит:

- **учебные помещения** (аудитория, лаборатория, спортзал) — «Свободно» или «Занято до 12:30»,
  идущую пару с предметом, **группой** и преподавателем, следующую пару и остаток дня;
- **неучебные** (библиотека, актовый зал, деканат, бухгалтерия, столовая, общежитие) — часы
  работы, телефон и примечание. Часы работы печатаются и на самой наклейке: у двери
  бухгалтерии это нужнее возможности отсканировать.

Занятость считается из расписания с наложением разовых изменений (`ScheduleChange`): отменённая
пара освобождает помещение, перенос в другую аудиторию убирает занятость отсюда, перенос сюда —
добавляет. Чётность недели и «сейчас» — те же правила, что в сетке расписания и на экране
«Сегодня» (общий `buildDayPairs` в `entities/schedule`), иначе экраны расходились бы в показаниях.
«Сейчас» приходит с сервера в таймзоне вуза: часы на телефоне студента могут врать.

**Доступ.** Страница закрыта авторизацией — расписание группы это внутренние данные вуза (§1),
а наклейка висит в открытом коридоре. Незалогиненного ведём на `/login?next=/r/<код>` и после
входа возвращаем на помещение. Неизвестный код и помещение чужого вуза дают ОДИНАКОВЫЙ `NOT_FOUND`:
иначе код становится оракулом для перебора.

**Код.** Короткий (8 символов, алфавит без похожих `0/O`, `1/I/L`) и отдельный от `id` помещения:
QR получается менее плотным (сканируется с большего расстояния) и код можно перевыпустить, обесценив
утёкшую или устаревшую распечатку. Печатается на наклейке текстом как запасной путь. Выдаёт
администратор вуза — по одному помещению или пачкой на корпус/этаж (`/university-admin/rooms`).

### 3.10 Камеры вуза

Просмотр камер наблюдения вуза в реальном времени — только **охране** (`SECURITY_GUARD`) и
**администратору вуза**, каждому свой вуз. Платформа видео не видит. Видео нигде не
записывается и не хранится, звук не передаётся, распознавания лиц нет.

**Как устроено.** В сети вуза работает **агент** — программа, которая сама ходит наружу, к
платформе: входящих портов в сети вуза не открывают, камеры в интернет не смотрят. Агент
забирает поток с камеры (обычно второй, лёгкий) и отдаёт его наружу только пока его
кто-то смотрит. Видео идёт через медиа-ретранслятор платформы в браузер по LL-HLS
(задержка 2–4 с) по короткоживущему токену.

**Данные** (`prisma/schema/33-cameras.prisma`): `CameraAgent` — агент вуза; в базе только
SHA-256 его токена (сам токен показывается админу один раз) и открытый ключ X25519, который
агент присылает о себе. `Camera` — камера за агентом: адрес потока в сети вуза **без
логина и пароля** (схема их в адресе не принимает), помещение, состояние по отчёту агента.
Логин и пароль камеры шифруются **открытым ключом агента** (`common/crypto/sealed-box`:
X25519 → HKDF-SHA256 → AES-256-GCM, id камеры в AAD) и лежат конвертом, который платформа
вскрыть не может — закрытый ключ есть только у агента. Поэтому пароль принимается лишь для
агента, уже приславшего ключ (`409 CONFLICT`, `details.field=agentId`). Перевыпуск токена
агента сбрасывает его ключ и конверты паролей: агент на новом месте их не вскроет.
`CameraSettings` — выключатель модуля на вуз; **по умолчанию выключен**, выключение
обрывает все просмотры разом.

**Агент** (`apps/camera-agent`, Docker-образ на Node 24 с ffprobe, без npm-зависимостей во
время работы). Держит с платформой длинный опрос `POST /camera-agent/sync`: присылает версию,
открытый ключ и состояние камер, получает конфигурацию — свои включённые камеры с адресами и
конвертами паролей. Ревизия конфигурации — хэш её содержимого; совпала с той, что у агента,
— ответ ждёт изменений до 25 с. Сервисы камер при любом изменении поднимают счётчик в Redis
(`camera-agent:rev:<id>`), ожидание сверяет его раз в секунду, поэтому новая камера или
выключатель доходят до агента за секунду. Ключ агента платформа принимает один раз; другой
при известном — `409` (`details.field=publicKey`), выход — перевыпуск токена. Закрытый ключ
агент хранит в томе (`/var/lib/studenthub-agent`, права 600), пароли — только в памяти;
камеры проверяет `ffprobe` раз в минуту: `ONLINE`, `OFFLINE`, `AUTH_FAILED` (401 от камеры).
Установка в вузе — `apps/camera-agent/README.md`, проверка на эмуляторе — `docker/camera-sim`.

**Просмотр** (`docker/media-relay`, сервис Railway). «Начать просмотр» создаёт сессию —
она же запись журнала (`CameraViewSession`: камера и ФИО на момент просмотра, IP,
начало, последнее подтверждение, конец; связи с камерой и человеком обнуляются при
удалении, запись остаётся) — отмечает спрос на поток (`camera:demand:<id>` в Redis, TTL
60 с) и будит агента. Агент получает в синхронизации адрес и токен публикации и отдаёт
поток ffmpeg'ом: без перекодирования, без звука, по **RTMPS** с закреплённым сертификатом
ретранслятора (`MEDIA_RELAY_CA_PEM`). RTSPS не годится: MediaMTX в режиме JWT не шлёт
вызов, и ffmpeg не отдаёт токен. Браузер берёт LL-HLS у ретранслятора с токеном в
`Authorization: Bearer`. Токены — JWT ES256 от API (`MEDIA_JWT_PRIVATE_KEY`): зрителю на
2 минуты, агенту на 10, права только на путь `cam/<id>`; ретранслятор проверяет их сам по
`GET /.well-known/media-jwks.json`. Плеер продлевает просмотр каждые 30 с. Последний
зритель закончил — спрос снимается, поток гаснет за секунду; закрыли вкладку — спрос
истекает, поток гаснет за ~1,5 минуты. Выключатель модуля гасит потоки мгновенно, а
продления получают `409`. Не больше 4 одновременных просмотров на человека.

Экран администратора — `/university-admin/cameras`: выключатель, агенты, камеры.

### 3.11 Библиотека (Фаза 20)

Бумажный формуляр библиотеки вуза в платформе: кто взял какой экземпляр и до какого срока,
кто должник, что можно забронировать. План и решения владельца — `docs/IMPLEMENTATION_PLAN.md`,
Фаза 20.

**Кто что делает.** Книги берут студенты и старосты своего вуза — у обоих есть цифровой
студенческий. Выдаёт и принимает книги только библиотекарь (`LIBRARIAN`), у каждой выдачи
один ответственный. Админ вуза включает модуль, задаёт правила выдачи и видит отчёты, но
книг не выдаёт.

**Выключатель и правила** (`LibrarySettings`, одна запись на вуз). По умолчанию модуль
**выключен**: нет записи — выключен, вуз включает библиотеку сам. Выключенный модуль закрывает
выдачу, возврат и брони `409` (`details.field = module`); каталог и история остаются. Правила по
умолчанию: срок выдачи 14 дней, максимум 120 (учебник на семестр), 5 книг на руках, 3 активные
брони, готовая бронь держится 3 дня, 1 продление. Срок по умолчанию не может быть больше
максимального (`422`, `field = defaultLoanDays`).

**Каталог и экземпляры.** Книга (`Book`) — карточка каталога; на полке стоят экземпляры
(`BookCopy`) с инвентарным номером (уникален в вузе) и коротким кодом QR-наклейки — отдельной
величиной, не `id` (BACKEND_RULES §13.2): наклейку можно перевыпустить. QR ведёт на
`/c/<код>`: библиотекаря — к книге в фонде, студента — к книге в каталоге. Книгу с историей
выдач не удаляют, а убирают в архив. Фонд заводится руками или импортом CSV/XLSX.

**Выдача.** Библиотекарь сканирует цифровой студенческий читателя: QR разовый и живёт две
минуты, поэтому сервер выдаёт пропуск на 15 минут — по нему можно выдать несколько книг
подряд. Книги не выдаются отчисленному, выпущенному или переведённому студенту, должнику (есть
просроченная книга) и тому, у кого на руках предельное число книг. Срок — до конца выбранного
дня по часам вуза. Читатель получает уведомление и может нажать «это не я» — выдача остаётся,
но библиотекари видят отметку.

**Возврат и удостоверение.** Книгу принимают сканом наклейки; если на неё есть очередь броней,
экземпляр сразу откладывается под первую, и экран говорит, на чьё имя. Выдачу и возврат не
правят задним числом — только отменяют с причиной в аудите. Ошибочный возврат отменяют в течение
суток, пока экземпляр на полке и никому с тех пор не выдан: выдача снова открыта с прежним
сроком. Пока книга на руках, библиотекарь
может открыть удостоверение читателя (узкая карточка, как у охраны); каждый просмотр пишется в
журнал, который видит и админ вуза, а после возврата карточка закрыта.

**Сроки.** Читателю приходят напоминания за два дня до срока, в последний день и о просрочке —
днём по часам вуза. Пока просроченная книга не вернётся, новые выдачи и брони ему закрыты.

**Студенту.** Раздел «Библиотека» (`/books` — каталог с наличием, `/books/:id` — книга и бронь,
`/my-books` — книги на руках со сроками и «это не я», брони с местом в очереди, история)
появляется в меню студента и старосты, только когда вуз включил библиотеку. Свободный
экземпляр бронируется сразу и ждёт на полке броней `reservationHoldDays` дней; если все на
руках — читатель встаёт в очередь, и возвращённая книга достаётся первому.

**Выпуск и отчисление.** Когда декан или админ вуза переводит студента в «выпускник»,
«отчислен» или «переведён», форма учебных данных показывает книги, которые за ним числятся.
Смену статуса это не блокирует — книги нужно вернуть до выхода. Студент сам печатает справку
«задолженностей в библиотеке нет» (`/my-books/clearance`), пока на руках ничего нет.

**Отчёты и инвентаризация.** Библиотекарь и админ вуза видят сводку фонда, выдач, должников и
броней, популярное за 30/90/365 дней и историю каждого экземпляра. Инвентаризация — скан
наклеек вдоль полок: отмеченный экземпляр «на месте», отчёт с даты начала показывает, что из
положенного на полке не нашли; странный статус (выдан, утерян, списан) скан не меняет, а
показывает.

## 7. Аутентификация

### 7.1 Токены

| | Access | Refresh |
|---|---|---|
| Срок | 15 минут | 30 дней |
| Хранение | Redux (память клиента) | httpOnly + Secure + SameSite cookie |
| Payload | `{ sub, role, universityId, facultyId, groupId, companyId, tfa, client? }` | UUID; в БД только SHA-256-хэш секрета (выданные до перехода bcrypt-записи доживают свой срок) |
| Ротация | — | Новый при каждом refresh, предыдущий инвалидируется |

Состав payload — `JwtPayload` (`common/auth/jwt-payload.type.ts`): `companyId` — компания работодателя
(у остальных ролей `null`), `tfa` — включена ли 2FA на момент выдачи (§8.3 «Форс 2FA»), `client: 'mini'` —
токен админского мини-аппа (у обычного входа поля нет). В `request.user` попадают только поля из белого
списка `JwtStrategy.validate` (`modules/auth/strategies/jwt.strategy.ts`): **новое поле токена нужно
добавить и туда**, иначе оно молча теряется — так однажды пропал `companyId`.

### 7.2 Жизненный цикл

```
1. Логин / регистрация по инвайту
   → access_token в JSON body → Redux
   → refresh_token в httpOnly cookie

2. Каждый запрос: Authorization: Bearer <access>
   → 401 + code=TOKEN_EXPIRED → POST /auth/refresh (cookie отправляется браузером)
   → то же для 401 + code=UNAUTHORIZED, если запрос ушёл БЕЗ Bearer (холодная
     загрузка страницы: токен ещё не восстановлен) — FRONTEND_RULES §5.3
   → новый access → прозрачный повтор исходного запроса (один раз)
   → refresh отклонён (истёк, погашен реюз-детектором, подделан) → 401 И гашение
     обеих cookie, включая нечувствительную sh_role: иначе она переживает мёртвую
     сессию и middleware разворачивает пользователя с /login обратно в приложение,
     где refresh падает снова — бесконечный редирект
   → повтор только что ротированного токена при живой цепочке → новая ротация, а не
     разрыв: ответ мог не доехать до клиента (окно REFRESH_REUSE_GRACE_MS,
     BACKEND_RULES §6.2)
   → 429 на refresh — не отказ сессии: клиент повторяет с выдержкой; на /login ведут
     только 401/403
   → вуз заблокирован платформой → 403 UNIVERSITY_BLOCKED на вход, refresh, регистрацию
     по инвайту и запросы с уже выданным токеном (до 15 с на других инстансах);
     платформенные роли не затронуты

3. Logout
   → POST /auth/logout → хэш refresh инвалидируется, cookie очищается
   → clearAuth() + queryClient.clear() + disconnect(socket) → /login

3a. Забыли пароль
   → /forgot-password: POST /auth/password/forgot { email } → 202 для любого адреса
     (нет перебора); письмо со ссылкой ${WEB}/reset-password?token=… уходит, только если
     учётная запись есть и не заблокирована. Новая просьба гасит прежние ссылки
   → /reset-password: POST /auth/password/reset { token, password } → 204; токен
     одноразовый, живёт час, в БД — только SHA-256 (PasswordResetToken)
   → все сессии гаснут, блокировка входа по подбору снимается; сессию сброс не выдаёт —
     вход заново, с 2FA, если она включена

4. WebSocket
   → handshake { auth: { token: accessToken } } → JwtWsGuard → client.data.user
   → авто-вход в комнаты user:{id}, group:{id}, university:{id}
   → токен мини-аппа (client:'mini') не пускается: handshake и auth:refresh его отклоняют;
     auth:refresh токеном другого пользователя рвёт соединение
```

### 7.3 Поток регистрации по инвайту

```
1. Администратор: POST /invites  → токен, роль, scope, expiresAt = now + 48ч, статус PENDING
2. Очередь email: письмо со ссылкой https://app/register?token=UUID
3. Пользователь открывает: GET /invites/:token/preview
   → { role, emailRequired, universityId, facultyId, groupId, expiresAt }
   → истёк / использован / отозван → страница ошибки с конкретным кодом
4. Форма: имя, username, пароль, фото (+ email, если emailRequired). Роль и scope — read-only
5. POST /auth/register-by-invite  → транзакция: создать User + Invite.status = USED
6. Редирект на ROLE_HOME[role]
```

**Инвайт без email.** `email` у инвайта необязателен: приглашение выдают и ссылкой (мессенджер,
распечатка), а письмо тогда не отправляется. Адрес в этом случае приходит из формы регистрации,
поэтому превью отдаёт признак `emailRequired = !invite.email`, а форма по нему показывает
обязательное поле. Сам адрес превью не раскрывает никогда: ручка публична по токену, а ссылку
могли переслать кому угодно. Без email не создаётся ни один пользователь — он логин и адрес
восстановления пароля (`BAD_REQUEST`, если адреса нет ни в инвайте, ни в теле запроса).

Защита: срок 48 ч (cron помечает `EXPIRED` раз в час; истечение пишется в `AuditLog` как `invites_expired`, одна запись на пачку), одноразовость (проверка внутри транзакции), отзыв через `PATCH /invites/:id/revoke` (только из `PENDING`, иначе `409`), throttling 10 попыток/час на токен инвайта + потолок 100/час с IP (§7.4), полный аудит. Инвайт преподавателя от декана — только на свой факультет (`WRONG_SCOPE`).

Email при регистрации сохраняется в нижнем регистре; адрес, занятый в другом регистре, → `CONFLICT`. Регистрация по инвайту `STAROSTA` делает пользователя старостой группы (`Group.starostaId`): прежние старосты становятся `STUDENT`, им гасятся сессии, в аудит пишется `user_role_changed` от имени выдавшего инвайт. Удаление вуза, факультета или группы переводит их `PENDING`-инвайты в `REVOKED` той же транзакцией; превью и регистрация по инвайту с удалённым вузом/факультетом/группой → `INVITE_REVOKED`.

**Массовый импорт (CSV/XLSX).** Для онбординга многих студентов сразу — двухшаговый поток:
`POST /invites/bulk/preview` (multipart-файл) парсит CSV/XLSX (обязательна только колонка `email`; `role` — по умолчанию STUDENT; `group` — имя группы, обязательна для STUDENT/STAROSTA; `faculty` — имя факультета, обязательна для DEAN и необязательна для TEACHER — так админ вуза заводит преподавателей и деканов одним файлом), разрешает имена группы и факультета в id в scope создателя и валидирует каждую строку БЕЗ записи → `{ rows: [{ line, email, groupName, facultyName, role, groupId, facultyId, status: READY|DUPLICATE|ERROR, error }], summary }`. Затем `POST /invites/bulk` (`rows: [{ email, groupId?, facultyId?, role? }]`) создаёт инвайты по подтверждённым строкам (сервер повторно проверяет, что группа и факультет в scope создателя, валидирует иерархию через тот же `resolveInviteTarget`, пропускает дубли) → `{ created, skipped, failed }`. Обе ручки — те же роли, что и одиночный инвайт (PLATFORM_ADMIN/UNIVERSITY_ADMIN/DEAN/STAROSTA); лимит 500 строк за импорт.

### 7.4 Rate limiting

`POST /auth/login` — 5 / 15 мин на пару «IP + логин» (без учёта регистра) + потолок 50 / 15 мин с IP, поверх — `LOGIN_LOCKED` · `POST /auth/login/2fa` — 5 / 15 мин на «IP + владелец challenge» + 50 / 15 мин с IP · `POST /auth/register-by-invite` — 10 / час на токен инвайта + 100 / час с IP · `POST /auth/refresh` — 10 / мин на id refresh-токена + 1000 / мин с IP · `POST /auth/password/forgot` — 3 / 15 мин с IP · `POST /auth/password/reset` — 5 / 15 мин с IP · `GET /invites/:token/preview` — 30 / час на токен + 200 / час с IP · `POST /complaints` — 10 / час с пользователя · прочее — 100 / мин с пользователя (без валидного токена — с IP).

Публичные auth-маршруты помечаются `@AuthThrottle(key, own, ipCeiling)`: IP кампуса за NAT общий, поэтому ключ — токен или логин, а IP — только мягкий потолок; без ключа считается только потолок.

## 8. Контракт API

Префикс: `/api/v1`. Аутентификация: `Authorization: Bearer <access_token>`, если не указано «публичный».

### 8.1 Формат ответа

```jsonc
// Успех
{ "success": true, "data": { }, "meta": { "total": 100, "cursor": "uuid", "hasNext": true } }

// Успех без данных (DELETE, logout)
{ "success": true, "data": null }

// Ошибка
{
  "success": false,
  "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [ { "field": "email", "message": "..." } ] },
  "statusCode": 422,
  "timestamp": "2026-01-15T10:30:00.000Z",
  "path": "/api/v1/auth/login"
}
```

### 8.2 Коды ошибок

| HTTP | code | Ситуация |
|---|---|---|
| 400 | `BAD_REQUEST` | Некорректный запрос |
| 401 | `UNAUTHORIZED` | Токен отсутствует или невалиден |
| 401 | `TOKEN_EXPIRED` | Access истёк → клиент делает refresh |
| 403 | `FORBIDDEN` | Недостаточно прав по роли |
| 403 | `WRONG_SCOPE` | Ресурс другого университета/факультета/группы |
| 404 | `NOT_FOUND` | Ресурс не найден |
| 409 | `CONFLICT` | Нарушение уникальности |
| 410 | `INVITE_EXPIRED` · `INVITE_USED` · `INVITE_REVOKED` | Состояние инвайта |
| 413 | `FILE_TOO_LARGE` | Размер файла больше лимита категории |
| 413 | `FILE_DIRECT_UPLOAD_REQUIRED` | Файл больше порога буферной загрузки — нужен presigned-upload в MinIO |
| 415 | `FILE_TYPE_NOT_ALLOWED` | Тип файла (по magic bytes) не в белом списке |
| 422 | `VALIDATION_ERROR` | Ошибка Zod, с `details[]` |
| 429 | `RATE_LIMIT` | Превышен лимит |
| 429 | `LOGIN_LOCKED` | Слишком много неудачных попыток входа в **эту учётную запись** — вход по ней временно закрыт, в том числе с верным паролем. Отдельно от `RATE_LIMIT`: тот про частоту запросов с адреса. Порог 10 неудач за 15 минут, блокировка нарастает 5 мин → 15 мин → час; успешный ввод пароля серию обнуляет |
| 401 | `INVALID_2FA_CODE` | Неверный/просроченный код 2FA (TOTP или backup) на втором шаге входа |
| 403 | `TWO_FACTOR_SETUP_REQUIRED` | Привилегированной роли нужно включить 2FA; доступ к API закрыт до настройки (кроме эндпоинтов 2FA). Клиент ведёт на `/setup-2fa` |
| 403 | `UNIVERSITY_BLOCKED` | Вуз заблокирован платформой: вход, refresh, регистрация по инвайту и запросы с выданным токеном отклоняются; смена статуса действует на других инстансах до 15 с. Платформенные роли не затронуты |
| 403 | `EMAIL_NOT_VERIFIED` | Работодатель не подтвердил почту компании: вход, QR, 2FA и refresh закрыты до перехода по ссылке |
| 409 | `USERNAME_TAKEN` | Имя пользователя занято другим аккаунтом (`PATCH /users/me/username`). Отдельно от `CONFLICT`: форма подсвечивает именно поле имени |
| 503 | `MAINTENANCE` | Платформа остановлена на техработы. Проходят платформенные роли и маршруты без которых режим не снять: `/auth`, `/auth/2fa`, `/mini`, `/platform`, `/health` |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка |

Коды — публичный контракт: клиент реагирует на `code`, не на `message`. Тексты для пользователя формирует фронтенд через i18n.

### 8.3 Реестр эндпоинтов

**Auth** — `POST /auth/login` (публ.; тело `{ identifier, password }` — `identifier` это email ИЛИ username, регистронезависимо; кроме лимита на пару IP+логин (§7.4) действует счётчик неудач **по учётной записи** — 10 промахов за 15 минут закрывают вход по этому логину на 5 мин → 15 мин → час (`LOGIN_LOCKED`), верный пароль серию обнуляет; при включённой 2FA возвращает `{ twoFactorRequired: true, challengeToken }` вместо токенов) · `POST /auth/login/2fa` (публ.; `{ challengeToken, code }` → сессия; один challenge принимает **не больше трёх** неверных кодов и после этого сгорает — дальше нужен повторный ввод пароля. Счётчик на challenge, а не на пользователя: привязка к аккаунту дала бы знающему пароль способ запереть чужой вход. По уже обменянному или сгоревшему challenge — сразу `401`: код не проверяется, backup-код не списывается; backup-код списывается только после погашения challenge) · `POST /auth/refresh` (cookie; повтор в окне грации и параллельные обмены одной cookie получают того же преемника — обмены цепочки идут под advisory-локом, преемник зашифрован в Redis на окно грации; повтор после окна гасит всю сессию) · `POST /auth/logout` · `GET /auth/me` (содержит `consentRequired`) · `POST /auth/password/forgot` (публ., throttle 3/15 мин; `{ email }` → `202`, ответ одинаков для любого адреса) · `POST /auth/password/reset` (публ., throttle 5/15 мин; `{ token, password }` → `204`; неизвестная, использованная и истёкшая ссылка — одинаковый `BAD_REQUEST`; гасит все сессии, сессию не выдаёт — см. §7.2 п. 3a). Регистрация (`/auth/register-by-invite`) требует `username` (обязателен, 3–32 [a-z0-9_], хранится в нижнем регистре, уникален), а также `birthDate` (ISO `ГГГГ-ММ-ДД`) и `consent: true`; при возрасте до 18 лет обязателен ещё и `guardianConsent: true`. Возраст считается и на клиенте, и **повторно на сервере**: согласие за несовершеннолетнего даёт законный представитель, и это разное основание обработки, а не формальность. В `User` пишутся `consentAt`, `consentVersion` (редакция документов, константа `LEGAL_VERSION`) и `consentByGuardian` — доказать согласие можно только вместе с тем, когда оно дано и на какой текст. `GET /users/me/consent` — состояние согласия, `POST /users/me/consent` — повторное согласие: требуется, если согласие дано на прежнюю редакцию `LEGAL_VERSION` или дата рождения в профиле больше не соответствует основанию (сам / законный представитель; до 18 лет — `guardianConsent`); аудит `consent_accepted`. Учётки без записанного согласия (`consentVersion` NULL) повторно не опрашиваются. Веб показывает неотменяемое окно: принять или выйти. Модель: `User.username String? @unique` (nullable — у зарегистрированных до фичи его нет; задать или сменить можно в настройках, в карточке «Личные данные» — тем же сохранением, что и ФИО; запрос отдельный: `PATCH /users/me/username`). `username` отдаётся **только владельцу** (в `/users/me`): в чужой карточке он вырезается, как и `twoFactorEnabled` — это половина учётных данных, а не публичный хэндл.

**2FA (TOTP)** — `POST /auth/2fa/setup` (секрет + QR/otpauth, pending) · `POST /auth/2fa/enable` (`{ code }` → включить, вернуть backup-коды один раз) · `POST /auth/2fa/disable` (`{ code }` — TOTP или backup) · `POST /auth/2fa/backup-codes` (`{ code }` → `{ backupCodes }` — новые 10 кодов взамен прежних) · `POST /users/:id/2fa/reset` (`{ code }` — админ/модератор платформы или вуза сбрасывает 2FA человеку строго ниже по роли в своём охвате, подтверждая своим TOTP/резервным кодом: без своей 2FA — `403`, у цели 2FA нет — `400`, неверный код — `401 INVALID_2FA_CODE`, 5 промахов за 15 мин — `429`. 2FA выключается, секрет и коды стираются, все сессии гасятся, аудит `user_2fa_reset`, письмо `send-two-factor-reset`). Секрет хранится зашифрованным (AES-256-GCM), backup-коды — bcrypt-хэши; наружу отдаётся только `twoFactorEnabled` (в `/users/me`).

**Форс 2FA для привилегированных ролей.** Ролям `PLATFORM_ADMIN`, `PLATFORM_MODERATOR`, `UNIVERSITY_ADMIN`, `UNIVERSITY_MODERATOR`, `DEAN`, `SECURITY_GUARD`, `LIBRARIAN` двухфакторная аутентификация обязательна. Глобальный `TwoFactorGuard` (после `JwtAuthGuard`) отдаёт `403 TWO_FACTOR_SETUP_REQUIRED` на все эндпоинты, кроме помеченных `@TwoFactorExempt()` (контроллер `auth/2fa/*`), пока 2FA не включена. Флаг `tfa` кладётся в access-токен (без обращения к БД на каждый запрос); при `refresh` payload пересобирается из БД, поэтому после включения 2FA следующая ротация токена снимает форс. Фронт: интерсептор по этому коду уводит на `/setup-2fa` (обязательная настройка); после включения — жёсткий переход на `/`, где `SessionInitializer` перевыпускает токен с `tfa=true`.

**Мини-апп (Telegram, админский)** — `POST /mini/link-code` (авторизован, `PLATFORM_ADMIN`/`PLATFORM_MODERATOR`; → `{ code, expiresIn: 300 }`, код 8 символов живёт в Redis 5 минут, 10/час) · `POST /mini/link` (**публ.**; `{ initData, code }` → привязка + токен) · `POST /mini/session` (**публ.**; `{ initData }` → `{ token, expiresIn: 900, user }`).

Публичны вынужденно: Telegram открывает мини-апп без нашего JWT, и предъявить в первом запросе нечего, кроме подписанного `initData`. Подпись проверяется по алгоритму Telegram (секрет — HMAC-SHA256 от токена бота с ключом `WebAppData`), сравнение постоянного времени, возраст `auth_date` — не более 5 минут в обе стороны. Отказ любой природы — одинаковый `401 UNAUTHORIZED` без подробностей: по разнице ответов «нет привязки» и «не та роль» вычислялось бы, кто из админов привязан.

Привязка `telegram_id ↔ userId` хранится в `telegram_accounts`, оба идентификатора уникальны; перепривязка — только после явного отзыва: в `POST /mini/link` отозванная или оставшаяся от удалённого аккаунта чужая привязка уступает место, действующая чужая — `409 CONFLICT`. Роль перечитывается из БД на каждую сессию, а не берётся из привязки. Удаление аккаунта удаляет и его привязку.

Токен мини-аппа несёт `tfa` — признак включённой 2FA, прочитанный из БД. Без него глобальный `TwoFactorGuard` отдавал бы `403 TWO_FACTOR_SETUP_REQUIRED` на каждом рабочем запросе: платформенные роли привилегированные все. Сессия при этом выдавалась бы нормально (`/mini/session` публичный, пользователя в запросе ещё нет), и приложение выглядело бы живым при неработающих экранах. Значение не подставляется в `true`: администратор без 2FA получает тот же отказ, что и в вебе.
**Поддержка платформы** — `POST /support` (любая роль; `{ text }` → `{ id, created }`) · `GET /support` (очередь, `PLATFORM_ADMIN`/`PLATFORM_MODERATOR`, `@MiniAllowed()`) · `GET /support/:id` (обращение + переписка) · `POST /support/:id/reply` · `PATCH /support/:id/close`. Обращение — чат типа `SUPPORT_PLATFORM`: участники — автор и команда платформы (создаётся сразу со всей командой). Не путать с `SUPPORT` вуза, где состоят все пользователи университета (в интерфейсе он называется «Помощь вуза»).

*Привязка и её отзыв* — `GET /mini/link` (состояние: к какому Telegram привязан аккаунт, когда привязан и когда последний раз открывали) · `DELETE /mini/link` (отзыв). Обе — `PLATFORM_ADMIN`/`PLATFORM_MODERATOR` из веба. Отзыв проставляет `TelegramAccount.revokedAt`, а строку не удаляет: перепривязка должна быть осознанным действием. Это единственный способ отобрать доступ у потерянного телефона — токен мини-аппа живёт в памяти 15 минут и сам не отзывается, а сессия по отозванной привязке больше не выдаётся.

*Язык мини-аппа* берётся из Telegram (`initDataUnsafe.user.language_code`), а не из настроек платформы: приложение открывается до выдачи сессии, и на экране привязки платформа о человеке ещё ничего не знает. Словари — `apps/mini-app/src/i18n/messages.ts` (ru/kk/en); их полнота и совпадение подстановок проверяются тестами.

*Что открыто мини-аппу.* Белый список `@MiniAllowed()` — 45 маршрутов: жалобы (очередь, карточка, переписка по жалобе, решение, квитирование, возврат в очередь, жалоба из обращения), поддержка (очередь, обращение, ответ, назначение, эскалация, закрытие, теги и их сводка, склейка дублей, голосовой ответ), состояние и рычаги платформы (включая откат последнего изменения), аналитика (`GET /analytics/platform/overview`, воронка инвайтов, размер вузов, топ действий и `complaints-latency` — из него берётся одна медиана времени разбора), люди (`GET /users`, `GET /users/:id`, `GET /users/:id/moderation`, блокировка, разблокировка и сброс сессий) и приглашения (`GET /invites`, отзыв). Всё остальное токену с `client: 'mini'` запрещено независимо от роли. Выдачи приглашений, массового импорта и правки профиля в списке нет намеренно: они требуют ввода и выбора scope — работа для клавиатуры, а не для телефона.

*Карточка для модератора.* `GET /users/:id/moderation` (Moderator+, `@MiniAllowed()`) — роль, вуз, `isBlocked`, `blockedUntil`, дата регистрации, число предупреждений и счётчик жалоб на самого человека (`total` / `upheld`). Отдельно от `GET /users/:id`: тот отдаёт профиль в полсотни полей и без `isBlocked`, а решение по жалобе или обращению принимают по четырём. Жалобы на посты и сообщения человека в счётчик не входят — собрать их значило бы пройти по всем его сущностям на каждое открытие карточки; историю по конкретной цели показывает `GET /complaints?targetId=`.

*Сброс сессий.* `PATCH /users/:id/logout` (Moderator+, `@MiniAllowed()`) завершает все сессии человека, не отбирая доступ. Угнанный аккаунт до этого останавливали блокировкой целиком — то есть наказывали пострадавшего; сброс выгоняет чужого и оставляет хозяину возможность войти заново.

*Подтверждение разрушительных действий.* Глобальный `ActionConfirmGuard` требует код 2FA в поле `code` для маршрутов с `@RequiresConfirmation()` — **только когда запрос идёт из мини-аппа** (`client: 'mini'`). В вебе человек прошёл пароль и 2FA в той же сессии, а телефон открывается одним касанием: потерянный аппарат иначе даёт полный доступ к модерации без единого вопроса. Декоратор принимает предикат по телу запроса — на `PATCH /complaints/:id/resolve` код спрашивается только при `action: 'BLOCK_USER'`: требовать его на «нарушения нет» значило бы приучить вводить код не глядя, а не требовать на блокировке через жалобу — оставить защиту декоративной. Разблокировка кода не требует: та же асимметрия, что у техработ.

Проверка живёт в guard'е, а не в сервисе, намеренно: домены `auth` и `users` замкнуты друг на друга через `forwardRef`, и каждый новый импорт в это кольцо однажды уже уронил запуск приложения при зелёных тестах и typecheck.

Сам guard зависит от **токена** `ACTION_CONFIRMATION` (`common/auth/confirmation.constants.ts` — файл без импортов), а не от класса `TwoFactorService`: прямой импорт замыкает кольцо `auth.module → guard → two-factor.service → users.service → auth.service → two-factor.service`, и `TwoFactorService` оказывается `undefined` в момент чтения метаданных `AuthService`. Тот же приём применён к `PLATFORM_STATE` для `MaintenanceGuard`. Ни типы, ни тесты этого не ловят — только реальный запуск приложения.

*Очереди задач.* `GET /platform/queues` отдаёт по каждой очереди BullMQ число ждущих и упавших задач. Растущее первое означает, что воркер не справляется, ненулевое второе — что часть работы потеряна молча; до этого оба числа были видны только в логах. Метод `QueueService.counts` возвращён вместе с экраном, который его читает, — ровно его однажды удаляли как мёртвый код, потому что читателя не было.

*Хранилище и журнал.* `GET /platform/storage` — объём файлов по записям `File`, а не свободное место на диске: S3-совместимое хранилище про свой диск не рассказывает, и обещать «осталось столько-то» было бы враньём; зато виден рост, а он и есть то, что заканчивается; ответ кэшируется в Redis на 5 минут. `GET /platform/changes` — последние 20 изменений рычагов из журнала аудита с именами: публичное состояние авторов не отдаёт (посетителю знать незачем), а команде без ответа на «кто включил техработы» жить нельзя. Имена добираются отдельным запросом — у `AuditLog` нет связи с `User` намеренно, журнал переживает удаление аккаунта.

*Наблюдение за зависимостями.* Cron `watchServices` (каждые 5 минут) проверяет те же три зависимости, что и `/health`, и сигналит **только на переход** «упало» / «поднялось»: повторять «всё ещё лежит» каждые пять минут бессмысленно, а поток одинаковых сообщений учит их не читать. Сигнал идёт как эскалация — мимо дежурства и тихих часов.

*Всплеск ошибок.* `HttpExceptionFilter` считает 5xx по минутным корзинам в Redis (`recordServerError`), тот же cron читает сумму за час и уведомляет при 25+, молча следующий час. Это возвращение счётчика, удалённого в начале эпика как мёртвый код, — с двумя отличиями: считаются только серверные ошибки (единицы в сутки, а не тысячи в минуту) и у счётчика есть читатель.

Второе обращение при открытом первом не заводится — дописывается в существующее (`created: false`): иначе один человек за минуту создаёт десяток веток, и очередь перестаёт показывать, сколько людей ждут ответа. Склеенная ветка (см. «Склейка дублей») для дописывания не берётся. Закрытие — отметка времени `Chat.supportClosedAt`; переписка остаётся, а **любое сообщение в закрытое обращение открывает его снова**, иначе человек с уточняющим вопросом завёл бы второе обращение о том же. Сообщение автора будит команду в Telegram, если обращение было закрыто или последнее слово было за командой; из команды `MESSAGE`-уведомление о новом сообщении получает только назначенный. Сотрудник, назначенный после создания обращения, добавляется в участников лениво при открытии очереди. О чужом обращении сервер отвечает `NOT_FOUND`, а не `FORBIDDEN`: по разнице ответов перебором id вычислялось бы, кто обращался в поддержку.

*Назначение.* `PATCH /support/:id/assign?take=true|false` (`@MiniAllowed()`); очередь фильтруется `?assignee=any|mine|free`. Перехватить чужое обращение нельзя: условие `supportAssigneeId: null` в самом запросе не даст двум одновременным «взять» победить обоим, и второй получает `409 CONFLICT`. Отдать обратно можно только своё.

*Теги.* `PATCH /support/:id/tags` (staff, `@MiniAllowed()`; набор заменяется целиком, до трёх) и `GET /support/tags` — счётчики за 30 дней. Список закрытый (`SUPPORT_TAGS`: ACCESS, DATA, DOCS, BUG, FEATURE, ABUSE, OTHER): свободные теги за неделю разрастаются в «оценки», «оценка», «Оценки!», и сводка «о чём спрашивают чаще» перестаёт складываться. Ради этой сводки теги и заведены — «поддержка отвечает на одно и то же» превращается в «шестьдесят обращений про доступ за месяц», то есть в задачу продукту. Очередь фильтруется `?tag=` на сервере: «все обращения про доступ» среди тридцати загруженных строк — это не «все». Окно в 30 дней намеренное: за всё время счётчик показывал бы историю платформы, а не то, что происходит сейчас.

*Голосовой ответ.* `POST /support/:id/voice` (staff, `@MiniAllowed()`, multipart, одно аудио). На телефоне надиктовать быстрее, чем набрать, а поддержка с телефона только этим и занимается. Отдельная ручка, а не `@MiniAllowed()` на `POST /chats/:id/messages`: последнее открыло бы токену мини-аппа все чаты сотрудника, включая личные. Файл именуется `voice-msg.<ext>` — по имени чат распознаёт голосовое, потому что mime по содержимому непредсказуем (webm-аудио браузеры отдают как `video/webm`). Правила текстового ответа действуют те же: закрытое обращение открывается снова, отметка первого ответа ставится один раз.

*Склейка дублей.* `POST /support/:id/merge` (staff, `@MiniAllowed()`; тело `{ intoId }`). Параллельных веток одного человека модель не допускает (`open` дописывает в открытое), но последовательные бывают: обращение закрыли, человек завёл новое о том же. Склеенная ветка закрывается и получает указатель `support_merged_into_id`; **сообщения не переносятся** — перенос переписал бы отправителям их собственную историю, а порядок внутри чата задан `seq`, который в чужом чате ничего не значит. Вместо переноса `GET /support/:id` отдаёт переписку целевой ветки вместе с перепиской склеенных, отсортированную по времени. Склеивать можно только обращения одного человека: две ветки разных людей — это чужая переписка в чужом обращении. Цепочки запрещены (`409`): читатель идёт ровно на один шаг, и ветка, склеенная в склеенное, не была бы видна нигде. В очереди склеенные не показываются ни среди открытых, ни среди закрытых, а в ответе треда есть `siblings` — другие обращения того же человека, то есть готовые кандидаты на склейку.

*Поиск и автозакрытие.* `GET /support?search=` ищет сразу по тексту переписки и по фамилии автора: «мы это уже кому-то отвечали» помнят словами, «что там было у Сериковой» — фамилией, и заставлять выбирать между ними незачем. Ежедневный cron `closeStaleTickets` закрывает обращения без движения 14 дней, но **только те, где последним писала команда**: обращение, где последним писал автор, — это неотвеченный вопрос, и закрывать его по таймеру значит прятать собственный долг. Ответ закрытое обращение открывает снова, поэтому закрытие ничего не отнимает.

*Эскалация.* `POST /support/:id/escalate` — действие, а не состояние: ответ на эскалацию человек, а не флаг в таблице. Уведомление уходит только `PLATFORM_ADMIN` и **мимо дежурства и тихих часов**: эскалируют ровно тогда, когда обычный путь не сработал, и глушить её теми же правилами значило бы глушить именно тот сигнал, ради которого её завели.

*Время первого ответа* (`Chat.supportFirstReplyAt`) проставляется один раз, при первом ответе КОМАНДЫ, и больше не меняется: повторное открытие обращения не делает первый ответ быстрее, а перезапись улучшала бы метрику задним числом.

**Уведомления в Telegram** — `TelegramNotifyService` (`common/telegram`) пишет команде платформы о срочной жалобе (приоритет `HIGH`) и о новом обращении. Глобальный модуль без зависимостей: уведомлять нужно из жалоб и из поддержки, а импорт `MiniModule` втянул бы в оба домена `AuthModule`. Кнопка в сообщении открывает нужную карточку через `startapp=complaint_<id>` / `support_<id>` — нужен `MINI_APP_URL`, без него уходит голый текст. Текст уведомления не содержит ни жалобы, ни обращения: Telegram — чужая инфраструктура, и сообщение говорит, ЧТО пришло и сколько такого ждёт в очереди, а читается оно в мини-аппе. Размер очереди строкой ниже — потому что «срочная жалоба» звучит одинаково и когда она одна, и когда она девятая, а решать, бросать ли текущее дело, приходится по этому тексту. Ошибка отправки никогда не роняет операцию, без `TELEGRAM_BOT_TOKEN` сервис молчит.

**Состояние платформы** — `GET /platform/state` (**публ.**, Bearer необязателен) → `{ maintenance, banner, disabledSections, announcedVersion, season, notifications }`. Ответ зависит от зрителя: аноним получает его без `notifications` и без адресных баннеров; вошедший видит баннер, только если тот ему адресован (`universityIds` сужается до своего вуза); команда платформы видит всё, включая настройки уведомлений команды. Глобальные рычаги, которыми админ управляет вебом без деплоя: режим техработ, баннер-объявление, погашенные разделы, объявленная версия релиза. Хранятся в `platform_state` (одна строка, `id = "singleton"`), кэш в Redis на 60 секунд; источник правды — БД, чтобы перезапуск Redis не снимал режим техработ.

Публичен вынужденно: страница логина тоже обязана показать техработы, иначе человек бьётся в форму, которая всё равно не пустит. Наружу уходят только объявления, адресованные посетителю; `updatedById` не публикуется.

Режим техработ и баннер хранятся **сроком** (`maintenance_until`, `banner_until`), а не флагом: состояние «включено навсегда» выразить нельзя, поэтому забытый выключатель снимается сам и cron для этого не нужен. Срок применяется на сервере — наружу уходит либо действующее объявление, либо `null`, и клиенты с уехавшими часами не решают этот вопрос каждый по-своему. Текст отдаётся только на всех трёх языках сразу: строка на двух из трёх — дыра в интерфейсе.

*Плановые техработы.* `startsInMinutes` задаёт отложенное начало (`maintenance_from`); срок окончания считается от НАЧАЛА окна, а не от нажатия, иначе работы, назначенные на вечер, кончались бы через час. До начала окна платформа работает, `MaintenanceGuard` пропускает, а веб показывает предупреждение: предупреждение и остановка — разные состояния одного события, и задаются они одним действием, чтобы два объявления об одном событии не разошлись.

*Адресный баннер.* `banner_roles` и `banner_university_ids` (пустые массивы — всем) фильтрует СЕРВЕР по зрителю (`forViewer`): кэш в Redis общий, а сужение под роль и вуз делается поверх него при ответе; веб-фильтр (`platform-gate`) остался и после серверного просто ничего не отсеивает. Роль и вуз проверяются как пересечение: «преподавателям такого-то вуза» не должно долетать до преподавателей остальных. Снятие баннера стирает и прицел — иначе следующий унаследовал бы чужой.

`announced_version` хранит только номер версии; текст ноты «Что нового» остаётся в бандле web (см. `28-releases.prisma`), и веб показывает ноту, лишь если её версия не выше его собственной сборки — у PWA с домашнего экрана вкладка неделями живёт на старой сборке — и не новее `announcedVersion` (`null` — без ограничения).

*Праздничное оформление.* `season` → `{ off, override }`. Сам праздник веб считает по справочнику в своём бандле (`apps/web/src/shared/config/holidays.ts`): даты одинаковы для всех и меняются раз в несколько лет законом, ради них не нужен ни запрос, ни таблица — и оформление обязано ехать той же сборкой, что и код, который его рисует. В `platform_state` лежит только вмешательство человека: `season_off` гасит праздник у всех без деплоя (траур, авария), `season_override` показывает сезон вне его даты (юбилей вуза, день открытых дверей). Срока у сезона нет намеренно, в отличие от техработ и баннера: те гасят продукт или требуют внимания, а забытый сезон — это другой цвет кнопки. Допустимые значения `override` перечислены в `SEASON_IDS` (`shared-schemas`); совпадение списка со справочником сторожит тест в вебе. Личная настройка человека сильнее подмены: согласие видеть оформление он даёт сам.

*Запись рычагов* — `PATCH /platform/maintenance` · `PATCH /platform/banner` · `PATCH /platform/sections` · `PATCH /platform/season` · `PATCH /platform/release`. Все — только `PLATFORM_ADMIN`, все помечены `@MiniAllowed()` (управление платформой с телефона и есть смысл мини-аппа). Модератора среди пишущих нет: его работа — разбирать жалобы, а выключатель, гасящий продукт для всех, к ней не относится. Каждое изменение пишется в `AuditLog` (`platform.maintenance.on|off`, `platform.banner.on|off`, `platform.sections.set`, `platform.season.set`, `platform.release.announce`).

Длительность приходит **минутами** (`minutes`), а не меткой времени: абсолютное время, посчитанное на телефоне с уехавшими часами, назначило бы окончание техработ не на тот момент. `minutes: null` — снять немедленно. Потолки: техработы ≤ 12 часов, баннер ≤ 30 суток.

**Включение техработ требует кода 2FA (`code`), снятие — нет.** Асимметрия намеренная: остановить платформу для всех нельзя одним промахом по экрану, а вернуть её обязано быть возможно всегда и быстро — иначе потерянный телефон продлевал бы простой. Код проверяет `TwoFactorService.verifyForUser` (TOTP или backup-код); неверный или отсутствующий → `401 INVALID_2FA_CODE`. Эндпоинт ограничен 5 запросами в минуту — против перебора кода.

*Принуждение.* Глобальный `MaintenanceGuard` (сразу после `JwtAuthGuard`) отдаёт `503 MAINTENANCE` всем, кроме `PLATFORM_ADMIN`/`PLATFORM_MODERATOR` и маршрутов с `@MaintenanceExempt()`. Техработы останавливают и запись через WS: `message:send|edit|delete` неплатформенных ролей → `error { code: 'MAINTENANCE' }`; вход в комнату, «печатает» и `message:read` работают. Список исключений — это список того, без чего режим НЕЛЬЗЯ СНЯТЬ, поэтому декоратор ставится на весь контроллер, а не на отдельные ручки: вход (`AuthController`, `TwoFactorController`), мини-апп (`MiniController`), состояние платформы (`PlatformController`) и живость (`HealthController` — без неё хостинг решит, что контейнер умер, и будет перезапускать его по кругу).

*Дежурство по очереди* — `GET /platform/duty` · `PATCH /platform/duty` (`PLATFORM_ADMIN`, `@MiniAllowed()`; `rotation` — до 10 id по порядку). В очередь и в дежурные можно поставить только сотрудника платформы (не удалён, не заблокирован) с действующей привязкой Telegram, иначе `422 VALIDATION_ERROR`; проверяются только новые id. Крон `rotateDuty` по понедельникам в 9:00 по поясу платформы (`Asia/Almaty`, `PLATFORM_TIME_ZONE`) делает дежурным следующего за текущим и пропускает тех, кому бот не может написать. Позиция ищется по id текущего дежурного, а не хранится числом: номер смены пришлось бы чинить руками при каждой правке списка, а по имени всё сходится само; дежурный не из списка (назначили руками на выходные) начинает круг сначала. Пул — те, кто привязал Telegram (`GET /mini/links` — только незаблокированные `PLATFORM_ADMIN`/`PLATFORM_MODERATOR`): дежурить может только тот, кому бот в принципе может написать. Отдельно от публичного `GET /platform/state` намеренно — список всей команды посетителю сайта знать незачем. Ротацию зовёт CleanupService через токен `PLATFORM_STATE`, а не через `PlatformService`: импорт сервиса втянул бы в планировщик домен auth.

*Откат* — `POST /platform/undo` (`PLATFORM_ADMIN`, `@MiniAllowed()`). Возвращает состояние, которое было до последнего изменения рычагов: чипы на телефоне стоят рядом, палец один, а прежнее состояние нигде не показано. Снимок «как было» пишется в метаданные каждой записи `platform.*` и содержит **только переписанные поля** — возврат баннера не снимет техработы, включённые в ту же минуту кем-то другим. Запись об откате сама несёт снимок, поэтому второе нажатие возвращает всё обратно. Автоматическая смена дежурного (`platform.duty.rotate`) откатом не считается и пропускается. Два ограничения: старше 30 минут — `409` (это уже не промах, а решение), и откатом нельзя включить техработы — на это есть своя кнопка, спрашивающая код 2FA.

*Уведомления команде* — `PATCH /platform/notifications` (`PLATFORM_ADMIN`, `@MiniAllowed()`): тихие часы, виды уведомлений, дежурный и час суточной сводки. Хранятся в той же строке `platform_state`.

Тихие часы задаются целыми часами по поясу платформы `Asia/Almaty` (`PLATFORM_TIME_ZONE`), а не по часам сервера — так же считаются час суточной сводки и понедельничная смена дежурства — и почти всегда переходят через полночь («с 22 до 8»), поэтому проверка — не «между», а «вне диапазона» при `from > to`. `from === to` означает тишину круглые сутки: так уведомления выключают, не стирая настройку.

`muted_notifications` — список ВЫКЛЮЧЕННОГО (`complaint|ticket|reply|digest`), чтобы новый вид уведомления по умолчанию доходил. Заданный `duty_user_id` направляет уведомления только дежурному: сообщение всей команде означает, что не среагирует никто. Если дежурному не дойти, уведомление уходит всей команде, и в лог пишется warn. Отказ чтения настроек уведомления не глушит — они не условие доступа.

Суточная сводка идёт ежечасным cron `sendDailyDigest` (`CleanupService`, §9.3) и отправляется в выбранный час: держать время в cron-выражении значило бы перезапускать приложение ради его смены. Сводка уходит и при пустой очереди — по её отсутствию нельзя отличить спокойный день от сломавшейся отправки. В ней очередь и движение за сутки (пришло / разобрано) по жалобам и обращениям, возраст самого старого из ждущих и кто дежурит: ноль в очереди после сорока разобранных жалоб и ноль в тихий день — разные новости, а по одному числу очереди выглядели одинаково. Текст собирает `common/telegram/digest.ts` — ту же сводку по запросу отдаёт команда бота `/digest`, и две копии текста отвечали бы по-разному на один вопрос.

Вопрос «идут ли техработы» задаёт каждый запрос, поэтому ответ лежит в памяти процесса 5 секунд (`MAINTENANCE_MEMO_MS`) — иначе к каждому запросу платформы добавился бы round-trip в Redis. Столько же режим доходит до инстанса, который его не включал; инстанс, принявший команду, сбрасывает память сразу.

*Разделы в вебе.* Погашенный раздел уходит из навигации (`isNavKeyDisabled`) и закрывается по прямой ссылке (`disabledSectionForPath` в `PlatformGate`) — **у всех, включая платформенные роли**: решающий, вернуть ли раздел, должен видеть ту же платформу, что и пользователи. Административные экраны настройки (типы документов, доступы) не гасятся: раздел выключают как раз тогда, когда в нём что-то сломалось.

Токен мини-аппа несёт `client: 'mini'` и живёт 15 минут; refresh-токена нет — клиент присылает свежий `initData`. Такой токен допускается **только** на маршруты с `@MiniAllowed()` (`MiniAppGuard`), на остальных — `403 FORBIDDEN`, независимо от роли. В Socket.IO токен мини-аппа не пускается вовсе: handshake и `auth:refresh` его отклоняют. Состав белого списка — в §8.3 («Что открыто мини-аппу»): держать два перечня в разных разделах значит однажды их разъехать.

**Вход по QR** (стиль Telegram Web; телефон уже авторизован) — `POST /auth/qr/create` (публ.; → `{ qrId, qr, claimSecret, expiresIn }`, QR кодирует `${WEB}/qr?t=<approveToken>`) · `POST /auth/qr/preview` (авторизован; `{ approveToken }` → `{ requester: { browser, os, ip }, createdAt }` — кто просит вход: браузер и ОС по User-Agent, IP с маской `a.b.c.x`; страница `/qr` показывает это до кнопки «Подтвердить», иначе присланную «на проверку» ссылку на чужой QR подтверждали вслепую; после подтверждения — 404) · `POST /auth/qr/approve` (авторизован; `{ approveToken }` — подтверждение с телефона; подтверждает вход один раз: повтор другим пользователем → `409 CONFLICT`, тем же — без изменений; access-токен старше 5 минут (по `iat`) → `401 TOKEN_EXPIRED`, клиент обновляет токен и повторяет запрос) · `POST /auth/qr/claim` (публ.; `{ qrId, claimSecret }` → сессия; забирает ровно один запрос — по результату `DEL`). Состояние — в Redis (TTL 2 мин, одноразовое). WS: отдельный namespace `/qr-login` (без токена), клиент шлёт `qr:subscribe { qrId }`, сервер эмитит `qr:approved { qrId }` при подтверждении. `claimSecret` в QR не попадает — сессию заберёт только инициировавший десктоп.

**Инвайты** — `GET /invites/:token/preview` (публ.) · `POST /auth/register-by-invite` (публ.) · `POST /invites` · `GET /invites` (в элементах списка — `createdBy`; `?scope=university` для `UNIVERSITY_ADMIN` — все инвайты вуза, а не только свои) · `POST /invites/bulk/preview` · `POST /invites/bulk` · `PATCH /invites/:id/revoke` (только из `PENDING`, иначе `409`). Правила выдачи, отзыва и истечения — §7.3.

**Пользователи** — `GET|PATCH /users/me` · `PATCH /users/me/username` (смена имени входа; тело `{ username }`, нормализуется в нижний регистр, `409 USERNAME_TAKEN` если занято; пишется в аудит как `change_username`) · `POST|DELETE /users/me/avatar` · `POST|DELETE /users/me/cover` (обложка профиля, multipart-изображение ≤ 10 МБ, бакет `profile-covers`) · `PATCH /users/me/password` (5 неверных текущих паролей за 15 минут → `429 RATE_LIMIT` до конца окна) · `DELETE /users/me` (`{ password, code? }`, `code` обязателен при включённой 2FA; неверный пароль → `400`, неверный код → `401 INVALID_2FA_CODE`, последний активный `PLATFORM_ADMIN` → `409`; что удаляется — §11.3) · `GET /users/:id` · `GET /users` (Admin+; у элемента есть `twoFactorEnabled`; фильтры `role/facultyId/groupId/search/blocked`, offset-пагинация (`limit` ≤ 200 — таблица даёт выбрать 20/100/150/200) + сортировка `?sort=name|email|role|blocked|createdAt&order=asc|desc` — по всей выборке, не по странице; поле сортировки — enum, произвольное имя в `orderBy` не попадает) · `GET /users/directory?q=&limit=` (справочник людей «кому написать», §50 — **все роли**, в отличие от `GET /users`: отдаёт только визитки (id, ФИО, аватар, роль, headline, группа/факультет) в пределах вуза смотрящего — платформенные роли вуза не имеют и ищут по всем, `EMPLOYER` доступа к справочнику не имеет. Ответ `{ items, hasMore }` без курсора: это пикер, при переполнении клиент просит уточнить запрос. У каждой карточки `isFriend` и `section` = `friend|group|university` — секции задают порядок: друзья → одногруппники → остальной вуз. Заблокированные в любую сторону исключены) · `GET /users/export?format=xlsx|csv&locale=` (Admin+; выгрузка списка файлом — та же выборка и те же фильтры, что у `GET /users`, включая scope; потолок 5000 строк, выше — `400 BAD_REQUEST` вместо тихого обрезания; не больше 5 выгрузок в минуту на пользователя; пишется в `AuditLog` (`users_export`) и в `DocumentExport`) · `PATCH /users/:id/block|unblock` (Moderator+) · `PATCH /users/:id/academic` (DEAN/UNIVERSITY_ADMIN, учебные данные студента — §3.7). Профиль отдаёт `avatarUrl`, `avatarThumbUrl` (квадратное превью ≈128px, генерируется джобой `generate-thumbnail` в очереди `file-processing`; асинхронно, до готовности `null`) и `coverUrl` (публичные URL; `coverUrl` виден и в «визитке» закрытого профиля).

**Друзья** (симметричная дружба, ВК-стиль; Social-зона — все роли) — `POST /friends/requests {userId}` (заявка; встречная PENDING → авто-принятие; создаётся под локом пары; после отклонения повтор закрыт на 7 дней — `409`) · `POST /friends/requests/:id/accept` (только адресат) · `DELETE /friends/:id` (отмена/отклонение/удаление из друзей — любой участник) · `GET /friends` (друзья, cursor) · `GET /friends/requests?direction=incoming|outgoing` (заявки, cursor) · `GET /friends/count` (счётчики) · `GET /friends/status/:userId` (статус `NONE|PENDING_OUTGOING|PENDING_INCOMING|ACCEPTED` + `friendshipId` — для кнопки в профиле). Модель `Friendship` (`requesterId`/`addresseeId`/`status`, `@@unique([requesterId, addresseeId])`); enum `FriendshipStatus = PENDING|ACCEPTED` (блокировка — отдельная `UserBlock`). Списки и счётчики друзей — без удалённых и заблокированных. Уведомления о заявке/принятии — тип `SYSTEM` (`data.url='/friends'`). Личная блокировка (`POST /chats/blocks/:userId`) удаляет дружбу и заявки в обе стороны и гасит уведомление-заявку; при блокировке дружба не открывает профиль, заявку принять нельзя (`403`), заблокированные не попадают в списки друзей и счётчики.

**Университеты** — `GET|POST /universities` · `GET|PATCH /universities/:id` · `PATCH /universities/:id/status` (Platform Admin) · `GET /universities/:id/stats`. `GET /universities` принимает `page`, `limit` (20/100/150/200, как у остальных админских таблиц), `search` (по названию и аббревиатуре, без учёта регистра), `status` и `sort`+`order` по колонкам `name|shortName|status|createdAt`. Поиск и сортировка идут по всей выборке, а не по открытой странице; `meta.total` считается по тем же фильтрам. Города в списке сортировки нет намеренно — см. ниже про КАТО: сортировка по коду выстроила бы строки по регионам, а не по алфавиту названий. Поле `city` хранит **код КАТО** (9 цифр), а не название: город переименуют — записи не протухнут, и казахская локаль берётся из справочника. Для зарубежного вуза, которого в КАТО нет, остаётся свободный текст — внешним ключом поле не связано.

**Справочник КАТО** (классификатор административно-территориальных объектов РК) — `GET /kato?search=&scope=places|regions|all&limit=` (поиск для комбобокса; ищет по русскому и казахскому названию сразу) · `GET /kato/resolve?codes=a,b,c` (названия по кодам, до 100 за запрос — один запрос на список вместо запроса на строку). Доступен всем аутентифицированным, без `@Roles` и без scope-гейта: названия городов — не персональные данные, а справочник общий для платформы. Модель `KatoUnit` (`code` — 9-значный код КАТО как первичный ключ, `kind`, `nameRu`/`nameKk`, `parentCode` — self-FK, `regionCode`), enum `KatoKind = REGION|DISTRICT|ADMIN|CITY|SETTLEMENT|VILLAGE|STATION|OTHER`. 16 205 записей, заливаются шагом сида `pnpm db:seed:kato` из `prisma/seed/data/kato.json` (генерируется из выгрузки stat.gov.kz скриптом `scripts/gen-kato.mjs`). **Верхний уровень — это `region_code = code` (20 записей: 17 областей + Астана, Алматы, Шымкент), а не `kind = 'REGION'`** (три города республиканского значения — города) и не `parentCode IS NULL` (под него попадают ещё 38 объектов с битой иерархией в исходной выгрузке).

**Факультеты** — `GET|POST /faculties` · `GET|PATCH|DELETE /faculties/:id` (удаление только без групп). Название факультета уникально в вузе, группы — на факультете, специальности — в справочнике вуза, без учёта регистра: дубль → `409 CONFLICT` (`details.field=name`).

**Специальности** (справочник вуза, `UNIVERSITY_ADMIN`; вуз — из JWT) — `GET|POST /specialties` · `PATCH|DELETE /specialties/:id` (`PATCH { name }` — переименование, переименовывает `specialty` и у студентов вуза; чужой вуз → `WRONG_SCOPE`, занятое название → `CONFLICT`)

**Группы** — `GET|POST /groups` (`GET` принимает необязательный `search` — подстрока названия без учёта регистра; выдача упорядочена по названию, затем по id, чтобы одноимённые записи не терялись и не дублировались на стыке страниц) · `GET|PATCH|DELETE /groups/:id` (`DELETE` → `409 CONFLICT`, если есть студенты, расписание, курсы, экзамены или материалы; `details[].field ∈ students|schedule|courses|exams|materials`) · `GET /groups/:id/members` · `PATCH /groups/:id/starosta` (`{ starostaId | null }`, админ вуза или декан факультета группы; старостой становится только студент этой группы. Староста — роль, а не отметка: в одной транзакции выбранный получает `STAROSTA`, остальные старосты группы — `STUDENT`; разжалованным гасятся сессии, обе смены роли пишутся в аудит `user_role_changed`)

**Расписание** — `GET /schedule` (по роли; фильтры `groupId/teacherId/roomId/dayOfWeek/weekType/subject`, отдаёт таймзону вуза) · `GET /schedule/changes` (`?from=&to=`; для `TEACHER` — изменения своих пар и тех, где он заменяющий; `pair` в изменении содержит `scheduleId`, `weekType`, `teacher`, `room`) · `POST /schedule/changes` (Dean/Admin; дата обязана быть днём недели пары — `422`, `field=date`; на уже отменённую дату — `409`; `MOVED`/`ROOM_CHANGED`/`SUBSTITUTED` проверяются на занятость в сетке даты → `409` с `details[]`) · `DELETE /schedule/changes/:id` (`PLATFORM_ADMIN`/`UNIVERSITY_ADMIN`/`DEAN` → `204`; WS `schedule:changed`/`schedule.lesson.updated` `{ change, groupId, removed: true }` в `group:<id>` и `user:<id>` преподавателей; уведомление `SCHEDULE_CHANGE` с `dedupe schedule-change-removed:<id>`, если дата ещё не прошла) · `GET|POST /schedules` · `GET|PATCH|DELETE /schedules/:id` (`PATCH { isActive: true }` перепроверяет конфликты → `409` с `details[]`; веб создаёт новую версию черновиком, если у группы уже есть активная) · `POST /pairs` (преподаватель — только себе и только в группе, где ведёт дисциплину, иначе `403 WRONG_SCOPE`: пара даёт ему ростер, посещаемость и предметный чат группы) · `PATCH|DELETE /pairs/:id`. `DELETE /pairs/:id` и `DELETE /schedules/:id` отвечают `409 CONFLICT` (`details[].field = "attendance"`), если по паре (парам версии) уже отмечена посещаемость: история не стирается — пару переносят правкой, версию деактивируют (`Attendance.pair` — `onDelete: Restrict`). Преподавателем пары и заменяющим можно назначить только действующего преподавателя или декана своего вуза, иначе `422 VALIDATION_ERROR` (`details[].field = teacherId/newTeacherId`). Проверка конфликтов, запись пары и активация версии идут под advisory-локом дня недели вуза; черновик не конфликтует с действующей версией своей группы. Преподаватель правит свою пару только в группе, где ведёт дисциплину (`403 WRONG_SCOPE`). При замене на дату журнал посещаемости ведёт заменяющий, основной преподаватель получает `FORBIDDEN`; `GET /me/today` для `TEACHER` включает в `pairs` чужие пары, которые он сегодня ведёт по замене. WS `schedule:changed`/`schedule.lesson.updated` уходит также в `user:<id>` основного и заменяющего; при правке или удалении пары активной версии payload — `{ change: null, groupId, pairId[, removed] }`.

**Файлы** — `POST /files/upload?bucket=` (буферная, ≤10 МБ) · `POST /files/presign` + `POST /files/confirm` (прямая загрузка крупных файлов: шаги 1 и 3, между ними браузер делает PUT в MinIO) · `GET /files/:id/presigned` · `DELETE /files/:id`. Доменные загрузки имеют свои пары: `POST /documents/upload/presign|confirm`, `POST /materials/:id/files/presign|confirm`, `POST /profile-content/media/presign|confirm`. Файлы больше `FILE_UPLOAD.MULTIPART_THRESHOLD_BYTES` (50 МБ) — многочастной загрузкой: `POST /files/multipart/start` (→ `key`, `uploadId`, размер и число частей) · `POST /files/multipart/urls` (подписи на диапазон частей `[from, to]`, нумерация с единицы) · PUT каждой части браузером · `POST /files/multipart/complete` (сервер склеивает и прогоняет объект через ту же проверку, что и `confirm`) · `POST /files/multipart/abort`. Сборку делает сервер, а не подписанная ссылка: иначе в приватном бакете появлялись бы объекты, которых никто не проверял по magic bytes. `etag` частей присылает клиент — в `minio@8` `listParts` объявлен protected, и серверу их взять неоткуда; подлог бесполезен, MinIO сверяет их сам. Ключ на каждом шаге обязан начинаться с идентификатора вызывающего. Предел видео и документов — 500 МБ (скан сборника или лекция с телефона весят больше прежних 25 и 100 МБ), изображения и аудио прежние. Архивы (`FILE_UPLOAD.ALLOWED_MIME.ARCHIVE`: ZIP, RAR, 7z, GZ, TAR, BZ2, XZ по magic bytes; предел 500 МБ) — категория «по приглашению» (`FILE_UPLOAD.OPT_IN_CATEGORIES`): `FileService` принимает её только при `allowArchives: true`, и передают его лишь вложения чатов. Любой другой путь (`/files/*`, документы, материалы, медиа профиля) отвечает на архив `415 FILE_TYPE_NOT_ALLOWED`, при прямой загрузке объект удаляется. Правила недоверия на шаге confirm — `docs/BACKEND_RULES.md §8.1`. Пара `(bucket, key)` **не уникальна**: на один объект хранилища может ссылаться несколько записей `File` (общий пул медиа у сида). Поэтому `DELETE /files/:id` удаляет объект в MinIO только когда ушла последняя ссылающаяся на него запись; пока есть другие — удаляется только строка. Обратный порядок непоправим: снесённый объект гасит картинку у всех остальных владельцев ссылок. Осиротевший объект (если две последние записи ушли одновременно) ночью уберёт `cleanOrphanFiles`. `DELETE /files/:id` удаляет только свой неприкреплённый файл (все FK владельцев пусты, не медиа сториса и не обложка альбома, не аватар); прикреплённый → `409 CONFLICT`, он удаляется через раздел-владелец.

**Медиа (единая медиа-система, `src/modules/media`)** — пользователь загружает файл один раз, а варианты готовит воркер. Обрабатываются изображения и видео в бакетах `chat-media`, `posts-media`, `stories-media`, `profile-media`, `materials` (аватары — своей джобой превью, документы и заявки — нет: сканы открывают целиком). Изображение → WebP-копии шириной 320/640/1280/2048 (только заметно у́же оригинала; GIF — без копий, анимацию показывает оригинал), LQIP-заглушка (data-URI WebP ≈16 px, сотни байт), размеры с учётом EXIF-поворота; из копий EXIF и GPS вычищены, оригинал не трогается. Видео → постер (кадр на 1-й секунде, WebP 640/1280), HLS-лесенка 360/480/720/1080 по **короткой стороне** кадра и только в пределах исходника (ролик меньше 360 — один рендишн своего размера), сегменты 4 с с выровненными ключевыми кадрами, H.264 + AAC, длительность. Варианты лежат в бакете оригинала под префиксом `variants/<fileId>/` — приватность и scope у них те же, что у оригинала; строки — модель `FileVariant`, статус — `File.mediaStatus` (`NONE` — не обрабатывается, `PENDING`/`PROCESSING`, `READY`, `FAILED` — показывается оригинал). Пересылка копирует готовые варианты в хранилище, а не перекодирует; удаление файла сносит префикс; ночная чистка считает объект варианта живым, пока жива запись-владелец. Обработка — очереди `media-image`/`media-video` (§10.1), HTTP-запрос её не ждёт.
Контракт — `MediaInfo`: `{ status, placeholder, width, height, durationMs, sources[], poster[], hls, expiresAt }`, где `sources`/`poster` — `{ width, height, url }` по возрастанию ширины (готовый srcset), `hls` — путь мастер-плейлиста **от корня сервера API** (`/api/v1/media/<id>/hls/master.m3u8?t=…`; веб ходит через свой прокси, мобильные клиенты подставляют свой адрес API), `expiresAt` — срок подписанных ссылок (`null` у публичных бакетов). Поля только добавлены к прежним ответам: `GET /chats/attachments/:fileId/url`, `GET /posts/:id/media/:fileId/url`, `GET /materials/:id/files/:fileId/presigned` отдают `{ url, expiresAt, …MediaInfo }`; медиа сторис (`GET /stories`) и медиа профиля (`GET /profile/:userId/media`) несут поля `MediaInfo` рядом с `url`; обложка альбома — копия 640. В ленте постов и посте по id `media[]` несёт `url` оригинала, `expiresAt` и поля `MediaInfo` (`status`, `sources`, `poster`, `hls`) — ссылки подписываются пачкой на выдачу; `GET /posts/:id/media/:fileId/url` остаётся для продления истёкшей ссылки. В списках без подписи ссылок (сообщения чата, материалы, вкладка «Медиа» чата) у файла есть `width`, `height`, `placeholder`, `mediaStatus`, `durationMs` — заглушка видна раньше запроса за ссылкой. Кружки календаря чата — копии 320, а не оригиналы.
**Подпись ссылок стабильна в пределах окна 5 минут** (`common/minio/stable-sign.ts`): момент подписания округляется вниз, и повторная выдача ссылки на тот же объект даёт тот же URL — браузер берёт байты из кеша. Ссылка живёт 10–15 минут (потолок §8 не нарушается); копии лежат с `Cache-Control: public, max-age=31536000, immutable`.
**HLS приватных видео** — по подписанному токену, а не по JWT: нативный HLS Safari/iOS заголовок Authorization к плейлистам не приложит. `GET /media/:fileId/hls/master.m3u8?t=` — master-токен (15 мин) выдаёт модуль-владелец вместе с остальным описанием, после своей проверки прав; мастер-плейлист раздаёт play-токен на весь просмотр (15 мин + 2 × длительность — иначе длинный ролик обрывался бы посередине). `GET /media/:fileId/hls/:rendition/index.m3u8?t=` — плейлист рендишна с токеном у сегментов. `GET /media/:fileId/hls/:rendition/:segment?t=` — `302` на подписанную ссылку сегмента в хранилище (байты видео через API не идут). Токен привязан к файлу и виду (master/play), подписан `MEDIA_TOKEN_SECRET` (не задан — выводится из `JWT_ACCESS_SECRET` с отдельной солью, токен плейлиста не проходит проверку как access-токен); имя рендишна и сегмента проверяется по шаблону до токена. Лимит частоты маршрутов — 1200/мин: зрители университетской сети сидят за одним IP.

*Избранное.* `POST /posts/:id/bookmark` переключает личную закладку и возвращает `{ bookmarked }`. Переключатель, а не две ручки: клиент не обязан знать текущее состояние, чтобы нажать кнопку, иначе два быстрых нажатия подряд расходятся с сервером. Таблица `post_bookmarks` (пара `user_id + post_id`, уникальная) — своя, а не общая с закладкой на статью профиля (`bookmarks`): это другой домен, и одна таблица на два означала бы полиморфную ссылку.

Признак **личный и наружу не уходит**: в ответе поста есть только `bookmarked` для зрителя, число сохранивших не считается и не публикуется — в отличие от реакций, которые видны всем намеренно.

*Реакции.* Лента и пост по id отдают `reactionSummary: { emoji, count, mine }[]` — сводку реакций из белого списка `POST_REACTION_EMOJIS` в его порядке. Построчный `reactions: { emoji, userId }[]` устарел: остаётся для мобильных клиентов (тоже только из белого списка), `GET /posts?reactions=summary` отдаёт ленту без него. Считается он отдельным запросом на страницу выдачи, а не включением отношения в выборку: отношение отдало бы, КТО ещё сохранил пост. Полка (`filter=SAVED`) пересекается с видимостью, как и любой другой таб: пост, который человек больше не имеет права видеть, в ней не появится.

**Аналитика платформы** (дашборд `PLATFORM_ADMIN`) — read-only агрегаты по всем вузам, только
`PLATFORM_ADMIN`/`PLATFORM_MODERATOR`, префикс `GET /analytics/platform/*`. Общие query-параметры
периода: `from`, `to` (полуинтервал `[from, to)`, по умолчанию последние 30 дней), `interval`
(`day|week|month`, по умолчанию `day`). Период проверяется: `from < to`, не больше 366 корзин и
не больше 731 дня (по дням — ≤ 366 дней), иначе `422 VALIDATION_ERROR`. Все ряды приходят с
ПОЛНЫМИ корзинами — сервер досыпает нули, клиент ничего не достраивает. Каждый агрегат кэшируется в Redis (TTL 300 с, ключ
`analytics:platform:<имя>:<параметры>`).

- `overview` — плитки: вузы по статусам, всего пользователей, жалоб в очереди, медиана времени
  разбора жалобы (за 30 дней + предыдущие 30 для дельты), DAU/WAU; спарклайны за 14 дней.
- `users-growth` — новые регистрации по корзинам, три группы ролей (`students` = STUDENT+STAROSTA,
  `teachers`, `staff`).
- `active-users` — `dau`/`wau` по `COUNT(DISTINCT audit_logs.user_id)`. Источник — журнал аудита,
  а НЕ `users.last_seen_at`: последнее поле перезаписывается при каждом уходе в оффлайн и
  исторического ряда не даёт. Считаются пользователи, чьи действия попадают в аудит.
- `universities-size` — по каждому вузу (≤ 200, крупнейшие первыми) студенты (со старостами) /
  преподаватели / всего, факультеты, группы, аудитории, плюс `name`/`shortName`/`status`/`city`,
  одним SQL; `totals` — итоги по всей платформе. На нём строится страница «Статистика платформы»
  (заменяет прежний N+1).
- `complaints-flow` — `created`/`resolved` по корзинам (обе величины — счётчики, одна ось).
- `complaints-latency` — распределение `resolved_at − created_at` по неравным корзинам
  (`lt1h`,`lt4h`,`lt1d`,`lt3d`,`lt7d`,`gte7d`) + медиана в часах (`percentile_cont`).
- `invites-funnel` — конверсия в регистрацию (`USED`/всего, проценты), разбивка по статусам и
  ряд статусов по корзинам.
- `activity-heatmap` — сетка 7×24 событий аудита, `cells[dow][hour]`, `dow` 0 = понедельник,
  плюс `days[dow]` — сколько календарных ДАТ этого дня недели попало в период, и `tz` эхом.
  Часы раскладываются в зоне query-параметра **`tz`** (IANA-имя, по умолчанию `UTC`): единого
  локального часа у платформы нет (у вузов свои зоны), поэтому берётся зона смотрящего —
  «пик в 18 UTC» для Алматы это 23:00, и без перевода картина рабочего дня сдвинута на сутки.
  `days` — делитель: в 30-дневном окне понедельников пять, а суббот четыре, и без него
  «в субботу меньше» означало бы лишь «суббот было меньше». Дашборд строит на этом суточный
  профиль (будни / выходные, среднее за день) и ряд по дням недели.
- `top-actions` — топ действий аудита за период (`limit` 1…20, по умолчанию 8).

Без новых моделей — агрегация поверх `User`/`University`/`Complaint`/`Invite`/`AuditLog`.

**Выгрузки и проверка документов** — `GET /verify/:code` (**публ.**, лимит 20/мин; отвечает только для справок — рабочие выгрузки по коду не раскрываются) · `GET /me/export?locale=` (машинная выгрузка СВОИХ персональных данных одним файлом JSON, Ф14.6; лимит 3/час с пользователя). Архив собирается из двадцати четырёх источников — учётка и профиль, файлы, посты и комментарии, свои сообщения, документы, оценки, посещаемость, сдачи заданий, результаты экзаменов, заявки, события, портфолио, друзья, уведомления, выданные приглашения, сторисы со своими просмотрами, реакциями и голосами в опросах, и журнал действий. У сторис в архив идёт признак `hasMedia`, а не идентификатор файла: сам файл лежит в разделе `files`, владелец у него тот же. Каждый раздел несёт `count` и `truncated`: потолок 5000 строк (журнал — 2000) не прячется, а объявляется. НЕ выгружаются никогда: хэш пароля, секрет и резервные коды 2FA, refresh-сессии, токены приглашений, полный номер документа (только `numberLast4`) и чужие данные — из переписки лишь свои сообщения, из дружбы имя друга без контактов. Событие пишется и в `AuditLog`, и в журнал `DocumentExport`. Всё, что пользователь скачивает, несёт происхождение: метаданные файла (`Title`/`Author=StudentHub`/`Creator=StudentHub v{версия}`/`Producer=StudentHub — {домен}`), видимая шапка «Сформировано {дата, время, таймзона} · Пользователь: {ФИО}», колонтитул с доменом и «стр. N из M», единое имя файла `studenthub_{вид}_{YYYY-MM-DD}.{ext}` и `Content-Disposition` с обеими формами имени (RFC 5987). Собирает это `ExportBrandingService` (`common/export`) — константы в контроллерах запрещены: домен временный, и переезд обязан быть правкой одной переменной. Язык подписей — `?locale=ru|kk|en` (на бэкенде i18n-слоя нет, словарь брендирования живёт в модуле; значения из БД при этом не переводятся).

Excel: книга из двух листов — **«Данные» первым** (таблица строго с A1, заголовки в первой строке, автофильтр, именованный диапазон `StudentHub_Data`) и «Инфо» вторым (система, домен, тип отчёта, дата с таймзоной, кто выгрузил, версия, фильтры). Шапку над таблицей не ставим: она ломает любой импорт «первая строка = заголовки», а `read_excel` без указания листа берёт первый. Закрепление строки в SheetJS 0.18.5 при записи не поддерживается — вместо него автофильтр. В CSV листов нет, поэтому происхождение несут только имя файла и журнал.

Журнал `DocumentExport`: `shortId` (8 символов, алфавит без 0/O и 1/I/L — код читают с бумаги), `userId`, `kind`, `format`, `params` (условия выборки, без ПД), `rows`, `ip`, `userAgent`, `createdAt`, `revokedAt` + реквизиты официального документа снимком на момент выдачи (`subjectName`, `documentNumber`, `issuerName`). Отдельно от `AuditLog` по двум причинам: там нет публичного идентификатора, и cron `cleanAuditLogs` чистит записи старше 90 дней — а выданную справку проверяют годами. Сбой записи журнала **не** отменяет рабочую выгрузку (принцип `AuditService`), но **отменяет** выдачу официального документа.

Страница проверки отвечает на один вопрос — «документ настоящий и действует?». Отдаёт тип, номер, кем выдан, дату, статус `VALID|REVOKED` и ФИО в виде «Фамилия И.О.»: код подбираем, и раздавать по нему полные данные нельзя. Ответ на «кода нет» и на чужой вид выгрузки одинаковый. Отзыв — `POST /applications/:id/results/certificate/revoke`: документ на руках не изымается, меняется только статус в журнале. Рабочие выгрузки в журнале тоже есть, но зелёной отметки не получают — страница говорит «служебная выгрузка, не официальный документ». Для казахстанской ЭЦП это основной путь проверки для человека: обычные читалки PDF ГОСТ-подпись не понимают и показывают «подпись недействительна».

**Чаты** — `GET|POST /chats` (список: cursor-пагинация `?cursor=&limit=` (limit ≤ 200, дефолт 100), порядок `updatedAt desc, id desc`; «закреплённые сверху» собирает клиент по `pinnedAt` поверх всех страниц — внутри одной страницы сквозной порядок не получить. Отправка троттлится 20/10с на пользователя (`RATE_LIMIT`); счётчик в Redis (`chat:flood:<userId>`, INCR+EXPIRE), поэтому лимит общий для всех инстансов и самоочищается. Все пять путей отправки (WS-сообщение, multipart, опрос, пересылка, «поделиться постом») проходят одну проверку `assertCanSend`: антифлуд + личная блокировка + потолок непринятого запроса (§50). До этого пересылка и share шли мимо и обходили и блокировку, и лимит. `POST /chats` с `type=PRIVATE` и собой в `memberIds` → `400 VALIDATION_ERROR`, несуществующий собеседник → `404`. Авточаты и личный чат пары создаются под транзакционным advisory-локом по ключу будущего чата; накопленные ранее дубли не склеиваются, берётся самый ранний. Сообщение с вложениями создаётся только после приёма всех файлов, одной транзакцией с привязкой; непривязанные вложения ночная чистка не трогает первый час. Последнее сообщение в `GET /chats` и в очереди поддержки читается отдельным запросом (`LATERAL … LIMIT 1`), а не всей историей чатов. Превью ссылок — без картинки (`linkPreview.image = null`). Список чатов отдаёт `avatarUrl` (для PRIVATE — аватар собеседника), `unreadCount`, `pinned` (закреплённые сортируются сверху), `isOwner`, `isAdmin`, `blocked`/`blockedBy`; `GET /chats/:id/members` — `banned` и `isAdmin`. Список чатов отдаёт также `requestIncoming`/`requestOutgoing` (§50). Модель: `Chat.avatarUrl/createdById/lastSeq/requestPendingForId/description`, `Message.seq` (монотонный номер внутри чата, уникальный `[chatId, seq]`; аллокатор — атомарный инкремент `Chat.lastSeq`), `ChatMember.bannedAt/isAdmin/clearedAt/clearedRanges/pinnedAt/muteImportantOnly`, модели `UserBlock`, `ChatFolder`/`ChatFolderItem` (§2). Текстовые сообщения/typing/статусы/ответы (`replyToId`) — через WS (`ChatGateway`). Вложения — REST: до `FILE_UPLOAD.DIRECT_UPLOAD_THRESHOLD_BYTES` (10 МБ) multipart-запросом (`POST /chats/:id/messages`), больше — прямой загрузкой в хранилище мимо API: `POST /chats/:id/attachments/presign` (одиночный PUT) либо `POST /chats/:id/attachments/multipart/start|urls` (файлы от 50 МБ, части по 10 МБ), а затем `POST /chats/:id/messages/uploaded` с ключами объектов — там же сервер собирает многочастные и привязывает файлы к сообщению. Пара presign/multipart своя, а не общая из `/files`: членство в чате проверяется на каждом шаге. Бакет `chat-media`, приватный. Вложения чата — единственное место, где принимаются архивы (ZIP, RAR, 7z, GZ, TAR, BZ2, XZ, до 500 МБ; см. «Файлы»). Системные сообщения группы (§20): `Message.systemType` (member_added/member_removed/member_left/admin_granted/admin_revoked/title_changed/avatar_changed/message_pinned/owner_changed) + `systemMeta` {targetName?, title?}; эмитятся `message:new` при событиях состава/названия/аватара/админа/владельца/закрепления; текст рендерит клиент по типу. Опросы: `ChatPoll`/`ChatPollOption`/`ChatPollVote` (§38, WS `poll:updated`). `GET /chats/saved` (§15: личный self-chat «Сохранённые» — `ChatType.SAVED`, единственный участник; найти/создать). Заводится и сам, вместе с остальными авточатами, — единственный, который положен всем ролям без исключения, включая платформенные и работодателя: у них нет ни группы, ни факультета, ни вуза. Ответ с цитатой фрагмента: `Message.replyQuote` — копия выделенного куска (не смещения: оригинал могут отредактировать), допустима только вместе с `replyToId`. Тихая отправка: `Message.silent` — сообщение доставляется как обычно, уведомления и push по нему не создаются. Спойлер (§34): `File.spoiler` (multipart-поле `spoiler` в `POST /chats/:id/messages` помечает все вложения, `spoilerIndexes` — номера отдельных вложений в порядке отправки, `«0,3»`; клиент размывает до клика). Два поля, а не одно: в альбоме из десяти снимков скрыть могут один, и общим флагом это не выражается; номера вне диапазона игнорируются. Отправка «без сжатия» (§9): `File.asDocument` (multipart-поле `asFiles` в том же маршруте помечает все вложения сообщения) — получатель видит строку файла с расширением и размером, а не превью, даже если mime картиночный. Флаг отправителя, а не свойство байтов: один и тот же снимок можно послать превью или документом, и показать нужно ровно выбранное. Помечаются все вложения сообщения разом, потому что способ отправки выбирается один раз на отправку. Размеры изображения: `File.width`/`File.height` заполняются при загрузке по содержимому (sharp читает заголовок) и приходят в `media` каждого сообщения — клиент резервирует под снимок точное место и держит скелетон той же формы, пока идут байты; у видео, документов и вложений старше этих полей — `null` (клиент рисует усреднённую заглушку). · Пользовательские группы: `POST /chats` с `type: GROUP` и `POST /chats/:id/members` проверяют каждого участника по правилам личного чата (живой и не заблокированный, без личной блокировки между сторонами, свой вуз или дружба; платформенным ролям — любой; работодатель чаты не создаёт и в группы не добавляется) · Ссылка-приглашение — код, а не id чата: `GET /chats/:id/invite` (админ группы; код выдаётся при первом запросе) · `POST /chats/:id/invite/reset` (новый код, прежняя ссылка гаснет; код сменяется и сам при исключении и бане участника) · `POST /chats/:id/join { code }` (неверный код → `404` как несуществующий чат, забаненный → `403`; вступление по ссылке и бан дают служебные сообщения `member_joined`/`member_banned` и события `chat:member-added`/`chat:member-removed`, повторы идемпотентны) · Уведомление о новом сообщении — имя отправителя и нейтральный текст (`chats.message.body`), без содержания сообщения (docs/PERSONAL_DATA.md §3) · Ссылка на вложение удалённого сообщения или очищенной «у себя» истории не выдаётся.

**Жалобы** — `POST /complaints` (роли-заявители — `COMPLAINT_REPORTER_ROLES`, 10/час; открытая жалоба того же автора на ту же цель → `409`) · `GET /complaints` (Moderator+, scope; фильтры `status/priority`, offset-пагинация (`limit` ≤ 200) + сортировка `?sort=priority|createdAt|status|targetType&order=asc|desc`; порядок по умолчанию — очередь: необработанные → приоритет HIGH раньше LOW → свежие раньше) · `GET /complaints/:id` · `GET /complaints/:id/messages` (доступ к чату по жалобе, пишется в аудит) · `PATCH /complaints/:id/resolve` (DELETE_CONTENT / BLOCK_USER / WARN_USER / DISMISS)

*Разбор.* `PATCH /complaints/:id/resolve` сначала условно захватывает жалобу (`PENDING`/`REVIEWING`): параллельное или повторное решение → `409`, мера применяется ровно один раз. Принимает `applyToDuplicates` — закрыть тем же статусом все необработанные жалобы на ту же цель в scope решающего (дубли получают ту же резолюцию, их авторы уведомляются). Побочное действие (снять контент, заблокировать) выполняется РОВНО ОДИН раз: вторая блокировка того же человека записала бы в журнал событие, которого не было. `PATCH /complaints/:id/reopen` возвращает разобранную жалобу в очередь и стирает решение, но **побочные действия не отменяет**: снятый контент не возвращается, блокировка снимается отдельно. `GET /complaints/:id` отдаёт `targetReports` — сколько всего жалоб на ту же цель от разных авторов; число отличает единичную обиду от травли — и `targetOwnerId`: кто отвечает за цель. В жалобе на пост или сообщение автора не видно, а блокируют человека; у снесённой цели поле приходит `null`, и карточка нарушителя просто не показывается.

*Квитирование.* `PATCH /complaints/:id/take` (Moderator+, `@MiniAllowed()`) ставит `REVIEWING` и запоминает, кто взял (`reviewing_by_id`). Уведомление о срочной жалобе уходит всей команде, и без отметки двое открывают одно и то же, а третья жалоба не достаётся никому. Перехватить чужую нельзя: условие `reviewingById: null` стоит в самом запросе, два одновременных «беру» не победят оба; разобранную жалобу `take` не берёт. Возврат в очередь (`reopen`) отметку снимает. То же действие делает кнопка под уведомлением в Telegram (см. «Вебхук бота»).

*Вебхук бота.* `POST /telegram/webhook` — **публичный** маршрут: Telegram приходит без нашего токена, и иначе быть не может. Защита одна — секрет `TELEGRAM_WEBHOOK_SECRET`, который бот присылает в заголовке `x-telegram-bot-api-secret-token` (ставится при `setWebhook`); секрет не задан — маршрут отвечает `200` и не делает ничего, потому что открытая ручка без проверки хуже её отсутствия. Ответ всегда `200`: обновление, на которое не ответили, Telegram повторяет часами и в итоге отключает вебхук. Из тела запроса берётся ТОЛЬКО `telegram_id` нажавшего; роль, scope и права читаются из `telegram_accounts` и `users` — иначе достаточно было бы прислать «я админ» вместе с нажатием. Удалённый или заблокированный аккаунт бот не узнаёт, а при `TWO_FACTOR_ENFORCE` — и сотрудника без включённой 2FA. Обрабатываются два вида обновлений. `callback_query` с `take:ticket:<id>` или `take:complaint:<id>` — в ответ уходит всплывающая подсказка и снимается кнопка. И `message` с командой в ЛИЧНОЙ переписке: `/start` и `/help` (что это за бот и список команд), `/queue` (жалоб в очереди, открытых обращений, возраст самого старого), `/digest` (та же сводка, что уходит раз в сутки, но по запросу), `/duty` (кто дежурит, кто следующий, тихие часы и заглушённые категории), `/status` (идут ли техработы, отвечают ли база, Redis и хранилище — проверки живые, а не из кэша сторожа), `/me` (роль написавшего, дата привязки Telegram и дежурит ли он сейчас — уведомления молчат и в тихие часы, и когда дежурит другой, и когда привязки нет, а выглядит это одинаково).

Команды отвечают **числами и состоянием платформы, но не содержимым**: ни текста жалобы, ни переписки поддержки, ни имён тех, о ком жалуются, — то же правило, что у исходящих уведомлений (§11.3). В группе бот молчит совсем: туда рядом с сотрудником может попасть посторонний. Непривязанному Telegram уходит один и тот же ответ «это служебный бот, привязка — в Настройках», по которому нельзя понять даже, есть ли на платформе очередь; данные для него не запрашиваются вовсе. Кнопка «Беру в работу» появляется под уведомлением только если секрет настроен: кнопка, нажатие которой некому принять, молча ничего не делает.

*Профиль бота.* При старте API бот сам рассказывает Telegram о себе: `setMyCommands` (меню команд в личной переписке), `setMyDescription` (текст на пустом экране до первого `/start`) и `setMyShortDescription`. Список команд один на три места — справку, меню и разбор сообщения; разойдясь, меню предлагало бы команду, на которую бот молчит. Вызовы уходят только когда заданы и `TELEGRAM_BOT_TOKEN`, и `TELEGRAM_WEBHOOK_SECRET`: без вебхука сообщения до API не доходят, и меню обещало бы ответ, которого не будет. Старт API их не ждёт и от их неудачи не зависит.

*Шкала решений.* `WARN_USER` — промежуточная мера между «нарушения нет» и блокировкой: до неё на первый грубый комментарий приходилось выбирать между «ничего» и отключением от платформы. Предупреждение не трогает ни контент, ни доступ; человеку уходит уведомление о самом факте, а внутренний комментарий модератора ему **не пересылается** — его писали не нарушителю. Запись ложится в `moderation_warnings`, а не в `AuditLog`: журнал чистится ежемесячно (`cleanAuditLogs`), а «второе предупреждение за месяц» и «первое за два года» — разные случаи, и различает их только сохранённая история. Кода 2FA предупреждение не требует.

*Срок блокировки.* `BLOCK_USER` принимает `blockDays` (1…365) — `PATCH /users/:id/block` тоже. Срок пишется в `users.blocked_until` и считается от момента решения: «на семь дней», выданное вечером, кончается вечером. Без срока блокировка бессрочная, как была. Снимает её крон `liftExpiredBlocks` (каждые 5 минут) — тем же способом, каким снимаются техработы; разблокировка руками срок стирает, иначе одна и та же блокировка «снималась» бы дважды. Потолок в год намеренный: всё, что дольше, по смыслу и есть «навсегда», а промах в поле не должен создавать блокировку до 2147 года.

*Жалоба из обращения.* `POST /complaints/from-support` (`PLATFORM_ADMIN`/`PLATFORM_MODERATOR`, `@MiniAllowed()`; тело `{ chatId, targetId }`) заводит жалобу на человека по обращению в поддержку. Люди жалуются на других людей через поддержку — адрес известен, а кнопку «пожаловаться» рядом с обидчиком ещё надо найти; до этой ручки путь кончался тупиком. **Автором жалобы остаётся автор обращения**, а не модератор: жаловался он, и очередь должна показывать именно это — иначе по статистике половину жалоб на платформе подаёт поддержка. Текст берётся из первого сообщения обращения (его собственные слова, до 2000 символов). Тип цели не спрашивается: через поддержку жалуются на людей, а `targetId` поста в переписке всё равно нет. Открытая жалоба того же автора на ту же цель → `409`, как и у `POST /complaints`.

*История по цели.* `GET /complaints?targetId=` — все жалобы на один объект или человека. Единичная обида и травля в очереди выглядят одинаково; разводит их только список прошлых разборов.

*Накопление очереди.* Ежечасный cron `alertQueueBacklog` (`CleanupService`) сигналит в Telegram, когда необработанных жалоб становится больше 20, и молчит следующие 6 часов: разгрести два десятка за час нельзя, а пять одинаковых сообщений подряд учат их не читать. Как только очередь опускается ниже порога, пауза снимается — следующий всплеск не пропустится.

**Приоритет жалобы** (`Complaint.priority`, enum `ComplaintPriority` = `HIGH|MEDIUM|LOW`) выводится из категории цели и записывается при создании — клиент его не присылает, иначе жалующийся сам назначал бы себе «срочно». Правило одно для API и UI — `complaintPriorityFor` в `packages/shared-schemas`: `USER` и `MESSAGE` → HIGH (страдает конкретный человек: травля, угрозы, спам в личку), `POST` и `STORY` → MEDIUM (публичный контент, не адресован одному человеку), `COMMENT` → LOW (локальная реплика). Порядок значений enum = порядок разбора, поэтому `ORDER BY priority ASC` даёт HIGH сверху. Индекс `@@index([status, priority])`.

**Аудит** — `GET /audit` (Moderator+/Admin, scope: платформа — всё, админ вуза — свой вуз, модератор — свои действия; фильтры `action/userId`, offset-пагинация (`limit` ≤ 200) + сортировка `?sort=createdAt|action|entity|userId&order=asc|desc`, по умолчанию `createdAt desc`)

**Мой день (BFF)** (Unified UX, PR-1/PR-9 — см. `docs/UNIFIED_UX.md`) — `GET /me/today` (операционный экран «Сегодня»/Action Center по роли: `{ role, date, timezone, pairs, scheduleChanges, applications, events, assignments, notifications }`). Агрегирует существующие доменные сервисы (Schedules/Events/Notifications/Assignments/Applications) по scope роли, чтобы клиент делал один запрос вместо нескольких; заявки — только студенту/старосте; `assignments` — до 50 заданий со сроком раньше чем через 9 суток, актуальные сверху; для `TEACHER` в `pairs` входят и чужие пары, которые он сегодня ведёт по замене; каждый источник устойчив к сбою (пустой дефолт). Прежняя лента активности `GET /me/activity` убрана.

**Карьера (Ф18)** — единственная зона платформы с внешним участником (`EMPLOYER`), поэтому правила доступа тут свои.

*Область данных карьерного центра.* Разделы вуза (допуск компаний, модерация вакансий, события, метрики) работают в scope ОДНОГО вуза. У сотрудника он берётся из токена; переданный в запросе чужой `universityId` → 403 `WRONG_SCOPE`. Платформенные роли своего вуза не имеют и указывают его параметром `?universityId` (в решениях — полем тела): без него — 403 `WRONG_SCOPE` «Выберите университет». Прав параметр не добавляет: платформенные роли и так видят любой вуз, он лишь выбирает, какой показать. Единая реализация — `career-scope.ts` (`resolveUniversityScope`), на фронте вуз живёт в query-параметре страницы и выбирается селектором в шапке раздела.

*Компания.* `POST /career/companies/signup` (публ., throttle 5/15 мин) — саморегистрация работодателя: создаёт `Company` в статусе `PENDING_EMAIL` и пользователя с ролью `EMPLOYER`, пустым scope и `profileVisibility = PRIVATE`. Вход `EMPLOYER` ждёт `Company.status ≠ PENDING_EMAIL`: до подтверждения почты вход, QR, 2FA и refresh отвечают `403 EMAIL_NOT_VERIFIED` (§8.2). Неподтверждённые компании старше 30 дней вместе с аккаунтами участников удаляет cron `purgeUnverifiedEmployers` — только при `CLEANUP_PURGE_UNVERIFIED_EMPLOYERS=true` (§10.2). Это единственное исключение из правила «регистрация только по инвайтам» (см. §2.1 и `BACKEND_RULES §19` п. 9). `POST /career/companies/verify-email` (публ.) — подтверждение по ссылке из письма; токен хранится хэшем. `POST /career/companies/resend-verification` (публ., throttle 3/15 мин, `{ email }`) — новая ссылка взамен истёкшей, прежняя гаснет; ответ `202 { email }` одинаков для любого адреса (нет перебора). Далее `GET|PATCH /career/companies/me`, `GET /career/companies/me/access`, `GET /career/companies/me/universities`, `POST /career/companies/me/access` (запрос допуска к вузу) — все `EMPLOYER`.

*Допуск к вузу.* `GET /career/university/companies` + `PATCH /career/university/companies/:id` (решение — `PLATFORM_ADMIN`, `UNIVERSITY_ADMIN`; чтение — ещё `PLATFORM_MODERATOR`/`UNIVERSITY_MODERATOR`/`DEAN`) — очередь заявок компаний и решение по ним. Статусы `CompanyUniversityAccess.status` = `REQUESTED|APPROVED|REJECTED|REVOKED`, у одобренного возможен `expiresAt`. Решение и повторная заявка — условный `UPDATE`, гонка → `409`. **Отзыв (`REVOKED`) каскадом закрывает вакансии этой компании в этом вузе**: тем же транзакционным шагом все `VacancyUniversityReview` компании по этому вузу (и `APPROVED`, и `PENDING`) переводятся в `REJECTED` с причиной «Университет отозвал допуск компании». Вузы, где допуск остался, не затрагиваются. Отдельного статуса `REVOKED` у решения по вакансии нет намеренно — вернут допуск, компания публикует заново, вуз рассматривает с нуля. Истёкший допуск ежечасно переводится в `REVOKED` с причиной «Истёк срок допуска» и тем же каскадом на вакансии (cron `expireCompanyAccess`, §10.2); `expiresAt` сохраняется. Доступ закрывается по сроку сразу — срок проверяется в каждом запросе, cron лишь приводит состояние в порядок. Уведомления: заявка на допуск → `UNIVERSITY_ADMIN` вуза; решение по допуску и по вакансии, новый отклик (свёрнуто по вакансии) → участникам компании.

**Ключевое правило модуля:** компания видит студентов **только тех вузов, где её допуск активен прямо сейчас**. Набор вузов НЕ кладётся в JWT: отзыв допуска обязан действовать немедленно, а 15 минут доступа к чужим студентам после отзыва — это инцидент, а не задержка. Поэтому набор читается из БД на каждый запрос (`CareerAccessService`), с минутным кэшем в Redis и точечным сбросом при любом изменении допуска; кэш — ускорение, а не источник истины.

*Вакансии.* Студенту и сотрудникам вуза (`TEACHER`, `DEAN`, `UNIVERSITY_ADMIN`, `UNIVERSITY_MODERATOR`) — `GET /career/vacancies`, `GET /career/vacancies/:id` (показываются только одобренные их вузом; платформенным ролям — витрина выбранного вуза по `?universityId`). Работодателю — `GET|POST /career/employer/vacancies`, `PATCH /career/employer/vacancies/:id` и переходы `POST :id/publish|pause|close` (`Vacancy.status` = `DRAFT|PUBLISHED|PAUSED|CLOSED`; граф `VACANCY_TRANSITIONS` в shared-schemas: `DRAFT → PUBLISHED|CLOSED`, `PUBLISHED → PUBLISHED|PAUSED|CLOSED`, `PAUSED → PUBLISHED|CLOSED`, `CLOSED` конечный). Правка содержательных полей одобренной вакансии (всё, кроме `deadline`) тем же транзакционным шагом возвращает её одобрения вузов в `PENDING`. Вузу — `GET /career/university/vacancies` + `PATCH :id` (модерация; чтение — ещё `DEAN`, решение — `UNIVERSITY_ADMIN`/`UNIVERSITY_MODERATOR` и обе платформенные роли; `VacancyUniversityReview.status` = `PENDING|APPROVED|REJECTED`; переходы `PENDING → APPROVED|REJECTED`, `APPROVED → REJECTED`; `APPROVED` — только при действующем допуске компании (`APPROVED` без истёкшего `expiresAt`), иначе `409`): вакансия видна в вузе только после одобрения **этим** вузом и только пока допуск компании в этот вуз действует — витрина, карточка, отклик и воронка идут через `vacancyVisibleWhere`/`applicationScopeWhere`.

*Профиль кандидата и согласия.* `GET|PATCH /career/profile` (`STUDENT`/`STAROSTA`) — `CareerProfile` с `visibility` = `HIDDEN|EMPLOYERS`, статусом поиска (`LOOKING|OPEN|NOT_LOOKING`), желаемыми позициями, форматами и вилкой. `POST /career/profile/consents` — согласия на передачу полей (`CareerConsent.field` = `GPA|PHONE|EMAIL`, общее или на конкретную компанию, отзывается). `GET /career/profile/candidates/:id` (`EMPLOYER`) отдаёт `gpa` и `phone` **только при активном согласии**, иначе `null` — это проверяется на уровне `select`/маппинга, а не скрытием в UI (§11).

*Резюме.* `GET|PATCH /career/resume`, `GET /career/resume/pdf` (`STUDENT`/`STAROSTA`) и `GET /career/resume/public/:slug` (публ.; резюме заблокированного пользователя → `404`) — публикация по ссылке включается самим студентом (`publishedAt` + `publicSlug`), контакты в публичной версии — по флагу `includeContacts`. Портфолио в публичной версии и в карточке кандидата для работодателя — только записи `PUBLIC`: `UNIVERSITY` значит «внутри вуза», а у работодателя вуза нет; `PRIVATE` видит только владелец (общее правило — `portfolioVisibilityWhere` в `portfolio.service.ts`).

*Отклики.* Студент: `GET|POST /career/applications`, `GET :id/history`, `POST :id/withdraw`. Работодатель: `GET /career/employer/applications`, `PATCH :id` (смена статуса). Воронка `CareerApplication.status` = `SUBMITTED|VIEWED|SHORTLISTED|INTERVIEW|OFFER|HIRED|REJECTED|WITHDRAWN`, каждый переход пишется в `CareerApplicationEvent`. Отзыв допуска вузом на уже поданные отклики не влияет: выборка откликов студента намеренно не фильтруется по решениям вуза, и в карточке остаются название компании, её `website` и полная история статусов — связь с работодателем вне платформы должна пережить решение вуза, иначе диалог обрывается на середине. Воронка компании показывает отклики из вузов с действующим допуском, а из остальных — только поданные до конца допуска.

*Прочее.* `GET /career/events` — карьерные мероприятия (все роли вуза и обе платформенные; вне карьерного центра — по аудитории события) (`Event.careerKind` = `CAREER_FAIR|WORKSHOP|INTERVIEW_DAY|COMPANY_PRESENTATION|HACKATHON`). `GET /career/analytics/university` (роли вуза, кроме `TEACHER`, и обе платформенные) и `GET /career/analytics/company` (`EMPLOYER`) — воронка и срезы; в метриках «студенты» = `STUDENT` + `STAROSTA`.

Сводка вуза (`GET /career/analytics/university`, кэш Redis 60 с, ключ `analytics:career:university:<id>`): `companies`/`vacancies` — решения по статусам; `funnel` — где отклики лежат **сейчас** (включая `REJECTED`/`WITHDRAWN`); `reached` — сколько откликов **дошло** до шага (`SUBMITTED|VIEWED|SHORTLISTED|INTERVIEW|OFFER|HIRED`, накопительно, по максимуму из текущего статуса и `CareerApplicationEvent`) — только на нём строятся воронка и `rates`, потому что группировка по текущему статусу теряет и найм, и отказ после интервью; `queue` — очередь и сроки (вакансий на модерации, возраст старейшей, медиана решения за 90 дней, заявки компаний, допуски с истечением в 30 дней, отклики без ответа дольше 14 дней); `weekly` — 12 недель (`submitted`/`interview`/`hired`); `skills` — топ-8 навыков «спрос вакансий, одобренных этим вузом, против предложения студентов». Ряды считаются в SQL (`date_trunc`/`generate_series`/`FILTER`/`unnest`), персональных данных нет.

Отчёт за период (`GET /career/analytics/university/report?period=month|quarter|year`, кэш Redis 5 мин, ключ `analytics:career:report:<id>:<period>`; `year` — **учебный** год с 1 сентября): `totals` — объём за период и за предыдущий той же длины (дельту считает экран); `timing` — медиана до первого ответа компании (`SUBMITTED → VIEWED`), медиана до найма и доля откликов без реакции; `funnel` — шаги за период и потери между соседними; `outcomes` — найм/отказ/отзыв/в работе; `faculties` — трудоустройство по факультетам **с порогом малых групп** (факультет меньше 5 студентов не показывается вовсе, число скрытых возвращается в `suppressed`); `graduates` — выпускной курс текущего учебного года; `companies` — топ-10 по найму; `vacancyCuts` и `salary` — снимок витрины на сегодня (занятость/формат/опыт/города, медианы вилок и ожиданий); `deadVacancies` — одобренные вакансии без единого отклика; `students` — корзины `readinessScore`, статусы поиска, опубликованные резюме, открытые профили. Ряда по мероприятиям в отчёте намеренно нет: `EventParticipant` фиксирует только запись, явки в модели не существует, а регистрации под видом посещаемости врали бы в отчёте.

`GET /career/analytics/university/report/export?format=xlsx|csv&locale=` — тот же отчёт файлом через общий `ExportBrandingService` (`ExportKind = 'career-report'`): лист «Данные» в виде «раздел · показатель · значение · справочно», лист «Инфо» с происхождением, запись в `AuditLog` и в реестр выгрузок.

**Релизы** (окно «Что нового», `docs/RELEASE.md`) — `GET /releases/me` (до какой версии пользователь дочитал: `{ version, seenAt, accountCreatedAt }`) · `POST /releases/seen` (`{ version }` — отметить прочитанным). Обе доступны любой аутентифицированной роли, `userId` берётся из JWT. Модель `ReleaseView` (`userId` — первичный ключ, `version`, `seenAt`): одна строка на пользователя, тексты релизов в БД не хранятся — они лежат в бандле web (`entities/release/model/notes.json`), иначе нота обгоняла бы сборку у установленного PWA. Сравнение версий и решение «показывать/промолчать» — на клиенте; сервер отметку не оспаривает.

**Приход вуза** (§31) — заявка снаружи и мастер настройки внутри.

*Заявка.* `POST /demo-requests` (**публ.**, throttle 5/15 мин, всегда `202` с `{ email }`) · `POST /demo-requests/verify` (**публ.**, `{ token }` из письма). Публичная подача не создаёт ни аккаунта, ни вуза, ни доступа — только строку в очереди к человеку: правило «внутрь только по приглашению» не обходится. Ответ одинаков для новой и для повторной заявки с того же адреса, иначе форма превращается в способ узнать, подавал ли этот вуз заявку. Токен подтверждения хранится хэшем и гасится при первом переходе.

Повторная отправка с того же адреса разбирается по состоянию заявки. Заявка уже в очереди (`NEW`) — не делается ничего. Адрес не подтверждён, а ссылка ещё жива — письмо уходит **заново, с новым токеном**: второй раз форму отправляют именно потому, что письма не увидели, и молчание в этом месте читается как «форма сломана». Между переотправками пауза 5 минут: адрес в форме пишет кто угодно, и без неё повтор превращается в способ засыпать чужой ящик. Открытой при этом считается только заявка с НЕИСТЁКШЕЙ ссылкой — иначе строка `PENDING_EMAIL` занимала бы адрес навсегда, и человек, до которого письмо не дошло, терял бы возможность подать заявку с него вообще.

Неподтверждённые заявки старше 7 дней удаляет ежедневный cron `purgeUnconfirmedDemoRequests` (04:30). Срок больше суточного срока ссылки: заявку могли подать в пятницу, а почту открыть в понедельник — переотправка письма до этого момента ещё доступна. Дальше хранить незачем, и дело не только в адресе: в заявке лежат настоящие персональные данные, а форму, которую не подтвердили, они пережить не должны. Решённые заявки не удаляются никогда — запись о том, кто и на каком основании получил доступ, переживает саму заявку.

*Очередь и решения* (`PLATFORM_ADMIN`) — `GET /demo-requests?status=&search=&page=&limit=` · `GET /demo-requests/:id` · `POST /demo-requests/:id/approve` · `POST /demo-requests/:id/reject`. `PLATFORM_MODERATOR` сюда не допущен: это решение о допуске организации, а не модерация контента. Одобрение — одна транзакция: условный перевод заявки `NEW → APPROVED`, `University` в статусе `PENDING`, `UniversityOnboarding` и обычный инвайт `UNIVERSITY_ADMIN` на подтверждённый адрес (`InviteService.createInTransaction`); сбой любого шага откатывает всё, письмо (одно, со ссылкой внутри) и аудит — после коммита. Отказ тоже условно из `NEW`. Повторное или параллельное решение по той же заявке — `409 CONFLICT`. `University.city` — код КАТО, свободный текст только у зарубежного вуза: при одобрении текст однозначного города заменяется кодом. Причина отказа — enum `DemoRejectionReason`, свободного текста в письме нет; `reviewNote` внутренняя и наружу не уходит.

*Мастер настройки* (`UNIVERSITY_ADMIN`, свой вуз из JWT) — `GET /onboarding` · `POST /onboarding/confirm-profile` · `POST /onboarding/skip` (`{ step }`) · `POST /onboarding/dismiss` · `POST /onboarding/launch`. Шаги и список пропускаемых заданы в `packages/shared-schemas` (`ONBOARDING_STEPS`, `SKIPPABLE_ONBOARDING_STEPS`): `profile → faculties → specialties → groups → rooms → terms → subjects → deans → launch`; пропустить можно только `specialties`, `rooms`, `subjects` — без факультетов и групп платформа не работает вообще. Пройденность шага считается по данным, а не хранится флагом (см. §6). `launch` переводит вуз только `PENDING → ACTIVE` (условная запись) и проверяет обязательные шаги на сервере, а не только кнопкой на фронте; из `ACTIVE` и `BLOCKED` — `409`: блокировку снимает только платформа. `canLaunch` = статус `PENDING` и пустой `blocking`.

**Пуши на устройства** — `POST /push/devices` (`{ token, platform: 'IOS' | 'ANDROID', appVersion? }`) · `POST /push/devices/remove` (`{ token }`). Обе под обычным guard'ом: токен устройства привязывается к вошедшему пользователю. Запись уникальна по токену, а не по паре с пользователем — одно устройство может сменить владельца (человек вышел и вошёл под другим аккаунтом), и пуши обязаны уйти за ним. Доставка — APNs по ключу p8 (`APNS_*`), транспорт на `node:http2` без внешней библиотеки; провайдерский токен кэшируется на 50 минут, иначе Apple отвечает `TooManyProviderTokenUpdates`. Ответ `410` или `BadDeviceToken` удаляет строку: приложение удалили или переустановили. Бейдж — число непрочитанных уведомлений, считается один раз на отправку. Без ключей отправка на устройства молчит, как Web Push без VAPID. Android — FCM HTTP v1 по сервисному аккаунту Firebase (`FCM_*`), тоже без библиотеки: JWT сервисного аккаунта обменивается на OAuth-токен Google, токен кэшируется на 50 минут. Транспорт выбирается по `platform` записи. Сообщение уходит data-only с приоритетом `high`: плашку собирает приложение — свой канал, переход по ссылке, язык. `UNREGISTERED` удаляет строку, как `410` у Apple.

Новая привязка устройства включает пользователю `NotificationSettings.pushEnabled` (флаг общий для браузера и телефонов, по умолчанию `false`, дефолт в схеме не меняется). Регистрация устройства и есть согласие: iOS отдаёт токен только после разрешения в системном диалоге, Android без разрешения плашку не покажет — как в вебе, где тумблер включается вместе с разрешением браузера. Новой считается привязка, когда токена не было или он был у другого аккаунта (установка, новый телефон, вход после выхода); подтверждение того же токена на каждом запуске приложения настроек не трогает, иначе выключенные пуши не продержались бы до следующего открытия. Цена решения: вход после выхода на том же телефоне снова включает пуши — «выключил сам» от «ещё не трогал» без отдельного поля не отличить. Мобильные клиенты читают и пишут настройки теми же полями, что и веб (`pushEnabled`, `emailEnabled`, …): схема `PATCH /notifications/settings` строгая, чужое поле — `400`. `systemEnabled` выключает только `SYSTEM`-job'ы `friend-request`, `friend-accepted` и `chat-request`.

Каналы доставки: WS `notification:new` — онлайн-адресатам; Web Push и письмо-зеркало — только офлайн; push на телефоны (APNs/FCM) — независимо от онлайна. Свёрнутые уведомления (§10.1) несут `tag = collapseKey`: service worker — `tag` + `renotify`, APNs — `thread-id`, FCM — `data.tag`, так что плашки одного источника складываются в стопку. У APNs, FCM и Web Push таймаут отправки 10 с. Токены телефонов, не подтверждённые 90 дней, и адреса пушей удалённых аккаунтов убирает cron `purgeDeviceTokens` (§10.2).

**Версия мобильного клиента** — `GET /client-version?platform=ios|android` (**публ.**) → `{ platform, minimumVersion, storeUrl? }`. Публичный намеренно: приложение спрашивает это до входа, иначе человек со старой сборкой упирался бы в неработающую форму входа и не узнал бы, что дело в версии. Режим техработ маршрут не закрывает (`@MaintenanceExempt`) — во время остановки платформы узнать про обновление нужно тем более. Значения берутся из `IOS_MIN_SUPPORTED_VERSION` и `IOS_STORE_URL` (для Android — `ANDROID_MIN_SUPPORTED_VERSION` и `ANDROID_STORE_URL`; планки у платформ свои, релизы выходят в разное время): меняет их человек при релизе, истории изменений не требуется, а таблица ради одной строки добавила бы миграцию и способ заблокировать всех пользователей опечаткой в проде. Сравнение версий — на клиенте: он всё равно обязан работать без сети и помнить последний ответ. Без `storeUrl` кнопки «Обновить» на экране нет — кнопка, ведущая в никуда, хуже её отсутствия.

Свою версию клиент присылает заголовком `X-Client-Version` (`ios/1.2.0+34`) на **каждый** запрос. Он попадает в строку лога запроса и тегом `client_version` в Sentry: у нативного приложения в поле одновременно живут все сборки, которые люди не обновили, и без этого ошибка старой сборки выглядит как общая авария. Значение приходит снаружи, поэтому в лог уходит обрезанная до 64 символов строка из безопасных символов.

**Служебное** — `GET /health` (публ.; формат terminus, по `database`/`redis`/`minio` только `status` — причина отказа пишется в журнал; каждая проба ограничена 3 с, пробы идут параллельно) · `GET /api/docs` (только dev)

Пагинация: списки контента и сообщений — cursor (`?cursor=&limit=`, `limit ≤ 50`); административные таблицы — offset (`?page=&limit=`, `limit ≤ 100`).

## 9. WebSocket

Транспорт socket.io, единый `ChatGateway`. Аутентификация — JWT в `socket.handshake.auth.token`.

### 9.1 Клиент → сервер

| Событие | Payload |
|---|---|
| `chat:join` | `{ chatId }` — только после серверной проверки членства (забаненного не пускает; при исключении, бане и выходе сокеты пользователя выводятся из комнаты) |
| `chat:leave` | `{ chatId }` |
| `message:send` | `{ chatId, content, replyToId? }` — `content` обрезается по краям и чистится от невидимых символов до проверки длины; пустой после этого текст отклоняется |
| `message:edit` | `{ messageId, content }` — `content` по тем же правилам; только действующим участником |
| `message:delete` | `{ messageId }` — только действующим участником |
| `message:read` | `{ chatId, messageId }` — «прочитано до этого сообщения»: `ChatMember.lastReadAt` становится временем сообщения (не текущим), только вперёд — более старое прочтение отметку не откатывает. Клиент шлёт последнее сообщение, прошедшее через экран, не чаще раза в 800 мс, и только из видимой вкладки; непрочитанным остаются чужие сообщения новее отметки |
| `chat:action` | `{ chatId, action }` — что человек делает сейчас; `action: null` — закончил. Значения: `TYPING`, `RECORDING_VOICE`, `UPLOADING_PHOTO`, `UPLOADING_VIDEO`, `UPLOADING_FILE`. Отправитель повторяет подтверждение не чаще раза в 3 с |
| `typing:start` / `typing:stop` | `{ chatId }` — то же самое для клиентов прошлой версии: сервер разворачивает их в `chat:action` с `TYPING` и `null` |
| `auth:refresh` | `{ token }` — обновление токена без разрыва соединения; токен другого пользователя или токен мини-аппа (`client: 'mini'`) рвёт соединение |

Лимиты на сокет: события чата — 120 подряд / 20 в секунду; `chat:action` и `typing:*` — 20 подряд / 2 в секунду. Сверх лимита событие отбрасывается, клиенту один раз на серию уходит `error { event, code: 'RATE_LIMIT' }`; `chat:leave` без лимита. `chat:action` в чате больше 64 участников принимается только от участника. В режиме техработ `message:send|edit|delete` неплатформенных ролей отвечают `error { code: 'MAINTENANCE' }` (§8.3 «Состояние платформы»).

### 9.2 Сервер → клиент

| Событие | Payload |
|---|---|
| `message:new` · `message:updated` | `{ message, chatId }` |
| `message:pinned` · `message:unpinned` · `message:reaction` | `{ message, chatId }` |
| `message:deleted` | `{ messageId, chatId }` |
| `presence:changed` | `{ userId, online }` — собеседникам личных чатов в `user:{id}` и участникам общих чатов в `chat:{id}`, а не всему вузу (§3.7) |
| `message:read` | `{ messageId, chatId, userId, readAt }` — в комнату `chat:{id}`; `readAt` — действующая отметка читателя (время прочитанного сообщения) |
| `chat:read` | `{ chatId, readAt }` — читателю в его личную комнату `user:{id}`: счётчик непрочитанного в списке и сводка навигации обновляются и на других его устройствах, где чат не открыт. Приходит и после собственной отправки: отправка — тоже прочтение (как в Telegram), отметка отправителя встаёт на его сообщение, включая системные события, которые он вызвал. Вступивший в группу (участник, приглашение по ссылке, официальный чат) получает отметку на момент входа — история до него непрочитанным не считается |
| `chat:activity` | `{ chatId }` — тихий сигнал «обнови список чатов» в личные комнаты `user:{id}` всех участников, **включая отправителя** (его список и другие устройства тоже должны показать новое сообщение — в том числе отправленное не из окна чата: «Поделиться профилем», пересылка, репост). Шлётся на новое сообщение, на системное сообщение и на правку или удаление последнего сообщения чата. Уведомления не создаёт |
| `chat:action` | `{ chatId, userId, action }` — в личные комнаты участников (`user:{id}`), чтобы подпись была видна и в строке списка чатов, а не только с открытым чатом. Веер ограничен 64 участниками (`TYPING_FANOUT_MAX`): в чате на сотни человек кто-то печатает всегда, строка перестала бы что-либо значить, а отправок было бы сотни каждые три секунды. Сверх потолка — в комнату `chat:{id}`. Членство отправителя проверяется тем же запросом, которым берутся получатели: адресация идёт мимо комнаты, и «я в неё вошёл» не защита |
| `typing:started` · `typing:stopped` | `{ chatId, userId }` — дубль `chat:action` для клиентов прошлой версии, только для `TYPING` и конца действия. Остальные действия старому клиенту не шлются вовсе: перевести он их не сумеет |
| `chat:updated` | `{ chat }` |
| `chat:member-added` | `{ chatId, user }` |
| `chat:member-removed` | `{ chatId, userId }` |
| `notification:new` | `{ notification }` |
| `schedule:changed` | `{ change, groupId }`; при удалении изменения — `{ change, groupId, removed: true }`; при правке или удалении пары активной версии — `{ change: null, groupId, pairId[, removed] }`. Уходит в `group:{id}` и в `user:{id}` основного и заменяющего преподавателей |
| `story:new` | `{ story }` |
| `application:updated` | `{ applicationId, status }` |

### 9.1a Действия в чате

Подпись «печатает…» обобщена до действия: `TYPING`, `RECORDING_VOICE`, `UPLOADING_PHOTO`,
`UPLOADING_VIDEO`, `UPLOADING_FILE` (контракт — `ChatActionSchema` в `@studenthub/shared-schemas`).
Это **не тип сообщения**: типа сообщения в модели нет вовсе, вид вложения выводится при рендере
из mime, имени файла (`voice-…`) и флага `asDocument`. Действие живёт секунды, в БД и в Redis
не попадает — только событие и память вкладки.

Время жизни держит получатель: подпись гаснет через 4 с без подтверждения, отправитель повторяет
его раз в 3 с. Поэтому «стоп» не обязателен — закрытая вкладка, разрыв связи и упавший сервер
гасят подпись сами, а `startedAt`/`expiresAt` в событии не нужны.

Набор текста подтверждается нажатиями и явного «стоп» не шлёт (кроме отправки сообщения и ухода
из чата). Запись голосового и загрузка вложения длятся сами, поэтому подтверждаются по таймеру и
всегда снимаются в `finally`. Загрузка сообщается не сразу, а через 400 мс: сжатый снимок
улетает за доли секунды, и подпись успела бы только мигнуть.

Текст собирает интерфейс: сервер шлёт только значение действия, i18n-ключи — `Chats.actions.*`
(мн. ч. по числу участников), `Chats.actionsNamed.*` (с именем, в групповых чатах) и
`Chats.actionsMany` (когда участники делают разное — перечислять их в одну строку негде).

### 9.2a Единый конверт `event` (Unified UX PR-8/#12)

Параллельно именованным событиям выше вводится **единый канал** `event` с конвертом
`{ type, entityId, version, ts, data }`, где `type` — `domain.entity.action`
(напр. `schedule.lesson.updated`, `notification.created`, `application.status.changed`,
`grade.published`). Контракт — `@studenthub/shared-schemas` (`RealtimeEnvelope`,
`REALTIME_CHANNEL`, `REALTIME_EVENTS`). Именованные события **не удаляются** — конверт
эмитится рядом (`RealtimeGateway.emitEventToUser/emitEventToRoom`), клиенты мигрируют
постепенно (`useRealtimeEnvelope(type, handler)`). Продублированы `schedule:changed`
→ `schedule.lesson.updated` и `notification:new` → `notification.created`. Реализованы
поверх конверта (без именованного дубля): **`application.status.changed`** (`{ status }` →
владельцу заявки при каждом переходе, вкл. запрос замены документа) и **`grade.published`**
(`{ columnId }` → каждому студенту с оценкой при публикации колонки журнала). Оба — точечно
в user-комнату, payload минимальный, без PII; клиент делает узкий `invalidateQueries`.

### 9.2b Одно соединение на все вкладки

Вкладки одного аккаунта выбирают мастера через `BroadcastChannel` (`shared/realtime/leader-election.ts`):
сокет держит только он, остальные получают события и отправляют свои `emit` через него по шине
(`realtime-bus.ts`). Потребители этого не видят — контекст в обеих ролях отдаёт `RealtimeClient` с тем
же API, что и раньше. Ключ канала включает id пользователя: вкладки разных аккаунтов соединение не
делят. Мастер ведёт рефкаунт комнат `chat:{chatId}` — `chat:leave` уходит на сервер, только когда
комнату отпустила последняя вкладка. Уход мастера (`pagehide`) или его молчание дольше 3 с запускают
перевыборы. Нет `BroadcastChannel` — каждая вкладка работает сама по себе, как до изменения.

### 9.2c Догон пропущенного после обрыва

События, прошедшие мимо отключённого клиента, никто не переприсылает. Вместо перезапроса страницы
истории чат-окно на `connect` забирает разницу: `GET /chats/:id/updates?since=<последний seq>`
(§8.3). `Message.seq` — монотонный номер внутри чата, выдаётся атомарным инкрементом `Chat.lastSeq`
в той же операции, что создаёт сообщение. Полный рефетч остаётся фолбэком: пустой кэш, ошибка
запроса или `overflow`. Остальные чаты по-прежнему обновляются одной инвалидацией списка.

### 9.4 Поток отправки сообщения

```
Клиент A: emit('message:send', { chatId, content })
  → ChatGateway: Zod-валидация payload + проверка членства в чате
  → prisma.message.create()
  → job 'new-message' в очередь notifications (для офлайн-участников)
  → server.to(`chat:${chatId}`).emit('message:new', { message, chatId })
  → NotificationsProcessor: Notification в БД → WS онлайн → email/push офлайн
```

## 10. Асинхронная обработка

### 10.1 Очереди (BullMQ + Redis)

| Очередь | Job'ы |
|---|---|
| `email` | `send-invite`, `send-notification` (офлайн-зеркало in-app уведомления), `send-company-verification`, `send-password-reset`, `send-two-factor-reset`, `send-demo-verification`, `send-demo-approved`, `send-demo-rejected`. Воркер — 5 job'ов одновременно |
| `file-processing` | `generate-thumbnail` (превью аватара: sharp, 128×128 WebP) |
| `link-preview` | `fetch-link-preview` (OG-превью первой ссылки сообщения, без картинки) |
| `media-image` | `process-media` (изображение: WebP-копии и LQIP), `copy-media-variants` (пересылка: копия готовых вариантов) — конкурентность `MEDIA_IMAGE_CONCURRENCY` |
| `media-video` | `process-media` (видео: постер, HLS 360–1080, длительность; 2 попытки) — конкурентность `MEDIA_VIDEO_CONCURRENCY`, блокировка job'а 5 мин |

Очереди `cleanup` нет — cron чистит сам, под локом (§10.2). Имена — только те, у которых есть и продюсер, и процессор (`common/queue/queue.constants.ts`): job без одного из них — обещание, которое никто не выполняет.

Базовая конфигурация job'а: `attempts: 3`, exponential backoff от 5 с, `removeOnComplete: true`, `removeOnFail: { age: 7 дней, count: 1000 }` (упавшие видны в `GET /platform/queues`, но не копятся вечно). У `email` — 8 попыток с backoff от 15 с (≈ 30 минут на аварию SMTP), у окончательно упавшего письма payload стирается. Payload содержит только идентификаторы. Все job'ы идемпотентны.

**Сворачивание сообщений чата.** У получателя одна строка уведомления на чат (`dedupeKey = new-message:chat:<chatId>`, поле job'а `collapseKey`); новое сообщение обновляет её (текст, `createdAt = now`, снова непрочитано), и WS `notification:new` приходит с тем же `id`; прочтение чата помечает её прочитанной. Письмо о сообщениях уходит, только когда строка снова стала непрочитанной, и не чаще раза в 6 ч на чат; push — на каждое сообщение. Письма-зеркала ставятся в `email` с приоритетом, транзакционные — без него и идут первыми.

Очереди медиа обрабатывает отдельный процесс `node dist/worker.js` (тот же образ, что у API; ffmpeg из apk), когда API запущен с `MEDIA_PROCESSING=worker`; при `inline` (dev, деплой без воркера) процессоры живут в процессе API. Временные файлы перекодирования — в `MEDIA_TMP_DIR` (по умолчанию системный tmp): каталог на job, удаляется в `finally`, брошенные упавшим процессом сносятся при старте воркера. Нет ffmpeg — видео остаются в `PENDING` и проигрываются оригиналом; наличие ffmpeg перепроверяется раз в минуту, и `resumeMediaProcessing` вернёт их в очередь, как только он появится (без перезапуска процесса). `FAILED` — только настоящая неудача обработки, его cron не повторяет.

Каждый job очереди `notifications`: создать запись `Notification` → отправить WS `notification:new` онлайн-пользователям → для офлайн с включённым каналом поставить задачу в `email` (`send-notification`) / push. Идемпотентность — через `Notification.dedupeKey` (уникален в пределах пользователя): повторный запуск job'а не создаёт дубликат и не рассылает повторно.

**Язык уведомления.** Продюсер кладёт в job не готовый текст, а ключ словарной статьи
(`titleKey`/`bodyKey`) и параметры (`params`): job один на всех адресатов, а язык у каждого
свой. Строку собирает процессор — там, где он и так читает получателя вместе с его
`locale`. В `Notification` пишется и отрисованный текст (`title`/`body` — его требуют push и
письмо-зеркало, им нужна готовая строка), и ключ с параметрами: они отдаются клиенту, чтобы
после смены языка перерисовались и вчерашние уведомления. Ключ пуст там, где словарной
статьи не бывает: имя отправителя в заголовке о сообщении, превью сообщения, комментарий
сотрудника, метка времени слота — пользовательский ввод переводить нечем. Словарь —
`NOTIFICATION_MESSAGES` в `@studenthub/shared-config` (общий: те же строки рендерит и
браузер), письма — `apps/api/src/modules/email/email-strings.ts` (только сервер).

Язык письма приходит в payload'е job'а очереди `email` полем `locale`. У приглашения это
язык приглашающего: у адресата учётной записи ещё нет. У писем внешним адресатам
(подтверждение компании, заявка вуза с лендинга) языка нет вовсе — русский по умолчанию.

## 11. Безопасность и приватность

### 11.1 Принципы доступа

- Студент не видит персональные данные других студентов.
- Староста не видит личные заявки, оценки и документы одногруппников.
- Администраторы и модераторы не получают доступ к личным чатам без жалобы; каждый такой доступ пишется в `AuditLog`.
- Любой `:id` в маршруте проверяется на принадлежность scope пользователя (защита от IDOR).
  Для `GET /users/:id` это реализовано через `profileVisibility` + роль смотрящего (§3.7): вне
  аудитории/scope отдаётся только `limited`-визитка, а не полная карточка.
- Soft delete для всех критичных сущностей.

### 11.2 Три уровня guard

```
JwtAuthGuard (глобальный, снимается @Public) → RolesGuard (@Roles) → ScopeGuard (scope из JWT)
```
Guard не заменяет проверку в сервисе: сервис дополнительно сверяет фактическую принадлежность ресурса.

Публичных (`@Public`) маршрутов немного и каждый объяснён там, где описан: вход и обновление сессии, регистрация по инвайту, публичное состояние платформы, `POST /mini/session` и `POST /mini/link` (Telegram открывает мини-апп без нашего токена), `POST /demo-requests` и `POST /demo-requests/verify` (заявка вуза: её подаёт человек, у которого аккаунта ещё нет и быть не может — вуза на платформе пока нет) `POST /telegram/webhook` и три маршрута HLS-плейлистов медиа (`GET /media/:fileId/hls/…`, доступ по подписанному токену — см. «Медиа» в §API). Последний — единственный, где заявителя не удостоверяет ни пароль, ни подпись initData: его защищает секрет в заголовке, и без настроенного секрета он не делает ничего.

### 11.3 Персональные данные

Минимальный сбор · выгрузка своих данных по запросу · удаление аккаунта · настройки приватности профиля · запрет логирования персональных данных, паролей и токенов.

**Удаление аккаунта** (`DELETE /users/me`, §8.3) удаляет контент профиля: фото и видео с объектами и постерами, обложки статей, статьи, опросы, альбомы, портфолио и свои закладки; удаляет привязку Telegram (`telegram_accounts`); адреса пушей (`DeviceToken`, `PushSubscription`) убирает cron `purgeDeviceTokens`. Посты, комментарии и сообщения остаются с автором-tombstone. Сканы удалённых документов физически удаляются через 30 дней (`cleanDetachedFiles`). Подробнее — `docs/PERSONAL_DATA.md`.

### 11.4 Аудит

`AuditLog` фиксирует: login, logout, все операции с инвайтами (включая `invites_expired` — одна запись на пачку), смену роли (`user_role_changed`), смену статуса университета, блокировку пользователя (`user_blocked` / `user_unblocked` / `user_unblocked_expired`), решения модератора, доступ администратора к личным чатам, события учётной записи (`2fa_enabled`, `2fa_disabled`, `2fa_backup_codes_regenerated`, `user_2fa_reset`, `password_changed`, `change_username`, `account_deleted`), проверку студенческого (`student_id_verified`), учебные данные (`user_academic_updated`), модерацию контента профиля (`profile_media_deleted`, `profile_article_deleted`, `poll_deleted`, `content_comment_deleted`, `event_comment_deleted`), выгрузки (`users_export`, `personal_data_export`) и рычаги платформы (`platform.*`). Поля: `userId`, `action`, `entity`, `entityId`, `metadata`, IP, user-agent, `createdAt`.

### 11.5 Наблюдаемость и внешний трекер ошибок (Ф13.8)

Sentry подключён и на api (`@sentry/nestjs`), и на web (`@sentry/nextjs`). Без DSN не
инициализируется — dev, тесты и CI работают как раньше.

Что покрыто: HTTP-5xx (глобальный фильтр), падения job'ов очередей, сбои WS-обработчиков,
падения cron-задач, ошибки серверного рендера Next (`onRequestError`) и любые исключения в
браузере (error-boundary + глобальные обработчики SDK).

**Персональные данные во внешний сервис не уходят.** `sendDefaultPii: false` (без IP и
cookie), плюс собственный `beforeSend`: вырезаются тела запросов, cookie, `Authorization`,
`job.data`; из URL, имён транзакций и хлебных крошек вычищаются секреты (`?token=` ссылки
приглашения и QR студенческого, токен в пути `/invites/:token/preview`). Пользователь
идентифицируется только `id` — без email и ФИО. Session Replay сознательно не подключён.
Правила чистки — общий `scrubSentryEvent` в `@studenthub/shared-config`, покрыт тестами
в обоих приложениях.

Событие Sentry и строка лога связаны в обе стороны: тег `request_id` в событии и
`sentryEventId` в логе pino.

Цена на фронте (§11 — производительность важна, аудитория мобильная): shared First Load JS
106 → 142 кБ, **+36 кБ**. Без tree-shaking трейсинга было бы +89 кБ, поэтому в
`next.config.mjs` включён `webpack.treeshake.removeTracing` — но по условию от
`NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE`, иначе включение сэмплирования через env тихо не
работало бы.

пути, домен не сверяется: ссылки собираются из `CORS_ORIGIN` и `APP_PUBLIC_URL`, и домены
могут не совпадать. Переход всегда собирается заново из проверенных частей и остаётся
внутри приложения. Чужие QR не открываются. Права проверяет целевой экран и сервер.
Камера проверки студенческого (`/verify-id` без токена) принимает только билеты.
Распознавание — `parseQrTarget` в `features/qr-scan`.

Ролевой редирект — `ROLE_HOME` в `shared/config/routes.ts`, применяется в `middleware.ts` до рендера.

| `demo` (по умолчанию) | только демо-вуз | ~360 | ~30 тыс. | секунды |

### Контент на пользователя

У каждого пользователя вуза свои посты, статьи и опросы; объёмы задаются ручками:

Диапазон задаётся ОДНОЙ строкой — `SEED_POSTS=100-500`; одно число означает точное
количество, а `0-0` — «не создавать вовсе» (шаг пропускается целиком). Пара
`SEED_POSTS_MIN`/`SEED_POSTS_MAX` по-прежнему работает и сильнее строки. Одна строка —
не украшение: у `workflow_dispatch` не больше десяти входов, и пара полей на каждую
сущность в форму не помещается.

| Ручка | По умолчанию | Что это даёт на 130 тыс. пользователей |
|---|---|---|
| `SEED_POSTS` | `20-100` | ~7.8 млн постов |
| `SEED_ARTICLES` | `20-50` | ~4.6 млн статей |
| `SEED_POLLS` | `10-100` | ~7.2 млн опросов + 25 млн вариантов |
| `SEED_PHOTOS_PER_USER` | `0-0` | строки `File` со ссылкой на пул (байт в хранилище не добавляют) |
| `SEED_VIDEOS_PER_USER` | `0-0` | то же для видео |
| `SEED_POLL_VOTES_MAX` | 3 | ~11 млн голосов |
| `SEED_POST_IMAGES_PER_USER` | 2 | ~260 тыс. строк `File` |

**Про изображения постов.** `File.postId` — эксклюзивная привязка: на каждый пост нужна
своя строка `File`. А вот пара `(bucket, key)` уникальной быть перестала (миграция
`20260929121630_files_shared_object_pool`), поэтому строки **ссылаются на объекты общего
пула**, а копий в хранилище не делается вовсе. Фото один раз уменьшаются до ширины поста
(640px, `sharp`) и кладутся в бакет постов как источники; дальше картинка у миллиона
постов стоит миллион строк и ноль дополнительных байт. Раньше здесь было серверное
копирование (`copyObject`, ~420 копий/с) — оно стоило 200+ ГБ на полном прогоне.

Демо-вуз (`seed-university-001`) генератор не трогает: он создаёт свои вузы `u001…u100`
рядом. На исторические id демо-вуза ссылаются этот раздел, dev-инвайт и e2e.

Ключевые переключатели (полный список — `prisma/seed/config.mjs`):

```bash
SEED_SCALE=full pnpm db:seed            # 100 вузов
SEED_FROM=20 SEED_TO=40 …               # догенерировать порцию вузов
SEED_FORCE=1 …                          # перегенерировать уже залитые вузы
SEED_CONCURRENCY=4 …                    # сколько вузов генерировать параллельно
SEED_MEDIA=1 pnpm db:seed                # медиа и для demo (по умолчанию только small/full)
SEED_MEDIA=0 …                          # без скачивания медиа
SEED_PHOTOS=1000 SEED_VIDEOS=150 …      # размер медиа-пула
SEED_POSTS=0-0 SEED_POLLS=5-20 …        # контент на пользователя диапазоном
SEED_PHOTOS_PER_USER=100-500 …          # личная галерея (ссылки на пул)
SEED_DEMO_UNIVERSITY=0 …                # без демо-вуза «Алатау» и dev-инвайта
SEED_TAG=run-17 …                       # пометить прогон (нужно для уборки)
SEED_MODE=cleanup SEED_TAG=run-17 …     # удалить всё, что налил прогон run-17
SEED_CONFIRM_BIG=1 …                    # согласие на объём выше мягкого потолка
SEED_POST_IMAGES_PER_USER=0 …           # без изображений у постов
SEED_MEDIA_REFRESH=1 …                  # заново обойти Викисклад за видео
```

Гарды: масштаб больше `demo` на **нелокальной** БД заблокирован без `SEED_ALLOW_REMOTE=1`
(22 млн строк на Railway — это тариф и полчаса прогона). Повторный прогон пропускает
уже залитые вузы по маркеру в `AuditLog` (`action = SEED_UNIVERSITY`).

Потолки объёма считаются **до первой записи**, по формулам планировщика: выше 50 млн
строк прогон требует `SEED_CONFIRM_BIG=1`, выше 300 млн отказывается работать. Оба
значения настраиваются (`SEED_MAX_ROWS_SOFT`, `SEED_MAX_ROWS_HARD`). Смысл в том, что
боевая база и база стенда — одна и та же: узнать «получился миллиард строк» надо до
старта, а не через пять часов.

### 14.0 Прогон на боевой базе: метка и уборка (workflow `SEED`)

`.github/workflows/seed.yml` — ручной запуск с настройкой состава из формы: ветка
(встроенный выбор `workflow_dispatch`), 0–500 вузов, диапазон студентов на вуз и по
диапазону на каждую сущность контента. Десять входов — это потолок формы, свободных
мест нет.

База у стенда та же, что у прода. Отсюда три правила, на которых построен весь режим:

1. **Сид только создаёт строки.** Режима «очистить и залить заново» в форме нет.
2. **Каждый прогон помечается меткой** (`tag`, по умолчанию `seed-<номер запуска>`).
   Метка попадает в маркер каждого вуза и в отдельную запись `AuditLog`
   (`action = SEED_RUN`) — это манифест прогона.
3. **Уборка только прицельная.** `mode: cleanup` + повтор метки в поле `confirm`
   удаляет ровно то, что налил прогон с этой меткой: сначала пользователей вузов (с
   ними каскадом весь контент), затем заявки, расписание, курсы, группы, факультеты и
   сам вуз. Порядок продиктован `Restrict`-связями. Вуз с id не вида `u042` и демо-вуз
   не удаляются вовсе, манифест снимается последним — прерванную уборку можно просто
   перезапустить.

Уборка не трогает **общие справочники**: КАТО, каталог услуг (категории и глобальные
шаблоны, на них ссылаются заявки всех вузов), компании с аккаунтами работодателей и
демо-вуз. Это не забывчивость, а граница: справочники не принадлежат прогону, и снос
категорий сломал бы заявки в вузах, которые никто не просил удалять.

Демо-вуз «Алатау» в этом workflow выключен жёстко (`SEED_DEMO_UNIVERSITY=0`): на боевой
базе сотни аккаунтов под одним общим паролем и dev-инвайт с известным токеном — это
готовый вход, а не демонстрация. Платформенный админ и каталог услуг создаются
по-прежнему всегда: первый — штатный бутстрап, второй — справочник, без которого
генератор падает на внешнем ключе `application_services_category_id_fkey`.

### 14.1 Второй вариант: тестовый стенд (`pnpm db:seed:test`)

Отдельная точка входа `prisma/seed-test.mjs` рядом с основным сидом. Состав задан
поимённо, а не выведен из числа студентов, — стенд заводят под приёмку, и числа в нём
проверяются:

| Роль | Сколько |
|---|---|
| `PLATFORM_ADMIN` | 1 |
| `PLATFORM_MODERATOR` | 2 |
| Университет | **1** (демо-вуз «Алатау» здесь не заливается) |
| `UNIVERSITY_ADMIN` | 1 |
| `UNIVERSITY_MODERATOR` | 2 |
| `DEAN` | 2 (по одному на факультет) |
| `TEACHER` | 24 (12 + 12) |
| `STUDENT` + `STAROSTA` | **1450** = 1392 + 58 (староста — по одному на группу) |
| `EMPLOYER` | 27 (20 компаний, иначе раздел «Карьера» пуст) |

Структура: 2 факультета × 29 групп по 25 учащихся = 58 групп. Заполнено всё остальное —
справочники (КАТО, каталог услуг, типы документов), расписание, оценки, посещаемость,
экзамены, документы, заявки, чаты, посты, статьи, опросы с голосами, портфолио, вакансии
и отклики. Профили пользователей заполнены целиком: пустое поле означает не отрисованный
блок на экране, а стенд заводят как раз чтобы эти блоки посмотреть.

**Почему отдельная точка входа, а не флаг.** Требование «1 университет» означает ровно
один, а основной сид безусловно заливает демо-вуз с named-аккаунтами: он вшит в его 1300
строк, и на его id ссылается этот раздел, dev-инвайт и e2e. Проще не звать его вовсе и
собрать стенд из тех же шагов — шаги переиспользуются один в один.

Вход: пароль у всех общий (см. §14, `SEED_PASSWORD`), платформенные — `admin@studenthub.app`,
`moderator1@`, `moderator2@studenthub.app`; вузовские — `admin@u001.edu.kz`,
`moderator.0@u001.edu.kz`, `dean.<код>@u001.edu.kz`, охрана — `security.0@u001.edu.kz`,
библиотекарь — `librarian.0@u001.edu.kz` и т. д. (итог прогона печатает список).
Named-аккаунтов вида `dean@studenthub.app` здесь нет — они принадлежат демо-вузу.

**Личная галерея — пустая.** Пул медиа (200 фото, 50 видео) заливается: из него идут
аватары, обложки профилей, обложки альбомов и статей, картинки постов. А вкладки «Фото»
и «Видео» в профиле остаются пустыми — по решению от 2026-09-16.

Причина была в цене: пока `File` был уникален по `(bucket, key)`, карточка галереи
означала отдельный объект в MinIO, и «сто фото у каждого» — это 150 тыс. объектов,
≈ **29 ГиБ, то есть 29 из 30 ГБ всего стенда** ради содержимого двух вкладок. После
снятия уникальности карточки — это ссылки на пул, и объём хранилища от их числа больше
не зависит: включать галерею можно свободно (`SEED_PHOTOS_PER_USER=100-500`). Плата
другая — картинки у всех одинаковые, и раздачу медиа под нагрузкой таким стендом не
измерить.

Механизм (`prisma/seed/steps/57-user-media.mjs`) не удалён, а выключен нулём и включается
без пересборки остального — копии делает сам MinIO (`copyObject`), заново ничего не
качается:

```bash
SEED_PHOTOS_PER_USER=30 SEED_VIDEOS_PER_USER=1 pnpm db:seed:test   # ~9 ГБ, +~1 мин
```

Шаг вызывается только из `seed-test.mjs`; в `demo`/`small`/`full` его нет вовсе.

Состав переопределяется теми же ручками: `SEED_FACULTIES`, `SEED_TEACHERS`,
`SEED_GROUP_SIZE`, `SEED_STUDENTS_MIN`/`MAX`, `SEED_PLATFORM_MODERATORS`. Стенд
пересобирается на пустой БД; прогон без медиа — около минуты, с галереей — десятки минут.

### Медиа сида

Шаг медиа скачивает **1000 уникальных фото** (200 портретов для аватаров + 800
контентных) и **~120 уникальных видео** из источников со свободными лицензиями
(picsum.photos, randomuser.me, образцы Blender Foundation, Викисклад), кладёт их в MinIO
и создаёт на каждый объект запись `File`. Запись обязательна: cron `cleanOrphanFiles`
удаляет из бакетов всё, на что нет `File`.

Скачанное кэшируется в `.seed-media/` (в `.gitignore`) с манифестом (URL, sha256,
лицензия) — повторный прогон не тянет из сети те же полгигабайта.

Аватар и обложка есть у **всех** пользователей: это URL публичного бакета, его можно
переиспользовать. Вложение поста, фото в альбоме и файл в чате требуют своей строки
`File` (привязка `postId`/`albumId`/`messageId` эксклюзивна), но объект переиспользуется:
после снятия уникальности `(bucket, key)` число таких сущностей не ограничено размером
пула. Разнообразие картинок — да, ограничено: их столько, сколько в пуле (`SEED_PHOTOS`).

Дальнейший порядок ввода пользователей — см. `IMPLEMENTATION_PLAN.md`, Приложение Б.

## 16. Git и процесс

Ветки: `main` (production, только PR) · `develop` (интеграционная, только PR) · `feat/*` · `fix/*` · `refactor/*` · `chore/*` · `hotfix/*` (от `main`).

Conventional Commits, scope обязателен для `feat` и `fix`:
`feat(auth): регистрация по инвайту` · `fix(schedule): корректный расчёт чётности недели` · `perf(feed): cursor-пагинация`.

PR: ≤ ~400 строк изменений, минимум 1 approve, зелёный CI, squash merge. Чеклист PR — в `BACKEND_RULES §17` / `FRONTEND_RULES §14`.

Исключение — релизный PR `develop → main`: он вливается **merge-коммитом**. Squash склеил бы все коммиты релиза в один, и описание релиза, которое собирается из conventional-коммитов между тегами, вышло бы из одной строки. Порядок выпуска, ноты «Что нового» и откат — `docs/RELEASE.md`.

Агент коммитит локально на каждом завершённом шаге, сообщения коммитов пишет по-русски и не делает `push`, PR и мёрж без явной просьбы человека — см. `AGENTS.md`.

Именование: файлы `kebab-case` · переменные и функции `camelCase` · классы, типы, enum `PascalCase` · константы `UPPER_SNAKE_CASE` · таблицы `snake_case` через `@@map`.

Prettier: без точек с запятой, одинарные кавычки, `trailingComma: all`, `printWidth: 100`, `tabWidth: 2`.
ESLint: `no-console: warn`, `@typescript-eslint/no-explicit-any: error`.
