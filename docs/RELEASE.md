# Релизы StudentHub

Как выпускается версия, откуда берётся её номер и как пользователь узнаёт, что изменилось.

Релиз здесь — это **три разных артефакта**, и путать их не надо:

| Артефакт | Кто делает | Кто читает |
|---|---|---|
| Тег `vX.Y.Z` и GitHub Release | человек создаёт релиз в интерфейсе, описание собирается само | команда: разбор инцидента, «когда это уехало» |
| Нота «Что нового» | человек, до мёржа в `main` | студент, преподаватель, сотрудник вуза |
| Деплой на Railway | автомат по push в `main` | — |

Из коммитов не выводится нота: `feat(applications): каталог услуг на странице заявок` —
это «что сделали», а человеку нужно «что теперь можно и чего больше не будет». Поэтому
список изменений собирается сам, а нота пишется руками — и без неё релиз не выпускается.

---

## 1. Ход релиза

Человек делает четыре вещи; остальное собирается само.

1. **Коммиты в рабочей ветке** → **PR в `develop`**. Заголовок PR и коммиты — Conventional
   Commits: из них соберётся описание релиза.
2. **Нота «Что нового»** — запись в `apps/web/src/entities/release/model/notes.json` для
   версии, которую собираетесь выпустить. Пишется **до** мёржа в `main`: нота едет в бандле
   вместе с кодом, который описывает, и после выпуска её уже не подложить. Проверяет
   `scripts/release.mjs check-unreleased` — отдельный job CI на PR в `main`.
3. **Миграции** — workflow **Migrate (Railway)**: сначала режим `status` (покажет
   неприменённые миграции и SQL), потом `deploy`. До мёржа: код должен встретить готовую
   схему, а не наоборот.
4. **PR `develop → main`**, мёрж **merge-коммитом** (не squash — иначе все коммиты релиза
   схлопнутся в один и описание выйдет из одной строки). Railway выкатывает api, web и
   landing; ops-бот пишет в чат по строке на сервис.
5. **Releases → Draft a new release** в интерфейсе GitHub: тег `vX.Y.Z` на `main`, цель —
   `main`, заголовок на ваше усмотрение, **тело можно оставить пустым**. Publish.

Дальше без участия человека (workflow `Release`, событие `release: published`):

- сверяется, что для версии тега есть нота — иначе прогон падает и это видно в чате;
- если тело релиза пустое, оно заполняется: сверху человеческий текст ноты «Что нового»,
  ниже «Что уехало» — conventional-коммиты с прошлого тега, сгруппированные по типам
  (`feat` → Новое, `fix` → Исправления, `perf`, `refactor`, `revert`; `chore`, `docs`, `ci`,
  `test`, `build`, `style` не показываются), и ссылка на полный diff между тегами.

Написанное руками описание не затирается: пустое тело — это «собери сам», непустое — «я уже
написал». Кнопка GitHub «Generate release notes» тоже считается написанным вручную.

## 2. Номер версии

Источник правды — **тег**, который вы вводите при создании релиза. SemVer:

| Что уехало | Как менять |
|---|---|
| Новые возможности (`feat`) | минорная: `1.4.0 → 1.5.0` |
| Только исправления (`fix`, `perf`) | патч: `1.5.0 → 1.5.1` |
| Ломающее изменение (`!`, `BREAKING CHANGE`) | мажорная: `1.5.1 → 2.0.0` |

Версия ноты в `notes.json` обязана совпадать с тегом без `v`. `version` в корневом
`package.json` источником правды **не является** и ни на что не влияет: пакет приватный и
никуда не публикуется, а версию сборки, которую видит пользователь в настройках, даёт
`RAILWAY_GIT_COMMIT_SHA` (`NEXT_PUBLIC_BUILD_ID`).

Отдельного `CHANGELOG.md` в репозитории нет намеренно: страница Releases и есть changelog,
а файл пришлось бы коммитить ботом в защищённую ветку.

## 3. Нота «Что нового»

Живёт в `apps/web/src/entities/release/model/notes.json`, новые записи — сверху. JSON, а не
TypeScript, потому что тот же файл читают CI и workflow релиза: Node не импортирует `.ts`
без сборки, а второго источника правды у релизных текстов быть не должно.

```json
{
  "version": "1.7.0",
  "date": "2026-09-07",
  "showModal": true,
  "content": {
    "ru": {
      "title": "Каждый видит своё: права по разделам",
      "intro": "Большой релиз про доступ…",
      "sections": [
        { "items": [{ "icon": "🔑", "title": "В меню только то, что доступно", "text": "Раньше…" }] },
        { "heading": "База знаний", "items": [] }
      ]
    }
  }
}
```

`version` — ровно тот тег, который вы потом введёте в интерфейсе, без `v`. `date` — день
выпуска: по ней решается, кому окно не показывать (зарегистрировавшимся позже).

**Почему текст лежит в коде, а не в БД и не в API.** У приложения с домашнего экрана
открытая страница неделями работает на старой сборке: service worker отдаёт закешированный
HTML и обновляется только по кнопке (`shared/lib/use-sw-update.ts`). Нота, прилетевшая из
API раньше нового бандла, рассказывала бы про кнопки, которых у человека ещё нет. В коде
нота и функции, которые она описывает, приезжают одним обновлением. Плата за это —
опечатку не исправить без деплоя.

**Почему не в `messages/*.json`.** Словари — строки интерфейса, и их наборы обязаны
совпадать во всех трёх локалях (`shared/i18n/messages.test.ts`). Нота — контент: русский
обязателен, `kk` и `en` добавляются по мере перевода, до тех пор работает общий fallback
на `ru`. Структура перевода обязана повторять русскую (столько же блоков и пунктов) —
иначе часть списка молча пропала бы; это проверяет тест.

**Как писать.** Заголовок — одной фразой о главном, а не «Версия 1.7.0». Пункт — что
изменилось для человека и, если уместно, что было раньше. Технические детали, рефакторинг
и зависимости в ноту не идут: для них есть список коммитов в самом релизе. Пять-семь
пунктов — потолок, дальше не читают.

**`showModal: false`** — для патчей и технических релизов. Окно ради «починили опечатку»
обесценивает само окно: в следующий раз его закроют не читая. Нота при этом остаётся в
истории, открывается из настроек и уходит в описание релиза — не показывается только окно.

## 4. Кому и когда показывается окно

Решение принимает клиент (`entities/release/lib/pick-note.ts`), сервер хранит только
отметку.

- Окно показывается **один раз на версию** и на всех устройствах: `POST /releases/seen`
  пишет `release_views` — одна строка на пользователя.
- **Зарегистрировавшимся после даты релиза окно не показывается** — им всё новое. Отметка
  при этом ставится молча, иначе на следующем релизе окно всплыло бы дважды.
- Версия сравнивается числами, не строками: `1.10.0` новее `1.9.0`.
- Пока ответ `GET /releases/me` не пришёл, окно не мигает.
- Закрытие любым способом (кнопка «Понятно», крестик, Esc) считается прочтением. Если
  запрос не прошёл — окно всплывёт в следующий раз; тоста об ошибке поверх приветственного
  текста не будет.

## 5. Откат

`prisma migrate` не откатывает — обратной операции нет. Отсюда правило:

- в релиз идут **только аддитивные** миграции (новая таблица, новая nullable-колонка,
  индекс); удаление колонки или таблицы — **следующим** релизом, когда стало видно, что
  откатываться не придётся;
- откат кода — Railway → предыдущий деплой (для api, web и landing независимо: у landing
  нет ни БД, ни общего кода с платформой);
- откат ноты не нужен: версия, которую человек уже подтвердил, второй раз не покажется.

## 6. Что настраивается один раз

- [ ] Первый релиз — `v1.0.0`: создаётся в интерфейсе, как все следующие. Нота 1.0.0 уже
      написана, теги до этого не ставились, поэтому описание соберётся по всей истории —
      это нормально ровно один раз.
- [ ] Секрет `DATABASE_PUBLIC_URL` в окружении `production` (уже нужен для workflow Seed).
- [ ] В Railway для `api` и `web`: `SENTRY_RELEASE` и `NEXT_PUBLIC_SENTRY_RELEASE` =
      `${{RAILWAY_GIT_COMMIT_SHA}}` — тогда ошибка в Sentry и сообщение ops-бота несут
      версию сборки (`docs/RAILWAY.md`).
- [ ] Branch protection на `main`: PR обязателен, CI обязателен, прямой push закрыт.
