# StudentHub — Runbook (эксплуатация)

Что делать при инцидентах и рутинных операциях. Прод-архитектура — `docker/docker-compose.prod.yml`
+ nginx (TLS, WS-upgrade). Приложение: API (`:3001`, префикс `/api/v1`) + Web (`:3000`).

## Быстрая диагностика

```bash
curl -s http://localhost:3001/api/v1/health | jq   # Prisma / Redis / MinIO — up/down
ss -ltnp | grep -E ':3000|:3001|:5432|:6379|:9000'  # что слушает
```

`GET /health` (@nestjs/terminus, публичный) проверяет PostgreSQL, Redis, MinIO. Снаружи его
каждые 10 минут опрашивает прогон `prodUptime` — см. «Аптайм-мониторинг». Алерты по error-rate
настраиваются в Sentry (см. ниже).

## Отказ зависимостей (graceful degradation)

| Сервис | Симптомы | Что происходит | Действия |
|---|---|---|---|
| **Redis** | `/health` redis=down; не идут письма/уведомления, счётчик unread не кэшируется | Очереди BullMQ не принимают job'ы; job'ы НЕ теряются после восстановления (продюсеры повторяют по dedupeKey). HTTP-ответы не блокируются. | Поднять redis (`docker compose ... up -d redis`). После — воркеры разгребут очередь. |
| **MinIO** | `/health` minio=down; загрузка/скачивание файлов падает | Cron `cleanOrphanFiles` пропускает бакеты с логом-warn (не падает). Бизнес-операции без файлов работают. | Поднять minio. Проверить бакеты создались (bootstrap на старте API). |
| **PostgreSQL** | `/health` database=down; 500 на большинстве запросов | Приложение неработоспособно. | Поднять postgres; проверить `DATABASE_URL`; при исчерпании пула — рестарт API. |

Идемпотентность job'ов (dedupeKey у Notification, `reminderSentAt` у Event) гарантирует, что
повторная обработка после сбоя не создаёт дубликатов уведомлений/писем.

## Рутинные операции

**Рестарт API (сбрасывает in-memory throttler — счётчики rate-limit):**
```bash
PID=$(ss -ltnp | grep ':3001' | grep -oP 'pid=\K[0-9]+'); kill "$PID"      # не pkill
set -a && . apps/api/.env && set +a && node apps/api/dist/main.js          # :3001
```
> Throttler хранит счётчики в памяти процесса — рестарт API моментально снимает лимиты
> (login 5/15мин, register 3/час, complaints 10/час). Логин/пароли при этом не меняются.

**Рестарт Web:**
```bash
PID=$(ss -ltnp | grep ':3000' | grep -oP 'pid=\K[0-9]+'); kill "$PID"
pnpm --filter web build && apps/web/node_modules/.bin/next start apps/web -p 3000
```

## Прод-стек: первый запуск и сертификаты

Самостоятельный хостинг — `docker/docker-compose.prod.yml`. Домены, секреты и адреса сервисов
лежат в `docker/.env`, образец со списком обязательных — `docker/.env.example`. Четыре имени
ведут A-записями на машину со стеком: корневой домен — лендинг, `app.*` — платформа, `files.*` —
MinIO (по нему браузер кладёт и забирает файлы), `mini.*` — мини-апп Telegram.

**1. Сертификат выпускается до первого старта nginx.** Без файлов сертификата nginx не
поднимается, а пока он не поднялся, webroot-проверку отдавать некому — поэтому первый выпуск
идёт в режиме standalone, на свободном 80-м порту:

```bash
cd docker && set -a && . ./.env && set +a
docker compose -f docker-compose.prod.yml run --rm -p 80:80 --entrypoint certbot certbot \
  certonly --standalone --agree-tos --non-interactive -m "$CERTBOT_EMAIL" \
  -d "$SH_DOMAIN" -d "www.$SH_DOMAIN" -d "$SH_APP_DOMAIN" -d "$SH_FILES_DOMAIN" -d "$SH_MINI_DOMAIN"
```

Порядок имён важен: certbot называет каталог по первому `-d`, а nginx ищет сертификат
в `/etc/letsencrypt/live/$SH_DOMAIN/`. Тем же вызовом сертификат перевыпускается, когда
добавился домен.

**2. Миграции — до старта api**, стек их не применяет. CLI Prisma живёт в корне репозитория
и в образ api не попадает, поэтому накатывают их с машины с исходниками через порт postgres
на петлевом интерфейсе:

```bash
docker compose -f docker-compose.prod.yml up -d postgres
DATABASE_URL="postgresql://postgres:<пароль>@127.0.0.1:5432/studenthub" pnpm db:deploy
```

**3. Запуск стека:**

```bash
docker compose -f docker-compose.prod.yml --env-file .env up -d --build
```

nginx стартует последним — ждёт, пока api, web, лендинг и мини-апп начнут слушать свои порты.

**Продление сертификата идёт само:** сервис `certbot` раз в 12 часов делает `renew` через общий
с nginx каталог проверки, а nginx раз в 6 часов перечитывает конфигурацию и подхватывает новый
файл. Посмотреть сроки: `docker compose -f docker-compose.prod.yml exec certbot certbot certificates`.

**Правка `NEXT_PUBLIC_*` требует пересборки** (`up -d --build`), а не рестарта: они инлайнятся
в образы web и лендинга во время сборки.

## Миграции БД

- Схема — multi-file `prisma/schema/`, `prisma.config.ts` НЕ грузит `.env` (передавайте `DATABASE_URL` окружением).
- **⚠️ `migrate diff --shadow-database-url` СБРАСЫВАЕТ указанную БД.** Никогда не подставляйте туда
  рабочую БД — только отдельную пустую (`studenthub_shadow`). Иначе данные и история миграций теряются.
- Применение к непустой БД: сначала прочитать SQL глазами, показать владельцу, затем `migrate deploy`.
- `--accept-data-loss`, `db push`, `migrate reset` на не-тестовой БД — запрещены.

**Восстановление истории миграций (если `_prisma_migrations` пуста, а схема есть) БЕЗ дропа:**
```bash
for m in <каждая старая миграция>; do prisma migrate resolve --applied "$m"; done
prisma migrate deploy    # накатит только новые
node prisma/seed.mjs        # справочник КАТО заливается первым шагом сида
```

**Пересоздать dev-БД с нуля** (данных не жалко): `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`
через `prisma db execute` (не `migrate reset`) → `migrate deploy` → `node prisma/seed.mjs`.

**Залить платформу целиком** (100 вузов, ~77 млн строк, 40–70 мин, БД вырастает до ~32 ГБ,
MinIO до ~13 ГБ):
`pnpm db:seed:full` (КАТО заливается тем же прогоном). Профили и переключатели — `docs/PROJECT.md §14`.
Прогон возобновляемый: упал или прервали — запустите снова, уже залитые вузы пропускаются
по маркеру. Порциями: `SEED_FROM=41 SEED_TO=60 pnpm db:seed:full`. Перегенерировать —
`SEED_FORCE=1`. Гард не даст залить такой объём в нелокальную БД без `SEED_ALLOW_REMOTE=1`,
а оценка выше 50 млн строк потребует `SEED_CONFIRM_BIG=1` (выше 300 млн — отказ).

**Залить на боевую базу** — только через workflow `SEED` (`.github/workflows/seed.yml`):
с локальной машины прод-БД обычно недоступна. База общая с продом, поэтому сброса там
нет: прогон помечается меткой, а удалить налитое можно тем же workflow в режиме
`cleanup` с повтором метки в поле `confirm`. Подробности — `docs/PROJECT.md §14.0`.

## Бэкапы и восстановление

- **PostgreSQL**: `pg_dump` по расписанию (cron/systemd-timer), хранить off-site; проверять
  восстановление на staging. Пример: `pg_dump "$DATABASE_URL" | gzip > studenthub_$(date +%F).sql.gz`.
- **MinIO**: `mc mirror` бакетов в резервное хранилище (кроме `stories-media` с TTL 24ч).
- Перед релизом v1.0 обязательно проверить восстановление из бэкапа (критерий готовности §13).

## Секреты: где живут и как менять

Реестр нужен ровно для одного вопроса: секрет скомпрометирован — что поменять и что
перезапустить, чтобы ничего не встало. Раньше это восстанавливалось по памяти, а
последствия у разных секретов очень разные.

| Секрет | Где задан | Что ломается при смене |
|---|---|---|
| `DATABASE_URL` | переменные сервиса api (Railway) | ничего, кроме простоя на перезапуск |
| пароль Postgres | сервис Postgres (Railway) + секрет `DATABASE_PUBLIC_URL` в GitHub | workflow `Migrate`, `SEED`, `Reset DB` — у них своя копия строки подключения |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | переменные api | все сессии; людей выкидывает на экран входа |
| `TOTP_ENCRYPTION_KEY` | переменные api | **второй фактор у всех.** Ключ один, версий нет (`CryptoService`), и старые секреты TOTP после смены не расшифровываются. Менять только вместе со сбросом 2FA у всех, кому она включена |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | переменные api **и** сервис MinIO | доступ к файлам целиком; менять одновременно в обоих местах |
| `REDIS_PASSWORD` | сервис Redis + переменные api | очереди, троттлинг, кэш; на сервисе Redis это реальное значение, не ссылка на самого себя |
| `SMTP_PASS` | переменные api | письма (приглашения, восстановление пароля) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` | переменные api | мини-апп администраторов; вебхук после смены нужно зарегистрировать заново |
| `VAPID_PRIVATE_KEY` / `VAPID_PUBLIC_KEY` | переменные api и сборка web | все существующие подписки на push — их придётся оформлять заново |
| `SENTRY_DSN` | переменные api и web | только сбор ошибок |
| `SEED_PASSWORD`, `RESET_ADMIN_PASSWORD` | секреты GitHub | пароли учёток, созданных сидом и сбросом |

**Порядок смены.** Новое значение → в Railway (и в секреты GitHub, если он там дублируется)
→ перезапуск сервиса → проверка, что вход и загрузка файла работают. Публичные переменные
веба (`NEXT_PUBLIC_*`, `API_PROXY_TARGET`) — build-time: их смена требует пересборки образа,
а не перезапуска.

**Когда менять.** Плановая ротация раз в год; внеплановая — сразу, как только значение
где-то засветилось: в скриншоте, в переписке, в логе стороннего сервиса, в чужих руках.
Секрет, который кто-то видел, считается скомпрометированным, даже если им не пользовались.

## Ротация логов

- API пишет `pino` (JSON) в stdout; ротация задана в `docker/docker-compose.prod.yml` —
  json-file по 10 МБ, 5 файлов на сервис (или внешний коллектор вместо неё). Секреты (`authorization`, `password`, `token`)
  редактируются на уровне pino — в логах их нет.

## Мониторинг ошибок (Sentry)

Включается DSN'ом: `SENTRY_DSN` у api, `NEXT_PUBLIC_SENTRY_DSN` у web. Пусто — трекер молчит.

**Проверить, что включён.** В логе старта api есть строка `Sentry включён (env=…)` либо
`Sentry выключен: SENTRY_DSN не задан`. Для web: открыть страницу и проверить в консоли
браузера `Boolean(window.__SENTRY__)`.

**Ошибки есть, а в трекере пусто** — по порядку:
1. DSN действительно виден процессу? Для web он «впекается» в бандл **на сборке** — после
   добавления переменной нужен ре-деплой (пересборка), рестарта недостаточно.
2. Ошибка — 4xx? Ожидаемые отказы (401/403/404, бизнес-`AppException`) не отправляются
   намеренно. Порог — `status >= 500`.
3. Ошибка попала в `ignoreErrors` (обрыв сети, расширения браузера)? Список —
   `apps/web/src/shared/lib/sentry-options.ts`.
4. С мобильных: события идут через свой домен (`/monitoring`, обход блокировщиков). Туннель
   работает **только** с DSN Sentry SaaS (`*.ingest.sentry.io`); для self-hosted его нет.
5. Исчерпана квота проекта в Sentry — видно в самом Sentry (Stats).

**Найти в логах то, что видно в трекере, и наоборот.** В событии Sentry есть тег
`request_id`; тот же идентификатор — в строке pino (`requestId`). Обратно: в строке лога об
ошибке есть `sentryEventId`.

**Алерты по росту ошибок.** Настраиваются в самом Sentry (Alerts → Create Alert), в
репозитории их нет: правила живут рядом с данными, по которым срабатывают. Минимум, который
стоит завести на проект api и на проект web:

| Правило | Условие | Куда |
|---|---|---|
| Всплеск ошибок | Число событий за час выше обычного более чем вдвое | Тот же чат, что у аптайма |
| Новая ошибка в проде | Issue появился впервые, окружение `production` | Почта команды |
| Регресс | Закрытый issue открылся заново | Почта команды |

Пороги подбираются по первым двум неделям живого трафика: до этого «обычного» уровня
ошибок просто нет, и любое число будет выдуманным.

**Проверить, что персональные данные не утекают** (после изменений в захвате ошибок).
Поднять фейковый приёмник и посмотреть, что реально уходит:

```bash
# 1. Приёмник на :9911, пишет envelope в файл
node -e "require('http').createServer((q,r)=>{let b='';q.on('data',c=>b+=c);q.on('end',()=>{require('fs').appendFileSync('/tmp/env.txt',b+'\n');r.end('{}')})}).listen(9911)" &
# 2. Запустить сервис с фейковым DSN и воспроизвести ошибку
SENTRY_DSN=http://key@localhost:9911/1 pnpm --filter api start
# 3. Убедиться, что в /tmp/env.txt нет токенов, cookie, ФИО, тел запросов
```

Именно так были найдены две настоящие утечки при внедрении (токен в `?token=` и в крошке
навигации `data.from`/`data.to`) — ревью их не показало. Правила чистки и их тесты:
`packages/shared-config/src/monitoring.ts`, `apps/api/src/common/monitoring/sentry-scrub.spec.ts`,
`apps/web/src/shared/lib/sentry-options.test.ts`.

## Аптайм-мониторинг

Отвечает на вопрос «прод жив прямо сейчас?». Это не то же, что Sentry: трекер видит
ошибки *работающего* приложения, а молчащий Sentry одинаково означает и «всё хорошо», и
«сервис не поднялся вовсе».

**Как устроено.** Прогон `.github/workflows/uptime.yml` каждые 10 минут стучится туда же,
куда стучится пользователь: `GET /api/v1/health` у API и `GET /` у веба. На каждую точку
три попытки с паузой 20 секунд — разовый таймаут сети не повод будить команду.

Состояние между запусками живёт в **открытом issue** с заголовком «Прод не отвечает»:
прогон по расписанию не помнит предыдущий запуск, и без этой памяти лежащий час прод дал
бы шесть одинаковых сообщений подряд. В Telegram уходят только переходы:

| Событие | Что происходит |
|---|---|
| Точка перестала отвечать, инцидента нет | Заводится issue, в Telegram 🔴 |
| Точка не отвечает, инцидент уже открыт | Только запись в лог прогона, в Telegram тишина |
| Все точки ответили, инцидент открыт | Issue закрывается, в Telegram 🟢 |

Issue закрывать руками не нужно — он закроется сам. Закроете раньше времени — следующая
проверка заведёт новый и пришлёт повторный сигнал.

**Что настроить** (Settings → Secrets and variables → Actions):

| Имя | Где | Значение |
|---|---|---|
| `SMOKE_API_URL` | Variables | `https://api.…` — корень домена API, без пути. Общая со `smoke` |
| `SMOKE_WEB_URL` | Variables | `https://app.…` — корень домена веба. Общая со `smoke` |
| `TELEGRAM_BOT_TOKEN` | Secrets | Токен бота. Общий с ночной сводкой `codeChecks` |
| `TELEGRAM_CHAT_ID` | Secrets | Чат или канал команды. Общий с ночной сводкой |

Оба секрета Telegram — те же, что у ночной сводки CI; отправка идёт через общий экшен
`.github/actions/notify-telegram`. Секретов Telegram нет — инцидент всё равно заводится,
просто молча: проверка доступности не должна зависеть от того, завели ли бота.

**Адреса не заданы — два прогона ведут себя по-разному, и это намеренно.** `prodUptime`
пропускает проверку и пишет об этом в сводку запуска: он идёт каждые десять минут, и
полтораста красных прогонов в сутки гасят канал быстрее, чем кто-нибудь заведёт
переменные. `prodSmoke` **падает**: он отвечает на прямой вопрос «выкатка доехала?», и
зелёный ответ от прогона, который никуда не стучался, — это не проверка, а её видимость.
До 10 октября 2026 он как раз и зеленел впустую после каждого релиза.

**Два свойства расписания GitHub, о которых узнают поздно:**

1. Расписание работает только в ветке по умолчанию. Пока файл не в `main`, cron не идёт.
2. GitHub молча отключает расписание в репозитории, где 60 дней не было активности.

**Проверить, что работает** — Actions → `prodUptime` → Run workflow. Ручной запуск идёт по тем
же шагам, что и по расписанию. Чтобы увидеть сигнал целиком, временно подставьте в
`SMOKE_API_URL` заведомо мёртвый адрес: прогон заведёт issue и пришлёт сообщение, а после
возврата верного адреса — закроет и пришлёт 🟢.

**Пришёл 🔴 — что делать.** По порядку: открыть указанный в сообщении прогон и посмотреть
код ответа (`000` — не достучались вовсе, `502`/`503` — платформа не поднимает контейнер,
`200` у веба при мёртвом API — лёг только API); дальше «Быстрая диагностика» выше и
состояние сервисов в Railway. Если `/health` отвечает, но с `down` по одной из
зависимостей — смотреть «Отказ зависимостей».

**Чего прогон не ловит.** Он проверяет, что платформа отвечает, а не что она работает
правильно: медленные ответы, сломанный вход, неработающие загрузки для него неотличимы от
здорового прода. Это цена дешёвой проверки, и закрывается она Sentry — следующий раздел.

## Инцидент с персональными данными

Отдельно от обычного сбоя: при утечке счёт идёт не на «когда почините», а на «когда
уведомили». Порядок писан заранее, потому что в момент инцидента его не пишут.

> Сроки и состав уведомления — по открытым публикациям (сентябрь 2026); формулировки для
> реального уведомления сверяет юрист по действующей редакции. В коде ничего из этого не
> автоматизировано: раздел описывает действия людей.

**Что считается инцидентом.** Утечка или неправомерный доступ к персональным данным:
скомпрометированный секрет с доступом к базе, выгрузка данных посторонним, публичный доступ
к приватному бакету, доступ сотрудника за пределами его роли, потерянное устройство с
активной сессией администратора.

**Первые действия — по порядку.**

1. **Остановить утечку.** Отозвать секрет, закрыть доступ, снять публичный домен.
2. **Зафиксировать состояние.** Снять выгрузку `AuditLog` и `DocumentEvent` за период до
   того, как сработает уборка: журнал аудита живёт 90 дней, и после этого восстановить
   картину будет нечем. Сохранить логи контейнеров — они ротируются.
3. **Определить объём.** Чьи данные и какие именно: список субъектов нужен и для уведомления,
   и для оценки тяжести. Состав данных по группам — `docs/PERSONAL_DATA.md`.
4. **Уведомить университет как оператора.** Он отвечает перед субъектами, платформа
   обрабатывает по его поручению — решение об уведомлении уполномоченного органа принимает
   он, но фактуру даём мы и немедленно.
5. **Уведомить уполномоченный орган — один рабочий день** с момента обнаружения. В
   уведомлении: контакты ответственного, что уже сделано для устранения, сведения о
   затронутых лицах.
6. **Уведомить субъектов** — порядок отдельный, установлен правилами уведомления о нарушении
   безопасности персональных данных.
7. **Разобрать причину** и записать её здесь же, в runbook, вместе с тем, что изменили.

**Чего не делать.** Не удалять журналы и логи «чтобы не мешали», не менять данные в базе
задним числом, не сообщать субъектам оценок объёма, пока объём не установлен. Каждое из
этого потом невозможно объяснить.

**Кто принимает решения.** Заполнить до запуска: ответственный за защиту персональных данных
со стороны платформы, контакт со стороны вуза, кто имеет право говорить с уполномоченным
органом.

## Частые вопросы

- **`RATE_LIMIT` при логине** — исчерпано окно 5/15мин с IP; подождать или рестартнуть API (сброс throttler).
- **`P3005` при `migrate deploy`** — схема есть, а `_prisma_migrations` пуста → baseline через `migrate resolve --applied` (см. выше).
- **Письма «не приходят»** — в dev SMTP не настроен (`jsonTransport`), письма только логируются; это ожидаемо.
