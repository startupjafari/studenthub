> Версия: 2.0 · Последнее обновление: 2026-08
> Связанные документы: `docs/RUNBOOK.md`, `docs/RAILWAY.md`, `docs/BACKEND_RULES.md`, `docs/IMPLEMENTATION_PLAN.md`

## 0. Область и границы

Бот — **служебный инструмент команды**: пишет в закрытый чат о состоянии платформы.
Студенты, преподаватели и деканы его не видят и не привязывают; доставка уведомлений
пользователям в этот контур не входит (§10).

**Что он даёт.** Сейчас о падении cron-задачи или неприменённой миграции узнаёшь
постфактум — из логов Railway или из сломавшегося приложения. Служебный канал переводит
это в режим «узнал в момент события». Второе — сводки: раз в сутки видно, что платформа
не разъезжается, без захода в три дашборда.

### 0.1 Жёсткие ограничения

Нарушение любого — блокирующее замечание на ревью.

1. **В служебный чат не попадают персональные данные.** Ни email, ни ФИО, ни содержимое
   постов и сообщений, ни номера документов. Только идентификаторы сущностей (`user
   a1b2…`), счётчики и технические сообщения об ошибках.
2. **Бот не выполняет действий, меняющих состояние.** Ни рестарта, ни миграций, ни сида,
   ни рассылок. Токен бота живёт в телефоне и утекает вместе с ним; Telegram — не место
   для прод-доступа. Всё, что умеет бот, — читать и рассказывать.
3. **Сбой отправки не влияет на приложение.** Telegram недоступен, токен протух, чат
   удалён — вызывающий код продолжает работать, ошибка уходит в лог.
4. **Токен и chat_id — секреты.** Только переменные окружения, никогда в репозиторий.
5. **Тексты служебных сообщений не проходят через i18n.** Это осознанное исключение из
   `FRONTEND_RULES §10` / общего запрета на хардкод строк: сообщения адресованы команде,
   а не пользователю, и локализовать их незачем. Правило про i18n остаётся в силе для
   всего, что видит пользователь.

## 1. Конфигурация

Бот создаётся через `@BotFather` и добавляется в **закрытую супергруппу с включёнными
темами** (не в канал: в канале не работают команды, а темы нужны для разделения потоков,
см. §3.1). Group ID берётся из `getUpdates` после первого сообщения.

Переменные окружения (`apps/api/src/config/env.schema.ts`, все **optional**):

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен от BotFather |
| `TELEGRAM_OPS_CHAT_ID` | ID служебной супергруппы (отрицательное число) |
| `TELEGRAM_TOPIC_DEPLOY` | ID темы «Деплой» (`message_thread_id`) |
| `TELEGRAM_TOPIC_ALERTS` | ID темы «Ошибки» |
| `TELEGRAM_TOPIC_DIGEST` | ID темы «Сводки» |
| `TELEGRAM_WEBHOOK_SECRET` | `secret_token` для входящих апдейтов Telegram |
| `OPS_HOOK_SECRET` | Общий секрет для вебхуков Railway, Sentry и GitHub |
| `OPS_ENV_LABEL` | Метка окружения в сообщениях: `prod`, `staging` |
| `OPS_PUBLIC_URL` | Внешний URL для синтетического пинга (§2.3) |

**Модуль выключен, пока не задан токен** — тем же приёмом, что Sentry (`SENTRY_DSN`) и
Web Push (`VAPID_*`): нет переменной, `TelegramOpsService.send()` молча возвращает
`false`, приложение работает как прежде. Локальная разработка и CI не требуют бота.
Не заданы ID тем — сообщения идут в общий поток группы, это допустимая деградация.

На проде переменные задаются в Railway (`docs/RAILWAY.md`), не в `.env` образа.

## 2. Что отправляем

Каждое событие описано в реестре (§4.2): тема, статус, ключ дедупликации, порог
троттлинга. Ниже — содержательная часть.

### 2.1 Релизы и код

| Событие | Источник | Тема |
|---|---|---|
| Деплой начался / прошёл / упал | Вебхук Railway | Деплой |
| Упавший CI: какой шаг и ссылка на прогон | Вебхук GitHub Actions | Деплой |
| Что уехало на прод: список коммитов | Сборка по данным деплоя | Деплой |
| Дрейф веток: develop опережает main | Суточная проверка | Сводки |

**Деплой** — одно сообщение на релиз, а не три (§3.2). В нём: сервис (api/web), статус,
ветка, короткий SHA, автор, кнопка «Логи». Ссылка на логи — то, что нужно в 90% разборов.

**Упавший CI.** Важна не сама «красная галочка», а шаг: `lint`, `typecheck`,
`test (unit)`, `test (e2e)` или `build` — по ним сразу понятно, чинить код или
инфраструктуру. Берётся из `workflow_run` / `check_run` вебхука GitHub.

**Что уехало на прод** — список conventional-коммитов между предыдущим успешным
деплоем и текущим. Хранить историю не нужно: достаточно SHA предыдущего успешного
деплоя (одна строка в таблице `ops_deploy` или в Redis).

**Дрейф веток** — «develop опережает main на 12 коммитов, последний релиз 9 дней
назад». Для нерегулярных релизов это единственное напоминание, что накопилось.

### 2.2 Инциденты (реальное время)

| Событие | Источник | Тема |
|---|---|---|
| В репозитории есть неприменённые миграции | Проверка при старте API | Ошибки |
| Cron-задача упала | `CronMonitorService` | Ошибки |
| Частая cron-задача молчит два окна подряд | Периодическая проверка | Ошибки |
| Новая группа ошибок / всплеск | Вебхук Sentry | Ошибки |
| Всплеск 5xx | Периодическая проверка | Ошибки |
| Рост `failed` в очередях BullMQ + текст последней ошибки | Периодическая проверка | Ошибки |
| Внешний URL недоступен (синтетический пинг) | Cron раз в 5 минут | Ошибки |
| Зависимость деградировала (Postgres / Redis / MinIO) | Health-индикаторы | Ошибки |

**Неприменённые миграции** — самая дешёвая проверка с самой высокой отдачей: при старте
сравнить каталоги `prisma/migrations` с таблицей `_prisma_migrations`, расхождение
отправить списком. Именно этот случай ломал локальный запуск и на проде проявился бы
только рантайм-ошибкой. Проверка **только сообщает**, применяет человек (`RUNBOOK`).

**Молчание cron** — `publishScheduledPosts` крутится раз в минуту, и её тишина десять
минут такой же инцидент, как исключение, хотя ошибки не было.

**Синтетический пинг** внешнего `OPS_PUBLIC_URL` — `/health` изнутри может отвечать,
когда снаружи приложение недоступно: упал прокси, протух сертификат, домен не резолвится.

**Флаппинг-подавление** обязателен для всех проверок по расписанию: состояние меняется
`up → down → up` за минуту, и без гистерезиса канал звенит. Сообщаем о смене состояния,
а не о каждой проверке; «выздоровление» — отдельным 🟢.

### 2.3 Суточные проверки данных

Одним сообщением в 21:00 по таймзоне университета, тема «Сводки». Это не алерты —
здесь смотрят на тренд, а не бегут чинить.

- **Рост БД**: общий размер и топ-5 таблиц по объёму, дельта к прошлой неделе. На
  Railway есть лимиты, и упираться в них лучше заранее.
- **Хранилище MinIO**: объём по бакетам и сколько «сирот» нашла ночная
  `cleanOrphanFiles`.
- **Push-подписки**: доля `410 Gone` при рассылке. Растёт — копится мусор в таблице,
  пора чистить.
- **Очереди дел, а не техники**: жалобы и заявки без решения дольше трёх суток,
  инвайты без активации дольше недели. Это деградация сервиса, и знать о ней админ
  платформы должен раньше ректората.
- **Активность**: активные пользователи за сутки, новые регистрации, доля 5xx.

### 2.4 Безопасность

| Событие | Источник | Тема |
|---|---|---|
| Всплеск 401/403 и срабатываний throttler | Периодическая проверка | Ошибки |
| Админское действие: блокировка, смена роли, массовый импорт | Аудит-лог | Ошибки |

Всплеск неудачных авторизаций — самый дешёвый признак перебора паролей. В сообщении
агрегат: сколько попыток, за какое окно, сколько разных IP. Сами IP — да (это не
персональные данные пользователя платформы), логины — нет.

Админские действия берутся из `AuditLog`: **только тип действия и `id` сущности**, без
ФИО и email. Смысл — заметить чужие руки в админке, а не следить за коллегами.

## 3. Как устроен канал

Раздел не про события, а про читаемость. Без него канал перестают открывать на второй
неделе, и весь остальной документ теряет смысл.

### 3.1 Темы вместо общей ленты

Супергруппа с темами: **Деплой**, **Ошибки**, **Сводки**. Ночной всплеск Sentry не
должен погребать под собой сообщение о релизе. Тема задаётся полем `message_thread_id`
при отправке; ID тем — в переменных окружения (§1).

### 3.2 Деплой — одно редактируемое сообщение

Бот отправляет 🟡 «Деплой api начался» и затем **редактирует это же сообщение**
(`editMessageText`) в 🟢 или 🔴. В канале остаётся одна строка на релиз вместо трёх.

`message_id` живёт до конца деплоя — хранить его нужно там, где переживёт рестарт
инстанса: Redis с TTL в час, ключ по `deploymentId`. Не нашли `message_id` (рестарт,
истёк TTL) — отправляем новое сообщение, а не теряем событие.

### 3.3 Живой закреплённый статус

Одно закреплённое сообщение, которое бот переписывает по расписанию (раз в 5 минут) и
после каждого деплоя: версия на проде и SHA, аптайм, состояние Postgres / Redis / MinIO,
глубина очередей, время последней проверки. Открыл канал, посмотрел вверх — видно всё,
команду дёргать не нужно.

Правки закреплённого сообщения **не должны порождать уведомления**: `disable_notification`
и редактирование вместо новой отправки. Если содержимое не изменилось — не редактируем
вовсе, иначе Telegram вернёт `message is not modified` и засорит лог.

### 3.4 Кнопки-ссылки

Inline-клавиатура с URL под сообщением: «Логи Railway», «Sentry issue», «PR», «Прогон
CI». Это ссылки, а не действия: callback'ов у бота нет вовсе, значит нет и поверхности
для несанкционированного вызова.

### 3.5 Тишина на время работ

`/quiet 2h` — приглушить всё, кроме 🔴, на заданный срок; `/quiet off` — снять. Плановая
миграция не должна порождать сорок сообщений. Состояние — в Redis с TTL, чтобы пережило
рестарт. Заглушенные события не теряются: по окончании тишины уходит одно сводное
«за время тишины: 12 событий, из них 2 красных».

### 3.6 Метка окружения

Каждое сообщение начинается с метки из `OPS_ENV_LABEL`, если она не `prod`. Пока среда
одна, это ничего не стоит; когда появится staging, не придётся гадать, где именно упало.

## 4. Архитектура

```
apps/api/src/common/monitoring/
  ops-notifier.interface.ts     # порт: OpsNotifier.emit(event)  ← знают доменные модули
  ops-event.registry.ts         # реестр событий: тема, статус, дедуп, троттлинг

apps/api/src/modules/ops-notify/
  ops-notify.module.ts
  telegram-ops.service.ts       # единственный, кто ходит в Telegram Bot API
  ops-message.builder.ts        # единственный, кто собирает текст и кнопки
  ops-sanitizer.ts              # вырезает ПД и секреты из любого текста
  ops-policy.service.ts         # тишина, дедупликация, троттлинг, метка окружения
  ops-status.service.ts         # метрики для /status, закреплённого статуса и сводки
  ops-hooks.controller.ts       # приём вебхуков: railway | sentry | github | telegram
  hooks/                        # по мапперу на источник + тест на реальном payload
  checks/                       # проверки по расписанию (миграции, 5xx, пинг, сводка)
```

### 4.1 Порт и адаптер

Доменные модули (`CronMonitorService`, `NotificationsProcessor`, health) **не знают про
Telegram**. Они зависят от интерфейса:

```ts
export interface OpsNotifier {
  emit(event: OpsEventName, data: Record<string, string | number>): void
}
```

Реализация — `TelegramOpsNotifier` в `ops-notify`. Замена транспорта (Slack, почта,
вебхук в другую систему) — новая реализация того же порта, без единой правки в доменных
модулях. Зависимость строго в одну сторону: `ops-notify` знает про prisma, health и
очереди; никто не знает про `ops-notify`, кроме DI-контейнера.

### 4.2 Реестр событий

Единственное место, где заводится событие:

```ts
export const OPS_EVENTS = {
  deployStarted: { topic: 'deploy', status: 'pending', dedupe: 'deploymentId', ttl: 0 },
  cronFailed:    { topic: 'alerts', status: 'error',   dedupe: 'job',          ttl: 600 },
  // …
} as const
```

Добавить событие = добавить строку в реестр и вызвать `emit()`. Не «ещё один вызов
`send()` где-то в коде»: тема, дедупликация и порог должны быть видны в одном списке,
иначе через полгода никто не ответит, почему канал шумит.

### 4.3 `TelegramOpsService`

Единственная точка сетевого вызова в Telegram. Контракт:

- **Никогда не бросает.** Ошибка сети, 4xx, отсутствие токена — лог и `false`.
- **Таймаут 5 секунд, одна повторная попытка** с экспоненциальной паузой.
- **Отправка через очередь BullMQ** (`ops-notify`, concurrency 1, лимитер): порядок
  сообщений сохраняется, всплеск не упирается в rate limit синхронно, задание переживает
  рестарт. Вызывающий код не ждёт сети вовсе.
- **Никогда внутри транзакции БД** — внешний вызов держал бы соединение пула.
- Умеет три операции: `send`, `edit`, `pin`. Больше от него не нужно.

### 4.4 Формат сообщения

Единый шаблон, чтобы канал читался с телефона по диагонали:

```
🔴 Деплой api — упал
ветка: develop · 2c7a86e · startupjafari
[Логи Railway] [PR #97]
```

Первая строка — эмодзи-статус и суть; в списке чатов видно только её.
Статусы: 🟢 успех · 🔴 отказ · 🟡 внимание/в процессе · ⚪️ информация.

Собирает текст только `OpsMessageBuilder`. Ручная конкатенация строк в местах вызова
запрещена — иначе формат разъедется, а санитайзер (§7.2) окажется не на пути данных.

## 5. Приём событий извне

`POST /api/v1/ops/hooks/:source`, где `source` — `railway` | `sentry` | `github`.

- Эндпоинты **публичные** (внешние сервисы не умеют наш JWT), поэтому:
  - обязательный секрет в заголовке (`X-Ops-Secret`), сверка через `timingSafeEqual`;
    для GitHub — штатная подпись `X-Hub-Signature-256` (HMAC-SHA256 от тела);
  - отдельный лимит throttler'а, строже дефолтного, и ограничение размера тела;
  - тело не логируется целиком — только тип события: в payload'ах ездят email
    коммитеров и фрагменты стектрейсов;
  - неизвестный `source` → 404 без подсказок; неверная подпись → 401 без деталей.
- Ответ всегда быстрый: маппер превращает payload в событие и кладёт в очередь;
  обработка — асинхронно. Внешние сервисы считают вебхук упавшим по таймауту.
- Добавление этих маршрутов в список публичных (`docs/PROJECT.md`) — **стоп-точка**:
  согласуется с человеком.

## 6. Команды бота

Требуют приёма апдейтов: `POST /api/v1/ops/hooks/telegram` с `secret_token`
(заголовок `X-Telegram-Bot-Api-Secret-Token`) и allowlist по `TELEGRAM_OPS_CHAT_ID` —
апдейты из других чатов игнорируются молча.

| Команда | Ответ |
|---|---|
| `/status` | То же, что в закреплённом сообщении, по запросу |
| `/queues` | Очереди BullMQ: waiting / active / failed |
| `/migrations` | Применённые и неприменённые миграции |
| `/quiet 2h`, `/quiet off` | Тишина на время работ (§3.5) |

Все команды — **только чтение** (`/quiet` меняет лишь состояние самого бота). Команд,
затрагивающих платформу, нет.

Раздел можно отложить: §2 работает на исходящих сообщениях и не требует публичного
эндпоинта для Telegram.

## 7. Правила кода

Правила этого раздела дополняют `docs/BACKEND_RULES.md` и относятся к модулю
`ops-notify`. Нарушение — блокирующее замечание на ревью.

### 7.1 Единственность

Одна ответственность — одно место в коде. Дублирование здесь особенно опасно: канал
читают глазами, и два разных формата одного события выглядят как два разных инцидента.

1. **Один транспорт.** Сетевой вызов в `api.telegram.org` существует ровно в
   `TelegramOpsService`. `fetch`/`axios` на Telegram из любого другого файла —
   запрещены, как и второй HTTP-клиент «по-быстрому».
2. **Один сборщик текста** — `OpsMessageBuilder`. Ни одной ручной склейки строк
   сообщения вне его.
3. **Один реестр событий** (§4.2). Событие без записи в реестре не отправляется.
4. **Одна политика доставки.** Тишина, дедупликация, троттлинг, метка окружения живут в
   `OpsPolicyService`, а не размазаны по вызывающим. Вызывающий сообщает факт; решает,
   отправлять ли, политика.
5. **Один источник метрик.** `/status`, закреплённое сообщение и вечерняя сводка берут
   числа из `OpsStatusService`; состояние зависимостей — из существующих
   health-индикаторов, а не собственными запросами к Postgres и MinIO.
6. **Один источник правды о деплое.** SHA последнего успешного деплоя хранится в одном
   месте; changelog и «дрейф веток» читают его оттуда, а не вычисляют каждый по-своему.

### 7.2 Безопасность

1. **Секреты только из окружения.** Ни токена, ни chat_id, ни ID тем в репозитории, в
   тестах и в снапшотах. Сравнение секретов — `timingSafeEqual`, не `===`.
2. **Санитайзер на пути наружу.** `OpsSanitizer` вызывается внутри `TelegramOpsService`
   перед отправкой и вырезает email, телефоны, JWT-подобные строки и всё похожее на
   ключ, плюс обрезает длину. Это архитектурная страховка: даже если кто-то передаст
   лишнее, наружу оно не уедет. Проверяется тестом.
3. **Модуль не пишет в доменные таблицы.** Prisma используется только на чтение
   (`findMany` с `take`, `count`, `groupBy`). Единственная допустимая запись —
   собственное служебное состояние (SHA деплоя, `message_id`), и лучше в Redis.
4. **Публичные эндпоинты — минимальная поверхность.** Подпись, отдельный throttler,
   лимит размера тела, никаких деталей в ответах об ошибке, тело не логируется.
5. **Никаких персональных данных**, даже «на всякий случай для отладки»: `id` вместо
   ФИО, агрегаты вместо списков, IP допустимы только в контексте безопасности (§2.4).
6. **Ошибка отправки не порождает событие.** Иначе получим петлю: не смогли отправить
   алерт → отправляем алерт об этом. Только лог и счётчик.
7. **Никаких действий над платформой** — ни разово, ни «временно для теста». Появится
   потребность — отдельное обсуждение с двойным подтверждением и аудитом.

### 7.3 Модульность

1. **Порт и адаптер** (§4.1). Доменные модули зависят от интерфейса `OpsNotifier`,
   не от Telegram. Зависимости строго однонаправленные, циклов нет.
2. **Тонкий контроллер.** `ops-hooks.controller.ts` проверяет подпись и передаёт тело
   мапперу. Ни бизнес-логики, ни обращений к БД.
3. **Маппер на источник.** `hooks/railway.mapper.ts`, `hooks/github.mapper.ts`,
   `hooks/sentry.mapper.ts` — чистые функции `payload → OpsEvent | null`, каждая со
   своим тестом на зафиксированном реальном payload. Новый источник = новый файл, а не
   ветка `if` в общем обработчике.
4. **Проверки по расписанию — отдельные классы** в `checks/`, по одной ответственности:
   миграции, 5xx, пинг, сводка. Каждая умеет работать независимо и падать независимо.
5. **Модуль выключается одной переменной.** Нет `TELEGRAM_BOT_TOKEN` — ни таймеров, ни
   вебхуков, ни фоновых запросов. Это проверяется тестом: приложение стартует и работает.
6. **Не тащить домен внутрь.** `ops-notify` не знает, что такое жалоба или заявка: он
   получает от доменных модулей готовые числа. Иначе он станет вторым местом, где
   описана предметная область.

### 7.4 Масштабируемость

1. **Отправка через очередь**, а не inline HTTP в хендлере (§4.3): всплеск в сто
   событий не блокирует воркеры и не упирается в rate limit синхронно.
2. **Идемпотентность по `dedupeKey`** — тем же приёмом, что у `Notification`. Повторная
   обработка после сбоя не даёт второго сообщения.
3. **Одна реплика — одна проверка.** На Railway инстанс может быть не один, и cron
   выполнится в каждом. Периодические проверки оформляются repeatable job'ами BullMQ
   (единый Redis) либо берут распределённый лок. Три сообщения об одном инциденте —
   верный признак, что правило нарушено.
4. **Только агрегаты.** Метрики считаются `count`/`groupBy`, а не выгрузкой строк в
   приложение. `findMany` без `take` запрещён и здесь (`BACKEND_RULES`).
5. **Тяжёлые проверки — в воркере**, с таймаутом; размер БД и объём бакетов не считаются
   в HTTP-хендлере.
6. **Пороги — в конфигурации**, не в коде: частота 5xx, глубина очереди, окно тишины,
   SLA заявок. Их придётся крутить по факту, и каждый раз это не должно быть релизом.
7. **Агрегация вместо потока.** Суточные проверки шлют одно сообщение, а не строку на
   каждую находку. Правило простое: если событие может произойти чаще раза в минуту, у
   него обязан быть либо `dedupeKey`, либо окно агрегации.

### 7.5 Тесты

Минимальный набор, без которого задача не считается сделанной:

- маппер каждого источника — на зафиксированном примере payload;
- политика: дедупликация, троттлинг, тишина;
- санитайзер: email и токен не проходят наружу;
- `TelegramOpsService`: сбой транспорта не бросает исключение;
- выключенный модуль: без токена приложение стартует, таймеры не заводятся.

## 9. Как проверить

1. **Без токена.** Убрать `TELEGRAM_BOT_TOKEN`, поднять API: старт без ошибок, в логе
   «Telegram ops выключен», фоновых проверок нет.
2. **Доставка и тема.** Задать переменные, отправить тестовое событие — пришло в свою тему.
3. **Отказоустойчивость.** Подменить токен на неверный: cron-задача, которая шлёт
   сообщение, отрабатывает до конца, в логе ошибка отправки, приложение живо.
4. **Санитайзер.** Отправить событие с email в тексте — в канал приходит без него.
5. **Миграции.** Откатить запись из `_prisma_migrations`, перезапустить API — пришёл список.
6. **Дедупликация.** Уронить cron-задачу трижды подряд — в канале одно сообщение.
7. **Деплой.** Проверить, что при смене статуса правится то же сообщение, а не приходит новое.
8. **Секрет вебхука.** `curl` без заголовка → 401; с верным → сообщение в канале.
9. **Тишина.** `/quiet 30m`, вызвать 🟡-событие — тихо; 🔴 — приходит; по окончании — сводка.

## 10. За рамками

Здесь перечислено то, чего бот **не делает** — чтобы при следующем расширении это
обсуждалось осознанно, а не «дописалось по дороге».

- **Доставка уведомлений пользователям.** Привязка аккаунтов, дайджесты, кнопки
  «Одобрить/Отклонить» в личке — это другой продукт: другой набор рисков (обработка
  персональных данных, согласие при привязке), другая авторизация (`chat_id`
  идентифицирует, но не авторизует) и другая нагрузка. Если такое понадобится,
  доставка пойдёт через существующую очередь уведомлений рядом с push и email, а не
  через `TelegramOpsService`; служебный контур останется служебным.
- **Любые действия над платформой** из чата: рестарт, миграции, сид, рассылки (§0.1).
- **Персональные данные** в сообщениях — идентификаторы и агрегаты вместо ФИО, email и
  содержимого (§0.1, §7.2).
