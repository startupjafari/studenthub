# StudentHub — Unified UX (эпик)

> Программа работ: превратить набор модулей в единый продукт («один день», «одна дисциплина»,
> «одна услуга»). Реализуется **последовательными PR поверх существующей архитектуры** — без
> дублирующих реализаций. Каждый PR переиспользует текущие backend-модули, API, FSD-компоненты,
> дизайн-систему, RBAC/scope, realtime, TanStack Query, Redux, BullMQ.
>
> Правила проекта в силе: один PR = один пункт; i18n ru/kk/en; проверки `lint`/`test`/`build`
> перед «готово»; стоп-точки (миграции на непустой БД, смена контрактов/guard/WS-формата) —
> только с явного согласия человека.

## Принципы

1. **Reuse-first.** Перед каждым разделом — анализ существующей реализации; новые сущности только
   если нельзя выразить через имеющиеся. Backend-модули физически не сливаем — агрегируем.
2. **BFF-агрегация.** Главные экраны питаются агрегирующими endpoint'ами `/me/*`, а не десятком
   отдельных запросов. Домены остаются раздельными на уровне сервисов.
3. **Role-first.** Контент и действия ранжируются под роль (STUDENT/STAROSTA/TEACHER/DEAN/…).
4. **Единый день / дисциплина / услуга.** UX связывает модули, не смешивая их данные.

## Стоп-точки (нужен явный OK перед реализацией)

| Пункт | Почему стоп-точка | План |
|---|---|---|
| #12 Единый WS-envelope `domain.entity.action` | Меняет формат WS-событий, от которых зависят текущие клиенты (`message:new` и т.д.) | Ввести **параллельно** новый канал `event` с envelope `{ type, entityId, version, ts, data }`, старые события не трогать; клиентов мигрировать постепенно; удалить старые события отдельным PR после проверки |
| #6 Документ ↔ Заявка (переиспользование одного файла) | Схема/миграция на непустой БД | Показать SQL; связь через `ApplicationDocument.documentId` (грант доступа), файл хранится один раз в домене «Документы» |
| #14 Unified Activity | Возможная миграция | Сначала **контракт** `Activity` (общий DTO поверх `ApplicationEvent`/`DocumentEvent`/`AuditLog`) без слияния таблиц; физическая унификация — отдельно, если понадобится |
| #15 `/me/*` контракты | Добавление endpoint'ов | Аддитивно, стандартный envelope `{success,data}` — реализуемо без стоп-точки; фиксируется в `docs/PROJECT.md §8.3` |

## Последовательность PR

### PR-1 — BFF `/me/today` + role-aware Action Center (пункты 1, 9, 15) ← **старт**
- Backend: новый модуль `apps/api/src/modules/me` (`MeController`/`MeService`), **переиспользует**
  `SchedulesService`, `EventsService`, `NotificationsService`, `AssignmentsService`,
  `ApplicationsService` (импорт модулей, не копирование логики). Endpoint `GET /me/today` собирает:
  следующая пара + timeline дня, «требует действия» (задания/заявки/дедлайны), события,
  свежие изменения расписания. Форма ответа зависит от роли.
- Contract: новый файл `packages/shared-schemas/src/me.ts` (аддитивно) — `MeTodaySchema`.
- Frontend: слайс `entities/me` (api + query-ключи), экран `views/today` переводится с 6 запросов
  на один `fetchMeToday()`; существующие `NextPairCard`/`TodayTimeline`/`AttentionList`/`RecentChanges`
  переиспользуются. `ROLE_HOME` для student → «Сегодня» как операционный дом.

### PR-2 — Universal Inbox / Центр активности (пункт 2)
- Расширить `views/notifications` (сейчас — только поповер колокольчика) до центра с табами
  **Все / Требует действия / Учёба / Деканат / Социальное / Системное**. Категория выводится из
  `NotificationType`. У каждого уведомления — контекст + прямое действие (deep-link на экран/действие).
- Backend: у `Notification` добавить (если нет) поле `actionUrl`/`category` в DTO-проекции
  (вычисляемо из type/entity — без миграции). Переиспользовать `entities/notification`.

### PR-3 — Workspace дисциплины (пункт 3, 4)
- Frontend-агрегация в `views/courses/course-view.tsx`: вкладки **Обзор / Расписание / Задания /
  Материалы / Оценки / Посещаемость / Чат** одной дисциплины. Данные — из существующих
  `entities/{course,schedule,assignment,material,gradebook,attendance,chat}`. Backend не меняем;
  при необходимости — BFF `GET /me/course/:id` (аддитивно).
- Интерактивная карточка пары (`schedule-grid`/`next-pair-card`): преподаватель, аудитория, тема,
  материалы, задание, посещаемость, чат дисциплины, QR check-in, онлайн-ссылка.

### PR-4 — Заявки ↔ Документы (пункты 5, 6) — **стоп-точка #6**
- Автоподстановка данных студента в форму заявки (из `users/me`), выбор документа из хранилища
  вместо повторной загрузки (грант доступа), SLA/ожидаемая дата (`dueAt`), QR получения оригинала.
- Один файл — одно хранение; переиспользование через ссылку/грант. Показать SQL до миграции.

### PR-5 — Student Pass v2 (пункт 7)
- Расширить `student-id`: статус обучения, курс, факультет/группа, доступные сервисы. Архитектура
  QR-токена — расширяемая под кампус/библиотеку/мероприятия (тип сервиса в payload токена).

### PR-6 — Global Search + Command Palette (пункт 8, 11)
- Расширить `search` на чаты/события (сейчас: люди/дисциплины/задания/материалы). Быстрые команды
  палитры и единая кнопка **Quick Actions** — набор зависит от роли (пост/событие/заявка/документ/
  сообщение/задание/материал/посещаемость/приглашение). Переиспользовать `command-palette`,
  `quick-actions.ts`.

### PR-7 — Early Warning Analytics (пункт 10)
- Расширить `analytics`: индикаторы «требует внимания» с **явными причинами** (низкая посещаемость
  &lt;60%, просроченные задания, падение среднего балла). Никаких непрозрачных авторешений — только
  объективные признаки и drill-down. Переиспользовать `dean-analytics`, `stats-dashboard`.

### PR-8 — Realtime envelope + delayed jobs (пункты 12, 13) — **стоп-точка #12**
- Параллельный WS-канал `event` с envelope `{ type: 'domain.entity.action', entityId, version, ts, data }`.
- Перевести SLA/expiration/reminders/scheduled-posts на **delayed BullMQ jobs**; cron оставить как
  reconciliation (догоняет пропущенное). Переиспользовать существующие очереди.

### PR-9 — Unified Activity contract (пункт 14) — **стоп-точка #14**
- Общий DTO `Activity` поверх `ApplicationEvent`/`DocumentEvent`/`AuditLog`; endpoint
  `GET /me/activity`. Без слияния таблиц.

### PR-10 — PWA offline (пункт 16) ✅ + BFF-расширение (пункт 15)
- **PWA offline-кэш** — `runtimeCaching` (NetworkFirst, только GET) для расписания, Student Pass,
  `/me/today`, недавних материалов/заданий, части истории сообщений. Критические мутации
  (POST/PUT/PATCH/DELETE) не перехватываются → только online. Реализовано в `apps/web/next.config.mjs`.
- **BFF `/me/dashboard` / `/me/actions` / `/me/bootstrap`** — сознательно НЕ добавлены как отдельные
  endpoint'ы: были бы дубликатами `/me/today` (данные дашборда/действий уже там, роль-aware) и
  `analytics.facultyOverview` / `applications/queue-stats` (для сотрудников). Reuse-first: главные
  экраны уже делают один агрегирующий запрос. `/me/bootstrap` (профиль + unread за один вызов) —
  возможная микрооптимизация загрузки, отложена до реальной необходимости.

## Definition of Done (каждый PR)
- Переиспользованы существующие API/типы/схемы/хуки/компоненты; нет параллельных реализаций.
- i18n ru/kk/en (parity), desktop/mobile/PWA, светлая/тёмная тема.
- RBAC/scope/аудит соблюдены; контрактные изменения зафиксированы в `docs/PROJECT.md`.
- `pnpm --filter <api|web> lint|test|build` — зелёные, вывод приложен.
