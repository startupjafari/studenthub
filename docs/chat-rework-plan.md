# Переписка iOS: глубокая переделка — план

Итерация 7 `PERFORMANCE_AUDIT.md` (пункты 8, 9, 12, 13, 14 и хвосты 10, 11, 15). **Только
план, кода нет.** Решение о каждом шаге — после замеров на устройстве по меткам итерации 1.

## Урок, с которого начинаем

Своя раскладка ленты с кешем высот (#479/#480) на устройстве дала пустоты между
сообщениями и откатана (#481). Отсюда правила этого плана:

1. Системный список (`UICollectionView` + `UIHostingConfiguration`, компоновка — системная)
   и размеры ячеек **не трогаем**. Переделываем то, что происходит до ячейки: чтение базы,
   сборку ленты, снапшот, тело пузыря.
2. Каждый шаг — за своим флагом `PerformanceFlags`, отдельным коммитом и с замером «до/после»
   на одном и том же устройстве и чате.
3. Шаг, который не дал выигрыша по метрике, не вливаем, даже если он «правильнее».

## Что уже сделано (итерации 1 и 4)

| Было (п. аудита) | Сделано |
| --- | --- |
| Наблюдения без отсева повторов (1) | `.removeDuplicates()` вне главного потока на всех наблюдениях переписки и списка |
| `apply` на каждый пересчёт экрана (2) | Ранний выход по номеру ленты, контексту и выбору |
| Отметка о прочтении перенастраивала всю ленту (8) | Перенастраиваются только свои сообщения, чьи галочки сменились |
| «Печатает…» пересчитывало весь список (4) | Наблюдаемый объект на чат |
| `MessageTimeline.build` на главном потоке (12, часть) | Сборка — в фоновой задаче, опоздавшая сборка отбрасывается номером |
| Разбор Markdown/ссылок в теле пузыря (3) | Кеш разбора, разбор свежего края — в той же фоновой задаче до показа |

Осталось главное: **на каждое изменение базы — работа O(N) по всем загруженным сообщениям**
(чтение среза целиком, сборка ленты целиком), и N растёт с каждой страницей истории.

## Что переделывать

### Шаг 1. Тонкая история: не ждать 2,5 с (п. 9) — низкий риск

Сейчас первое открытие чата, где в базе меньше страницы, скрывает ленту и крутит индикатор
до ответа сети или 2,5 с (`holdsThinHistory`). Предел — 0,6 с, после него показываем, что
есть, и досыпаем страницу снизу вверх без прыжка (новые строки — над первой видимой).

- Флаг: `chatThinHistoryShortWait`.
- Риск: прыжок позиции, когда страница приходит после показа. Уже есть механизм удержания
  якоря при подгрузке истории — проверить, что он срабатывает и для первой страницы.

### Шаг 2. Хвосты низкого риска (п. 10, 11, 15)

- `saveAttachments`: сравнивать с текущими перед записью, не удалять/вставлять одинаковое
  (лишняя запись будит наблюдения ленты); поиск своего неотправленного — по частичному
  индексу `sendState != sent`.
- Стикеры: чтение файла и `UIImage` — в акторе, `byPreparingForDisplay`, каталог создаётся
  один раз.
- Тело пузыря: `ProfileShare.parse`, `formatted()` времени и resample волны голосового —
  один раз на элемент ленты (в `MessageTimeline.Item` при сборке, вне главного потока);
  строка файла подписывается только на свой прогресс.
- Флаг на этот шаг не нужен: поведение и вид не меняются. Тесты — на `saveAttachments`
  (без изменений — без записи) и на готовые поля элемента ленты.

### Шаг 3. Кеш в `ChatBubbleStack` (п. 13) — средний риск

Свой `Layout` пузыря без кеша: каждый ребёнок меряется 2–3 раза за проход. `makeCache`/
`updateCache` с размерами детей для последней ширины; сброс при смене ширины и Dynamic
Type. Размеры не меняются — меняется число вызовов `sizeThatFits`.

- Флаг: `chatBubbleLayoutCache`.
- Риск: устаревший кеш при смене содержимого без смены ширины (правка сообщения,
  пришедшая картинка). `updateCache` вызывается системой при смене детей — проверить
  тестом раскладки на снимках (одинаковые кадры с кешем и без).

### Шаг 4. Наблюдать окно у свежего края (п. 12) — высокий риск

Сейчас `readSnapshot` читает все сообщения чата и все вложения, и каждое изменение базы
перечитывает всё. Предлагается:

- наблюдение — только «живое окно»: последние `K` сообщений (`K` ≈ 150) и их вложения
  (`LIMIT` по `seq`/`createdAt`, тот же порядок);
- страницы истории — отдельный неизменяемый массив в модели; читается разово при подгрузке
  и перечитывается точечно, когда событие сокета касается сообщения из истории (правка,
  удаление, реакция) — по id, а не всё;
- лента = история + окно, склейка по `seq` без повторов.

- Флаг: `chatWindowedObservation`. Выключен — прежнее наблюдение всего чата.
- Тесты: «окно + история» = «весь чат» для последовательностей вставок, правок,
  удалений, отложенных отправок (случайные последовательности, сравнение с полной
  сборкой).

### Шаг 5. Сборка ленты по изменениям (п. 12) — высокий риск

`MessageTimeline.build` по всем N на каждый срез. После шага 4 вход маленький, но разбивка
по дням и группам авторов всё равно строится заново. Инкрементально: изменение окна
(добавлены в конец, изменены по id, удалены) → правка затронутых дней и соседних групп
(граница группы зависит от соседа), остальные дни — те же значения.

- Флаг: `chatIncrementalTimeline`.
- Тесты: инкрементальная сборка = полная сборка на тех же случайных последовательностях
  (включая смену дня, «непрочитанные» и свои неотправленные).

### Шаг 6. Без `UIViewRepresentable`-якорей и тени в пузыре (п. 14) — средний риск

В каждой ячейке два якоря для меню (рамка пузыря и реакций) и `.shadow` у чужих пузырей в
светлой теме. Рамку брать из ячейки в момент долгого нажатия (`cell.convert`), тень —
второй заливкой со сдвигом.

- Флаг: `chatAnchorFromCell`.
- Риск: меню и «лупа» встают не там (iOS 17 и 26, клавиатура открыта, режим выбора).

## Какие замеры итерации 1 это обосновывают

Метки — подсистема `kz.studenthub`, категория `Chats` (Instruments → os_signpost).

| Метка | Что показывает | Довод за шаг |
| --- | --- | --- |
| `ThreadSnapshotRead` (интервал, `messages: N, attachments: M`) | Чтение среза на каждое изменение базы | Растёт с N → шаг 4. Порог: p95 > 8 мс при N ≈ 2000 |
| `DBChangeObserved` (событие) | Сколько раз срез действительно сменился | Частота × длительность чтения = бюджет, который съедает чат |
| `TimelineBuild` (интервал, `messages: N`) | Сборка ленты в фоне | Растёт с N и задерживает показ нового сообщения → шаг 5. Порог: > 16 мс при N ≈ 2000 |
| `SnapshotApply` (интервал) | Применение снапшота | Если доля в hitch'ах заметна после шагов 4–5 — смотреть перенастройки |
| `MessageReceived` → конец `SnapshotApply` | Задержка «пришло → видно» | Главная метрика шагов 4–5 |
| `FirstContentFrame` (событие, `items: N`) | Первый кадр переписки при открытии | Шаг 1 (тонкая история) |
| `TextParse` / `TextPrepare` (итерация 4) | Разбор при прокрутке | Должен быть ≈ 0 на прокрутке; если нет — кеш мал или ключи плывут |
| Time Profiler: `ChatBubbleStack.sizeThatFits` | Повторные замеры пузыря | Доля > 5 % времени главного потока на прокрутке → шаг 3 |
| Time Profiler: создание `UIViewRepresentable` при настройке ячейки | Цена якорей | Заметная доля → шаг 6 |

**Сценарий замера (один на все шаги):** чат с 3000+ сообщений (сид или реальный),
iPhone не новее 12; открыть; долистать вверх на 5 страниц; получить 10 сообщений и 10
отметок о прочтении с другого устройства; набрать сообщение. Instruments: Animation Hitches
+ os_signpost + Time Profiler. Сравнивать один и тот же сценарий до и после, три прогона,
медиана.

## Какие метрики должны улучшиться

| Метрика | Сейчас (ожидаемо) | Цель |
| --- | --- | --- |
| `ThreadSnapshotRead` на изменение | O(N): растёт с каждой страницей | O(K): не зависит от длины истории |
| `TimelineBuild` на изменение | O(N) | O(изменения) |
| «пришло → видно» (`MessageReceived` → `SnapshotApply`) | растёт с N | < 50 мс независимо от N |
| Hitch ratio на прокрутке длинного чата | — (снять) | < 5 мс/с (Apple: «хорошо») |
| `sizeThatFits` пузыря на кадр прокрутки | 2–3 замера на ребёнка | 1 |
| Первый кадр тонкой истории | до 2,5 с | ≤ 0,6 с |
| Память длинного чата | все сообщения в срезе дважды (срез + лента) | окно + неизменяемая история |

## Как делать поэтапно

1. Снять базу: сценарий выше на текущей ветке, записать числа в этот файл.
2. Шаги 1 и 2 (низкий риск) — одним PR, замер.
3. Шаг 3 — PR, замер; не дал выигрыша по `sizeThatFits`/hitch — не вливаем.
4. Шаг 4 — PR с флагом, выключенным по умолчанию; неделя на внутренней сборке с
   включённым; затем включить по умолчанию.
5. Шаг 5 — то же, после шага 4 (без окна выигрыш меньше, а риск тот же).
6. Шаг 6 — последним: самый заметный глазом, самый лёгкий на откат флагом.

Каждый шаг — отдельная ветка от `develop`, отдельный PR, юнит-тесты на логику
(эквивалентность сборок), ручная проверка по `CHECKLIST.md` (раздел «Переписка»).

## Что может сломаться

- **Позиция прокрутки** при склейке истории и окна, при подгрузке страницы и при переходе
  окна (сообщение уехало из окна в историю) — прыжок или пустота. Именно это сломало
  #479/#480; поэтому якорь — по id первой видимой строки, а не по смещению.
- **Разделитель «непрочитанные»** — считается по последним сообщениям чата; при окне —
  только по окну, если непрочитанных больше `K`, разделитель должен встать в истории.
- **Переходы к сообщению** (поиск, ответ, закреплённое, ссылка из пуша) за пределы окна —
  нужен «сброс окна» вокруг цели (`pendingWindowReset` уже есть — расширить).
- **Правки, удаления и реакции в истории** — не придут через наблюдение окна: нужна
  точечная перечитка по id из событий сокета; пропуск = устаревшее сообщение в ленте.
- **Свои неотправленные** (outbox) — должны быть видны всегда, даже если старше окна.
- **Отметки о прочтении** для своих сообщений в истории — перенастройка по id.
- **Режим выбора** через границу окна и истории; пересылка выбранного.
- **Группы авторов** на стыке истории и окна (кто первый в группе — аватар, хвостик).
- **Меню и лупа** (шаг 6) — рамка из ячейки при открытой клавиатуре, в режиме выбора, на
  iOS 17 и 26, при Dynamic Type.
- **VoiceOver** — порядок и фокус при перенастройке только части ячеек.

## Что решить после замеров

- Брать ли шаги 4–5 вообще: если на реальных чатах N редко больше 500, а
  `ThreadSnapshotRead` < 4 мс, хватит шагов 1–3.
- Размер окна `K` — по длительности чтения и по тому, сколько сообщений видно на iPad.
- Нужен ли отдельный флаг на каждый шаг 2 (сейчас — без флага).
